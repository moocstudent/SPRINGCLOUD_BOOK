## The internal network is not a trust boundary

For twenty years, security meant one thing: build a hard shell, trust the soft inside. Put a firewall at the edge, and any process already in the datacenter could call any other with no questions asked. Split a monolith into forty services and that model quietly becomes a liability. The forty services still talk over the internal network, and the old habit says "we're behind the firewall, so a call from another service is trusted." An attacker who phishes one credential, exploits one unpatched Log4j, or compromises one leaky container now stands inside that soft interior — and every service that trusts "internal" traffic hands them the next hop for free. This is **lateral movement**: one breached service becomes forty, because the perimeter was the only wall.

The fix is to stop treating "inside" as a fact about trust. Every call — north-south from the client and east-west between services — carries and proves an identity.

## One login at the edge, one token for the whole chain

The user authenticates once, at the gateway, through OAuth2 / OIDC against an identity provider (Keycloak, Auth0, or your own). In return the gateway attaches a **JWT** to the request: a signed token of three parts (`header.payload.signature`) whose payload carries claims — `sub` (who), `scope` or roles (what they may do), `iss` (who signed it) and `exp` (when it dies). That token then rides the `Authorization: Bearer` header hop by hop: gateway to order, order to inventory, inventory to payment.

The point of signing is that every downstream service verifies the token **locally**. It fetches the identity provider's public keys once (the JWKS endpoint), caches them, and from then on checks the signature and `exp` in memory — no round-trip to the auth server per call. A forged or expired token fails the check at the door.

@fig sc22-jwt

In Spring Security a service becomes a resource server with a few lines:

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.shop.internal/realms/shop
          jwk-set-uri: https://auth.shop.internal/realms/shop/protocol/openid-connect/certs
```

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
  http
    .authorizeHttpRequests(a -> a
      .requestMatchers("/orders/**").hasAuthority("SCOPE_order.write")
      .anyRequest().authenticated())
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));
  return http.build();
}
```

## JWT versus opaque token: the revocation you cannot take back

The self-contained JWT is fast precisely because nobody has to be asked. That same property is its weakness: once issued, it is valid until `exp`, and you cannot un-issue it. Steal a JWT with a one-hour lifetime and the thief has an hour. An **opaque token** — a random string the service must send to the auth server's introspection endpoint on every call — flips both properties: instantly revocable, but a network round-trip and load on the auth server for every single request.

| Property | JWT (self-contained) | Opaque token |
|---|---|---|
| Verify cost | local, ~0.1 ms, no network | introspection call, +1 to 5 ms/req |
| Auth-server load | keys fetched once | one lookup per call |
| Revoke before expiry | hard — valid until `exp` | instant |
| Token size on the wire | ~0.5 to 1 KB | ~32 bytes |
| Best when | high call volume, short TTL | revocation must be immediate |

The usual compromise is short-lived JWTs (5 to 15 min) plus refresh tokens, so a leaked token dies soon and the revocation window is small; add a denylist only for the few tokens you must kill right now — accepting that the denylist reintroduces a lookup.

## mTLS and the per-call bill of zero trust

A JWT proves who the *user* is; it does not prove which *service* is calling. For that, use **mTLS** — mutual TLS, where both client and server present certificates and each verifies the other. Now the inventory service accepts a connection only from a peer holding a certificate signed by your internal CA, so a rogue container with a stolen JWT still cannot open the socket. A service mesh (Istio, Linkerd) usually issues and rotates these certificates through sidecars, so application code stays clean.

None of this is free. mTLS adds a handshake (one extra round-trip on a cold connection, plus CPU for the asymmetric crypto); JWT parsing and signature checks cost per request; and "authenticate every call" means paying that on every hop, not once at the edge. That is the literal meaning of **zero trust**: no call is trusted for being internal, and the bill is a few milliseconds and some CPU on each one. The bench lets you toggle gateway validation, token expiry and mTLS on a multi-hop call and watch the security-versus-overhead needle move — turning mTLS on closes the rogue-service hole but adds latency to every east-west call.

## Exercises

1. Stand up Keycloak (or any OIDC provider), configure one service as a resource server with the yaml above, and call it with an expired JWT — confirm you get a 401 without any traffic reaching the auth server.
2. Measure it: put a stopwatch around local JWT verification versus a token-introspection call to your auth server. Record both, and compute how many introspection calls per second your auth server would take at 5,000 req/s.
3. On the bench, breach one service (stolen JWT) with mTLS off, then on. Describe exactly which hop stops the attacker in each case.
4. Design a revocation story for your team: token TTL, refresh lifetime, and which specific events (password reset, logout, role change) must force an immediate kill, and how.
