## 内网不是信任边界

二十年来,安全约等于一件事:造一层硬壳,信任柔软的内部。边界上架一道防火墙,凡是已经在机房里的进程,调用彼此都不必盘问。可一旦把单体拆成四十个服务,这个模型就悄悄变成了负债。四十个服务照样在内网里互相通信,而旧习惯说「反正都在防火墙后面,别的服务发来的调用就是可信的」。攻击者只要钓到一个凭证、打穿一个没打补丁的 Log4j、或攻陷一个有漏洞的容器,就站进了这层柔软的内部——而每一个信任「内网流量」的服务,都免费把下一跳递给了他。这就是**横向移动**:一个被攻破的服务变成四十个,因为那道边界是唯一的墙。

解法是:不再把「在内网里」当成一个关于信任的事实。每一次调用——南北向的客户端请求、东西向的服务间调用——都要携带并证明一个身份。

## 在入口登录一次,一个令牌走完全链路

用户只在网关处登录一次,通过 OAuth2 / OIDC 向身份提供方(Keycloak、Auth0、或你自建的)认证。作为回报,网关给请求附上一个 **JWT**:一个由三段组成(`header.payload.signature`)的签名令牌,payload 里装着声明——`sub`(是谁)、`scope` 或角色(能干什么)、`iss`(谁签的)、`exp`(何时失效)。这个令牌随 `Authorization: Bearer` 头逐跳传递:网关到订单,订单到库存,库存到支付。

签名的意义在于,每个下游服务都在**本地**验签。它只需从身份提供方拉一次公钥(JWKS 端点)并缓存,之后每次都在内存里校验签名和 `exp`,不必为每次调用回头去问认证中心。伪造的或过期的令牌,在门口就被挡下。

@fig sc22-jwt

在 Spring Security 里,几行配置就能让一个服务变成资源服务器:

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.shop.internal/realms/shop
          jwk-set-uri: https://auth.shop.internal/realms/shop/protocol/openid-connect/certs
```

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
  http
    .authorizeHttpRequests(a -> a
      .requestMatchers("/orders/**").hasAuthority("SCOPE_order.write")
      .anyRequest().authenticated())
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));
  return http.build();
}
```

## JWT 还是不透明令牌:那个收不回的授权

自包含的 JWT 之所以快,恰恰因为不必问任何人。而这一点也正是它的软肋:一旦签发,它在 `exp` 之前始终有效,你无法「反悔」。偷到一个有效期一小时的 JWT,窃贼就有一小时。**不透明令牌**——一串随机字符串,服务每次都得送到认证中心的内省(introspection)端点去问——把这两个性质都反了过来:可以即时吊销,但每一个请求都要付出一次网络往返、并给认证中心压上一次查询。

| 特性 | JWT(自包含) | 不透明令牌 |
|---|---|---|
| 验证成本 | 本地,约 0.1 毫秒,无网络 | 内省调用,每请求 +1 到 5 毫秒 |
| 认证中心负载 | 公钥只拉一次 | 每次调用一次查询 |
| 过期前吊销 | 难——`exp` 之前一直有效 | 即时 |
| 线上令牌大小 | 约 0.5 到 1 KB | 约 32 字节 |
| 适用场景 | 高调用量、短 TTL | 必须即时吊销 |

常见的折中是:用短命 JWT(5 到 15 分钟)配刷新令牌,这样泄露的令牌很快就死,吊销窗口很小;只对少数必须马上杀掉的令牌加一份黑名单——并接受黑名单重新引入了一次查询。

## mTLS 与零信任的每次调用账单

JWT 证明的是**用户**是谁,它不证明**哪个服务**在发起调用。要证明后者,用 **mTLS**——双向 TLS,客户端和服务端都出示证书、都验证对方。这样库存服务只接受持有你内部 CA 签发证书的对端连接,一个偷了 JWT 的流氓容器,连 socket 都打不开。服务网格(Istio、Linkerd)通常用 sidecar 来签发和轮换这些证书,让业务代码保持干净。

这一切都不是免费的。mTLS 多一次握手(冷连接上多一个往返,加上非对称加密的 CPU);JWT 的解析和验签每个请求都要花;而「每次调用都认证」意味着这笔开销要在每一跳上付,而不是只在入口付一次。这正是**零信任**的字面意思:没有哪次调用因为「来自内网」就被信任,代价是每一次都多花几毫秒和一点 CPU。治理台让你在一次多跳调用上开关网关校验、令牌过期和 mTLS,看着安全与开销这根指针来回移动——打开 mTLS 堵住了流氓服务的洞,但给每一次东西向调用都加了延迟。

## 练习

1. 起一个 Keycloak(或任意 OIDC 提供方),用上面的 yaml 把一个服务配成资源服务器,再用一个过期的 JWT 去调它——确认你拿到 401,且没有任何流量打到认证中心。
2. 量一量:给本地验签和一次向认证中心的令牌内省调用分别掐表,把两个数都记下来,并算出在 5,000 请求/秒时,你的认证中心每秒要扛多少次内省调用。
3. 在治理台上分别在 mTLS 关闭、开启两种情况下攻破一个服务(偷来的 JWT)。说清每种情况下到底是哪一跳把攻击者挡住了。
4. 给你的团队设计一套吊销方案:令牌 TTL、刷新有效期,以及哪些具体事件(改密码、登出、改角色)必须强制即时杀掉令牌、又该怎么做。
