## 为什么要采样

OB1 里你给每条请求打了 traceId、画出了它的瀑布图。调一条请求时,这很美妙;可当你一秒有一百万条时,这会要命。每条请求产生十几个甚至更多 span,每个 span 几百字节,每个都要通过网络导出、存储、建索引。乘起来,把所有请求都追踪的开销,可能比跑那些被追踪的服务本身还大。所以在任何真实的量级上,你都得**采样**:留一部分 trace,把其余的扔掉。有意思的问题——也是本章的全部——是你留哪些,以及*你在什么时候决定*。

## 头部采样:在起点决定并传播

最简单的方案是头部采样(或叫「起点采样」):在第一跳,通常是网关,你做一个决定——这条 trace 采不采?——然后把这个决定传给请求经过的每一个服务。这个「传播」不是附带的,它才是关键。W3C 的 `traceparent` 头里有一个 flags 字节,它的最后一位就是「sampled」标志;默认每个服务是 **parent-based**(基于父级)的:它服从收到的那一位,而不是自己重新决定。正是这一点保证了一条 trace 的一致性——它的所有 span 要么全记录、要么全不记录。一条一半 span 被采、一半被丢的 trace 是坏的、读不了的,而头部采样从设计上就避免了它。

@fig sc30-sample

头部采样便宜(一个决定,不用缓冲)又简单(配置里一个概率)。但它有个刻在名字里的硬伤:决定是在*起点*做的,在请求还没跑、你还不知道它有没有出错、慢不慢的时候。一个 1% 的头部采样器,留住 1% 的所有 trace——因此也只留住 1% 的错误。那条顾客正在投诉的、慢了 3 秒的下单,在它还没跑完之前,就有 99% 的概率被扔掉了。治理台把这一点变得触目惊心:在 1% 下,二十条出错的 trace,你一条都没捕获到。

## 尾部采样:等 trace 完成再决定

尾部采样把时机倒过来。不在起点决定,而是每个服务都记录自己的 span、发给一个收集器,收集器把一条 trace 的所有 span 缓冲住,直到这条 trace 跑完。只有到那时,知道了完整结果,它才决定要不要留。现在你能表达你真正想要的策略了:含错误的 trace 100% 留、慢过 800 毫秒的 100% 留、其余无聊的只留 1%。你再也不会漏掉那次事故,因为你是在事故发生*之后*才决定的。

这份能力有实打实的基础设施代价。得有个东西把每一个在途的 span 都缓冲到它的 trace 结束——那是内存,还有一个你必须调的 `decision_wait`(太短,你就在慢 trace 还没跑完时就决定了)。还有一个常把人绊倒的路由约束:一条 trace 的所有 span 必须到达**同一个收集器实例**,否则没有哪个收集器能看到整条 trace 来判断——所以你要在收集器集群前面放一个按 traceId 路由的负载均衡。这也是为什么尾部采样是 OpenTelemetry Collector 的功能,而不是一行 Spring 配置。

## 取舍

两者都不是普适正解;它们坐在成本 / 可见性 / 基础设施三角的不同点上:

| | 头部采样 | 尾部采样 |
|---|---|---|
| 何时决定 | 起点,还不知道结果 | 结尾,已知道结果 |
| 是否捕获每个错误 | 否(只有被采样的那部分) | 是 |
| 成本 / 复杂度 | 便宜,一行配置 | 一个缓冲收集器,要调参 |
| 一致性 | 靠传播的 sampled 位 | 全都记录,收集器决定 |
| 住在哪 | 应用里(Micrometer) | 收集器里 |

一个常见而务实的答案是把两者结合:用一个适度的头部采样把原始量压住,再在收集器里用尾部采样保证——不管最后留下什么,错误和慢 trace 总在里面。先上头部采样,因为它免费;等你第一次去查一次事故、却发现它的 trace 根本没被留下时,再去上尾部采样。

## 练习

1. 把 `management.tracing.sampling.probability` 设成 0.01,制造一个错误;确认你通常找不到它的 trace。调到 1.0,看着你的存储账单(以及那条 trace 出现)。
2. 起一个带 `tail_sampling` 处理器、留住所有错误的 OpenTelemetry Collector;复现那个错误,确认在很低的基础采样率下它的 trace 总被留住。
3. 在一条 trace 的两个服务上查看 `traceparent` 头,确认 sampled 位相同——那个被传播的、一致的决定。
4. 故意搞坏尾部采样:跑两个不做 traceId 路由的收集器实例,观察 trace 被拆到两边,没有哪个策略看得到整条 trace。
