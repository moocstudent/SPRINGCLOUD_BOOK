## 一份日志不够用的那天

单体里,「下单很慢」是个五分钟的问题:grep 一个文件,找到这次请求,把堆栈从上读到下。把这次下单拆到网关、订单、库存、优惠、支付、通知六个服务上,同一次请求就在六台机器上写了六份日志,每台机器有自己的时钟、自己的行号,没有任何东西把它们连起来。你只能猜是哪一跳慢了——而猜,正是让一次二十分钟的故障拖成三小时的原因。

链路追踪把这条链重新接上,想法很小:每一条进入系统的请求被打上一个 **traceId**——128 位、十六字节、写成三十二个十六进制字符、全局唯一。这条请求下的每一段工作——一个服务在处理它、一次对外的 HTTP 调用、一次数据库查询——都开一个 **span**:记录开始时间、结束时间、属于哪个服务,以及指向父 span 的指针。于是一条 trace 就是一棵共享同一个 traceId 的 span 树,而因为每个 span 都带着父亲,这棵树能精确还原「谁调用了谁」。

### 上下文必须跟着跑

traceId 如果在第一个服务就停下,它就毫无用处。它必须在每一跳上传递,而它靠 HTTP 头传递。W3C 标准头叫 `traceparent`,值得逐字节记住,因为总有一天你会在抓包里读到它:

| 字段 | 示例 | 含义 |
|---|---|---|
| version | `00` | 格式版本 |
| trace-id | `4bf92f3577b34da6a3ce929d0e0e4736` | 16 字节——整条请求 |
| parent-id | `00f067aa0ba902b7` | 8 字节——调用方那个 span |
| trace-flags | `01` | 是否被采样(01 采样,00 不采样) |

老一点的 B3 格式(来自 Zipkin/Brave)把同样的信息拆到 `X-B3-TraceId`、`X-B3-SpanId`、`X-B3-ParentSpanId`、`X-B3-Sampled` 几个头里。不管你选哪种,每次调用的两端必须约定一致,否则这条 trace 就从中间断成两截。

### 瀑布图把慢的那一跳钉住

span 收集齐之后,把它们画在同一根时间轴上——每个 span 是一条从开始到结束的横条,子 span 嵌在父 span 下面。这就是**瀑布图**,也是全部的回报所在。一次花了 900 毫秒的请求不再是谜:你看到网关 40 毫秒、订单 30 毫秒、库存 20 毫秒,然后是支付调用银行接口那一条 800 毫秒的长条。慢在哪一跳不用争论,是被指出来的。治理台渲染的正是这个——一次真实的多服务调用被画成可交互的瀑布图——拖动那些 span,看最长的那条自己跳出来。

### Spring Boot 3:Micrometer Tracing

在 Spring Boot 3 上,负责埋点的是 **Micrometer Tracing**,它取代了 Spring Cloud Sleuth(Sleuth 没有跟上 Boot 3)。你加一个通向 tracer 的桥——`micrometer-tracing-bridge-brave`(Brave)或 `-bridge-otel`(OpenTelemetry)——再加一个上报器比如 `zipkin-reporter-brave` 把 span 发出去,以及 `spring-boot-starter-actuator`,追踪的自动配置在它手里。后端是可换的:Zipkin 上手快,Grafana Tempo 用对象存储便宜地长期留存,或者一个 OTLP collector 分发给任何东西。

```yaml
management:
  tracing:
    sampling:
      probability: 0.10                 # 保留 10% 的 trace
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans
logging:
  pattern:
    level: "%5p [%X{traceId:-},%X{spanId:-}]"   # traceId 打进每一行日志
```

最后那一行为下一章埋了伏笔:Micrometer 把 traceId 放进日志的 MDC,于是画出瀑布图的那个 id,也标在了每一行日志上。

### 采样是一笔按 trace 计费的账

`probability: 0.10` 是那个承重的数字。在 10000 请求/秒下追踪每一条请求,意味着每秒 10000 条 trace 要序列化、传输、存储——存储和网络成本是实打实的,生产上 1–3% 很常见。但采样是一场赌博。头部采样(head-based)在入口处就决定,那时它还不知道这条请求会失败还是会变慢,于是你最想要的那条 trace,恰恰是最可能被丢掉的那条。尾部采样(在 OTel collector 里)先把 span 缓存起来,再留下有意思的——所有错误、所有超过 500 毫秒的——代价是一个有状态、要在内存里攒 span 的 collector。最该怕的失败模式是无声的:一次线程池交接、一个 `@Async` 边界、一个不传播头的消息队列,trace 就在那里断掉,留下一个树桩而不是一棵树。

## 练习

1. 给两个服务(一个调用方、一个被调方)加上 `micrometer-tracing-bridge-brave` + `zipkin-reporter-brave`,用 Docker 跑一个 Zipkin(`openzipkin/zipkin`),发一条穿过两者的请求,在 Zipkin UI 里找到这一条 trace。确认两个服务共享同一个 traceId,且被调方的 span 是调用方 span 的子节点。
2. 把 `management.tracing.sampling.probability` 依次设成 `1.0`、`0.1`、`0.0`,每次发 20 条请求,数一数 Zipkin 里出现几条 trace,并解释这些数字。
3. 在调用方里加一个 `@Async` 方法或一个裸的 `new Thread(...)`,观察 trace 在这个边界处断掉;再恢复上下文传播(一个 `taskDecorator`),确认子 span 重新出现。
4. 在治理台里加载瀑布图,找出最长的 span,用一句话说明你会先优化哪一跳、为什么。
