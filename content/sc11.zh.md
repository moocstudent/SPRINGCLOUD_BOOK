## 在门口把令牌验一次

JWT(JSON Web Token)是一份签了名的身份声明:一个头、一段声明载荷(用户 id、角色、过期时间)、以及签发方用私钥算出的签名。因为签名是自包含的,任何持有公钥的一方都能校验它、不用查数据库。这就让网关成了校验它最合适的地方:**在入口把签名验一次**,确认没过期,解出用户身份,再把身份放进一个可信的头(比如 `X-User-Id`)透传给后端,同时把客户端自带的那个头剥掉。一百个后端于是信任这个头、永远不再校验——它们待在网关守着的内网里。

代价是 CPU。验一个 RSA-2048 签名大约要几十微秒;在每秒两万请求的量级上,这就是实打实花在入口密码学上的核时。诱人的「优化」是按令牌缓存校验结果、或者对「内部」路径跳过校验——两者都会重新捅开安全的口子。缓存解出来的令牌,意味着一个**已吊销或已过期**的令牌会一直好用到缓存条目老化;信任内部路径,意味着任何能够到网关内网的人都能伪造身份头。老实的答案是每个请求都验,并把网关横向扩容(它是无状态的,扩容很容易);当校验开销真的咬人时,优先选 **EdDSA / ES256** 而不是 RSA——椭圆曲线的校验明显更便宜。

## 令牌桶:限速和突发一把抓

入口的第二件事是限流,而胜出的算法是**令牌桶**。想象一个桶,最多装 `burstCapacity` 个令牌,以每秒 `replenishRate` 个的速度回填。每个请求都要拿走一个令牌;桶空了,请求就被拒。两个数字给了你两个相互独立的旋钮:

- **replenishRate** 定住持续的平均速率——你允许的长期每秒请求数。
- **burstCapacity** 定住你能容忍多大的瞬时突发——一个满桶可以在回填速率接手之前一次性花光。

@fig sc11-bucket

| 配置 | replenishRate | burstCapacity | 行为 |
|------|--------------:|--------------:|------|
| 严格 | 100 | 100 | 稳定 100/s,毫无余量 |
| 容突发 | 100 | 500 | 平均 100/s,能吸收一次 500 的尖峰 |
| 配错 | 100 | 100000 | 真突发来了也永远触发不了的「限流」 |

这正是治理台演示的**削峰**。往网关灌一个十倍于持续速率的突发,看三条线怎么动:通过的请求跟着回填速率加上一次性的排空桶走,被限的请求是溢出的部分,而后端负载稳稳停在它被规划的那个速率上。那个本会拍平数据库的十倍尖峰,变成了一条扛得住的稳定流加上一堆拒绝——数据库根本没见到那个尖峰。

## Redis 限流器与 KeyResolver

因为网关是多实例跑的,桶必须**共享**——否则五个网关各放行 100/s,真实上限就成了 500/s。Spring Cloud Gateway 的 `RequestRateLimiter` 过滤器把桶放在 Redis 里,所有实例从同一个桶取令牌。`KeyResolver` 决定**限的是什么**——按用户、按 IP、还是全局:

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: orders
          uri: lb://ORDER-SERVICE
          predicates:
            - Path=/api/orders/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
                key-resolver: "#{@userKeyResolver}"
```

```java
@Bean
KeyResolver userKeyResolver() {
    return exchange -> Mono.justOrEmpty(
            exchange.getRequest().getHeaders().getFirst("X-User-Id"))
        .defaultIfEmpty("anonymous");
}
```

按用户限(上面这个 resolver)能摁住一个滥用的客户端而不波及其他人;按 IP 限更粗,但能在鉴权之前就生效;一个全局 key 则不管谁来调都护住一个脆弱的后端。

## 429,而不是排队

桶空了,网关立刻返回 **HTTP 429 Too Many Requests**——它不会把请求攥在手里等令牌。这是最关键的一个设计取舍。把溢出的请求排队看着更温柔,其实是个陷阱:攥着的请求占着内存和连接,所有人的延迟一起往上爬,而客户端——本来就在超时——会重试,再添一层负载。这就是**慢性死亡**:系统对所有调用方一起劣化,还要几分钟才缓得过来。一个快速的 429 则是调用方能据此行动的**背压**——退避、带抖动稍后重试、或者干脆丢掉这次工作。把你服务不了的那 1000 个请求拒掉,才能让你服务得了的那 100 个保持快。429 应当带上 `Retry-After` 头,让守规矩的客户端知道什么时候再来。

## 练习

1. 在治理台上设 replenishRate=50、burstCapacity=50,在一秒内灌入 500 个请求,记录通过与被限的分布;再把 burstCapacity 提到 250,解释这次多放行了哪些之前进不来的请求。
2. 写一个按客户端 IP(而不是 `X-User-Id`)限流的 KeyResolver,并举出一个「按 IP 限」会误伤的场景(提示:很多用户在同一个 NAT 后面)。
3. 让 RequestRateLimiter 在返回 429 时带上 `Retry-After` 头,并描述一个守规矩的客户端拿到它之后该怎么做。
4. 估算每秒校验两万个 RSA-2048 签名、每个约 30 微秒的 CPU 开销,并按 50% 余量决定你要给网关配几个核。
