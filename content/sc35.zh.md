## 大屏要的是「推」,不是「拉」

上一章,Python 时序服务把异常事件发到了 Kafka。但一条事件躺在 topic 里没人看,不叫监控。监控的最后一米,是它要**实时出现在运维盯着的那块大屏上**——设备一异常,屏上立刻跳出一条红色告警,而不是等谁去刷新。

问题具体化:一块网页大屏(浏览器),怎么实时拿到服务器这一侧不断产生的异常事件?这里有个方向性的坎:HTTP 天生是「客户端问、服务器答」,是**拉**;而大屏要的是服务器主动**推**。

新手的第一反应,是让大屏每隔几秒 `setInterval` 轮询一次告警接口。它能跑,但它是在用拉去模拟推,于是卡在一个两头不讨好的取舍里:轮询太勤——比如每秒一次——一千块大屏就是每秒一千个请求砸向服务器,而在异常并不密集的时候,这些请求绝大多数拿回来的是「没有新告警」的空响应,纯粹浪费;轮询太疏——比如每 10 秒一次——告警平均要等 5 秒才上屏,对一个要人命的功率异常,这 5 秒可能就是事故。治理台让你把这笔账看清楚:一千块屏、5 秒间隔,服务器就得扛 200 req/s 的轮询,而其中绝大多数是空的。

轮询不是不能用——屏很少、实时性要求松的时候它最省事,而且它无状态、没有后面要讲的扇出问题。但对一块要实时告警的监控大屏,正确答案是让服务器**推**。

## 三种传输:轮询 / SSE / WebSocket——大屏选 SSE

浏览器和服务器之间做实时推送,主流就三种,按「谁能主动发」来分:

**轮询(polling)**——上一节讲过。客户端反复拉,服务器被动答。简单、无状态,但浪费且有延迟。

**SSE(Server-Sent Events)**——服务器→浏览器的**单向**流。浏览器用一行 `new EventSource(url)` 打开一条长连接,之后服务器想推就推,一条条事件顺着这条连接流下来。它的几个特质,对大屏简直是量身定做:它就是**普通 HTTP**(`Content-Type: text/event-stream`),所以能直接穿过 Spring Cloud Gateway、能复用现有的鉴权和 TLS,不需要额外协议;它**自带断线重连**——连接掉了浏览器自己会重连,还会带上 `Last-Event-ID` 让服务器从断点续传;它天然是单向的,而大屏这个场景,数据流本来就是单向的(服务器推告警,大屏只管显示)。

**WebSocket**——**全双工**,浏览器和服务器可以互相主动发。它比 SSE 强,但也重:它是独立协议(`ws://`),握手、心跳、重连都要你自己张罗(浏览器不像 SSE 那样自动重连)。你只有在大屏**还要往回发东西**时才需要它——比如运维要在屏上点一下「静音这个设备」「只看 A 车间」,这些指令要从浏览器发回服务器。如果大屏只是单纯地显示推来的告警,上 WebSocket 就是杀鸡用牛刀。

一句话选型:**只往大屏推 → SSE;大屏还要往回发指令 → WebSocket;都不想折腾且能接受延迟 → 轮询。** 对「监控大屏消费异常事件」这个题,答案默认是 SSE。

## 扩容的陷阱:共享消费组让大屏漏报

选对了传输,你以为就完了——直到你为了扛更多大屏,把推送服务从 1 个实例扩到 3 个。然后告警开始**随机丢失**,而且你在开发环境怎么都复现不出来。

这是整章最值得记住的一个坑。回想机制:推送服务要从 Kafka 消费异常事件,再推给连在自己身上的大屏。当你只有 1 个实例时,它消费到全部异常、推给全部大屏,一切正常。可当你扩到 3 个实例、而它们**用的是同一个 Kafka 消费组**时——消费组的语义是「组内每条消息只被一个消费者拿到」(这正是 sc13 讲的,消费组用来分摊负载)。于是每条异常只会被 3 个实例中的**一个**消费到。而大屏是通过网关负载均衡、随机连到某一个实例上的。结果:一条异常被实例 1 消费到了,可你这块大屏连在实例 2 上——它永远收不到这条告警。**送达率直接掉到 1/M。**

@fig sc35-dashboard

开发时 M=1,一切完美,你信心满满地上线;一扩容,告警就开始「莫名其妙地漏」——而且是随机漏(取决于哪条事件落到哪个实例、哪块屏连在哪个实例),最难查。治理台把这个塌陷画出来:切到「SSE·共享消费组」,把实例数从 1 拉到 3,看着送达率从 100% 掉到 33%、每条告警实际送达的大屏数被砍成三分之一。

根子在于:**消费组是用来「分摊」的,而大屏推送要的是「广播」——每个实例都得拿到每一条事件。** 两种修法:

- **每实例独立消费组**:让每个推送实例用一个唯一的消费组(比如把实例 ID 拼进 group 名)。这样每条异常会被每个组各消费一份,即每个实例都收到全量,再各自扇出给自己的连接。简单,代价是 Kafka 那边多了 M 份消费。
- **Redis 广播 / Pub-Sub**:只用一个消费者从 Kafka 收异常,再经 Redis Pub/Sub 把每条事件广播给全部实例,由各实例推给自己的大屏。多一跳 Redis,但扇出这件事被干净地收拢到一层,实例数再多也不怕。

治理台里「SSE·广播」这一档,就是修好之后的样子:不管大屏连在哪个实例上,送达率都是 100%。

## 断线重连与快照:大屏不能一刷新就白屏

最后一块,是让大屏「活得住」。两个现实问题:

**断线重连。** 大屏是挂在墙上一年 365 天不关的,网络一定会抖、连接一定会掉。好消息是 SSE 自带重连——连接断了浏览器会自动重连,不用你写心跳。但你要在服务端配合:给每条事件带一个 `id`,浏览器重连时会把最后收到的 id 放进 `Last-Event-ID` 请求头发回来,服务端据此从断点接着推,断线那几秒的告警就不会丢(WebSocket 没有这个内置机制,得自己实现)。

**首屏快照。** 想象运维刷新了一下大屏,或者新开了一块屏。如果你只推「增量」——从这一刻起新产生的告警——那这块屏一开始是**空白的**:此刻正红着的那几十条告警,它一条都不显示,要等下一条新告警来了才开始有内容。这对监控大屏是不可接受的。正解是:大屏一连上,服务端先推一份**当前所有未处理告警的快照**(首屏立刻画满),紧接着再无缝切到增量流。代码上就是把 SSE 的流拼成「快照 ++ 实时流」两段(见代码面板的 `Flux.concat(snapshot, live)`)。

一句话收尾:**大屏要实时告警,就让服务器用 SSE 推;扩容时用广播或独立消费组保证每块屏都收到;再配上断线重连和首屏快照,这块屏才既不漏报、也不白屏。** 到这里,从 Python 把数据变成异常信号(sc34),到异常信号实时落到运维眼前的那块屏(sc35),这条链才算真正闭环。

## 练习

1. 在治理台上选「SSE·共享消费组」,实例数设 1,确认送达率 100%;再把实例数拉到 4,看送达率掉到多少、每条告警送达几块屏。这解释了「开发好好的,上线就漏告警」。
2. 对比「轮询」和「SSE·广播」在 2000 块大屏下的「服务器空转请求」;想想为什么轮询的这个数会随大屏数线性上涨,而 SSE 不会。
3. 你的大屏需要让运维点「静音某设备」把指令发回服务器。这时你还能只用 SSE 吗?说明你会怎么组合(提示:SSE 下行 + 一个普通 POST 上行,vs 直接上 WebSocket)。
4. 设计首屏快照 + 增量流的衔接:如果在「查快照」和「订上增量流」这两步之间,恰好来了一条新告警,你怎么保证它既不漏、也不重复显示?
