## Logs that outlive the container

Metrics say something is wrong. Tracing says which service. But when you need to know what actually happened inside that service — the exact exception, the parameter that was null, the branch that was taken — you are back to reading logs. Microservices break log reading in two ways at once, and both come from one root: the process is no longer pinned to a machine you can log into.

A container is ephemeral. It is scheduled onto some node, it runs, and when it is redeployed, crashes, or is rescheduled by Kubernetes, it is destroyed and its local filesystem — including `/var/log` — goes with it. The log line that explains last night's incident may live in a container that stopped existing at 03:00. So microservice logging has to do two things a monolith never needed: **centralise** and **correlate**.

### Centralise: ship logs off the box

Centralising means a shipper on each node (Fluent Bit, Filebeat, Promtail) tails the containers' stdout and forwards every line to a store, so you search the whole fleet in one place instead of SSHing into machines that may already be gone. Two stacks dominate, and they make opposite bets:

| | ELK (Elasticsearch) | Loki |
|---|---|---|
| Indexes | every field, full text | labels only (service, level, pod) |
| Storage cost | high — the inverted index is large | low — compressed chunks in object storage |
| Query | KQL/Lucene, fast arbitrary search | LogQL, grep over label-selected streams |
| Fits | rich ad-hoc search, audit, security | high-volume app logs, cost-sensitive, already on Grafana |

Elasticsearch indexes everything, so any search is fast and all storage is expensive. Loki indexes only a handful of labels and greps the rest, so it is dramatically cheaper to run and slower on unindexed searches. For chatty application logs, Loki's bet usually wins.

### Correlate: the traceId is the join key

Centralising alone gives you one giant haystack. The magic is **correlation**, and the key is the same traceId from the tracing chapter. Stamp every log line with the traceId of the request it belongs to, and a slow trace you found in Zipkin becomes a single query — `{traceId="4bf92..."}` — that pulls every line that request wrote in every service, orders them by time, and hands you the whole story as one timeline. Two things put the traceId on every line for free. Micrometer Tracing writes `traceId` and `spanId` into SLF4J's **MDC** (mapped diagnostic context), and a JSON encoder copies the MDC into each log event. Structured logging — JSON, not plain text — is the second half: a machine can filter `level=ERROR AND service=payment` across a billion lines in milliseconds, which it cannot do reliably against free-form text.

```xml
<configuration>
  <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
      <includeMdcKeyName>traceId</includeMdcKeyName>
      <includeMdcKeyName>spanId</includeMdcKeyName>
    </encoder>
  </appender>
  <root level="INFO">
    <appender-ref ref="JSON"/>
  </root>
</configuration>
```

(Spring Boot 3.4+ can do this natively with `logging.structured.format.console=logstash`, no encoder dependency needed.)

### Sampling and retention: logs cost money

Logs are the most voluminous of the three signals — a busy fleet writes hundreds of gigabytes to a terabyte a day, and Elasticsearch storage for that is a line item you will be asked to defend. So you make two cuts. **Retention** tiers by age: 7 days hot and searchable, then 30–90 days cheap and cold in object storage, then delete. **Sampling** tiers by importance: keep 100% of WARN and ERROR, but sample INFO/DEBUG — or better, keep all logs for traces that were sampled or errored, and drop the rest. The trade is sharp and the failure mode is specific: sample too aggressively and the one request you need to reconstruct at 3 a.m. is exactly the one you threw away. Keep everything and the bill, not the outage, becomes the incident.

## Exercises

1. Add `logstash-logback-encoder` and the `logback-spring.xml` above to a service; confirm each log line is now JSON carrying `traceId`/`spanId` fields. Fire one traced request and copy its traceId out of Zipkin.
2. Stand up Loki + Promtail + Grafana (or ELK) with Docker Compose, ship two services' logs into it, and run a query filtered by the traceId from task 1 — verify you see lines from both services on one timeline.
3. Kill and redeploy a container mid-request (`docker rm -f` or `kubectl delete pod`); confirm its local logs vanished but the centralised store still has them.
4. Estimate your fleet's daily log volume (lines/s × bytes/line × services × 86,400), then design a retention-plus-sampling policy that cuts storage 5–10× while still keeping every ERROR and every sampled trace.
