## Moving cross-cutting concerns out of code

Everything you have built so far assumes governance lives in the application. Resilience4j retries and breaks; Spring Cloud LoadBalancer picks an instance; Micrometer emits traces; your code validates the JWT. This works beautifully — as long as every service is a Spring Boot app that pulls in the same libraries and upgrades them together. It stops working the moment a Go service, a Node service, or a Python model server joins the system: none of them speak Resilience4j, and now your retry policy, your mTLS and your tracing are inconsistent across the fleet.

A **service mesh** removes that assumption. Beside every service's pod it injects a **sidecar** — a small proxy, almost always Envoy — and reconfigures the pod so that all traffic in and out of the service goes through its sidecar first. The application talks to localhost; the sidecar does the real network work. And because the sidecar sits in the path of every request, it can do all the cross-cutting things the request needs — mutual TLS, retries, timeouts, circuit breaking, load balancing, canary splitting, telemetry — without the application knowing or caring, and identically for a Go service as for a Java one.

## Data plane and control plane

A mesh has two halves. The **data plane** is the swarm of sidecar proxies — one per pod — that actually carry and govern the traffic. The **control plane** (Istiod in Istio, the controller in Linkerd) is the brain: it watches the cluster and pushes configuration and certificates down to every sidecar. You do not configure proxies individually; you write a policy once — "split order traffic 90/10", "require mTLS in this namespace", "retry inventory 3 times" — and the control plane distributes it to the relevant sidecars. That control-plane / data-plane split is what lets one set of rules govern thousands of proxies.

Crucially, the mesh's policies are Kubernetes resources — a `VirtualService` for routing and retries, a `DestinationRule` for load balancing and outlier detection (its circuit breaker), a `PeerAuthentication` for mTLS. The platform team owns them; the application team no longer writes that code.

## Mesh vs Spring Cloud: who owns what

Here is the uncomfortable part: the mesh does much of what Spring Cloud already does. Both can retry. Both can break a circuit. Both can do mTLS, load balancing and tracing. The two overlap heavily, and that overlap is a trap.

| Concern | Spring Cloud (in-process) | Service mesh (sidecar) |
|---|---|---|
| mTLS | manual TLS/JWT per service | automatic, zero code |
| Retry / timeout | Resilience4j `@Retry` | VirtualService retries |
| Circuit breaking | `@CircuitBreaker` | outlierDetection |
| Load balancing | Spring Cloud LoadBalancer | Envoy |
| Canary / split | gateway weight (edge only) | service-to-service weight |
| Tracing | Micrometer instrumentation | Envoy auto-generated spans |

The rule is: **pick exactly one owner per concern.** If both your `@Retry` and the mesh retry, the attempts multiply — three app retries times three mesh retries is nine calls, a retry storm you built by accident. If both do mTLS you pay twice for nothing. So when you adopt a mesh, you delete the corresponding Spring Cloud config and keep in code only what the mesh cannot know: business-specific fallback logic (what to return when inventory is down is a product decision, not a network one). Use the bench above to assign each concern and watch the trade.

## The cost

A mesh is not free, and its costs are exactly why not every team should run one. First, a **latency tax**: every hop now traverses two extra proxies (out of the caller's sidecar, into the callee's), adding a fraction of a millisecond each — small per hop, but multiplied across a deep call chain and every request. Second, **resources**: a sidecar per pod means hundreds of Envoy processes, each with its own CPU and often ~100 MB of memory — a real line item at fleet scale. Third, **operational complexity**: you now run and upgrade a control plane and a data plane, debug traffic that no longer goes where the app thinks it does, and add a layer that can fail.

For a small, all-JVM system, Spring Cloud in-process may be simpler and cheaper. The mesh earns its keep when you are polyglot, large, or need uniform security and traffic policy you cannot trust every team to implement identically in code.

## Exercises

1. Install Istio on a kind/minikube cluster, label a namespace `istio-injection=enabled`, deploy a service, and confirm `kubectl get pod` shows `2/2` (app + sidecar).
2. Move retries and timeouts from a Resilience4j config into a VirtualService; then remove the `@Retry` annotations and verify behaviour is unchanged — and that you are no longer double-retrying.
3. Turn on strict mTLS with a PeerAuthentication; capture traffic between two pods and confirm it is now encrypted, with no code change.
4. Do a service-to-service canary — split traffic 90/10 between two versions with a VirtualService — and compare it with the edge canary you did at the gateway (Module IV).
