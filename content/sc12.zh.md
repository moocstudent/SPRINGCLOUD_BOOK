## 住在 jar 包外面的配置

几十个服务,每个又分开发 / 测试 / 生产,就是几百份配置文件。如果一个数据库密码、一个限流阈值、一个功能开关还写在各自的 `application.yml` 里,那么改一个就意味着改文件、重新打包、重新部署——为了一行改动付出几分钟的工作量和一次完整发布的风险。**配置中心**把这些拽出来:服务在启动时从一个集中的源头拉取配置,而不是把它烤进 jar 包。

主流实现有两个。**Spring Cloud Config** 用 **Git** 做存储——每次改动都是一次提交,于是历史、diff、blame、回滚全都白送,还能走 pull request 评审。**Nacos Config** 把配置存在自己的服务里,带 Web 界面,通过长轮询把变更推下去。Git 后端可审计、对 gitops 友好;Nacos 改起来更快、和 Nacos 发现天然打通。客户端在应用上下文构建之前,通过导入指向其中之一:

```yaml
spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://config:8888"
  cloud:
    config:
      profile: prod
      label: main          # Git 分支/标签
```

服务端把 `order-service` + `prod` + `main` 解析到某个提交上的某个具体文件——**label** 正是你能把所有实例钉在同一个 Git 标签上、并确切知道它们加载了什么的原因。

## 不重启就刷新

启动时拉配置只是一半价值。另一半是**动态刷新**:改一个值,正在运行的实例不重启就能拿到新值。Spring 用 **`@RefreshScope`** 实现它。标了这个注解的 Bean 会在一次刷新事件之后、下次被用到时被重建,于是读到新值:

```java
@RefreshScope
@Component
@ConfigurationProperties(prefix = "orders")
public class OrderProps {
    private int maxPerSecond = 100;   // 刷新后重新绑定
    // getters / setters
}
```

一个实例,在你 POST 它的 Actuator 端点 `/actuator/refresh` 时刷新。但你有三十个实例,一个个去敲三十个端点荒唐至极。**Spring Cloud Bus** 解决这个:它用一个消息中间件(RabbitMQ 或 Kafka)把所有实例连起来,于是对任意一个实例的 `/actuator/busrefresh` 发一次 POST,就会把刷新事件**广播**给全部。用 Nacos 的话,保存时自动推送。无论哪种,顺序都是:改源头、广播、每个 `@RefreshScope` Bean 重建、新值生效——没有进程重启,没有连接断开。

## 危险窗口:刷新不是原子的

这就是本章存在、要提醒你的那块暗礁。一次广播刷新在**多个实例之间不是原子的**。事件经消息中间件到达三十个实例,每个各自重建 Bean,这一切都要时间——端到端通常是几百毫秒到几秒。在这个窗口里,**一部分实例已经在用新配置,一部分还在用旧配置。**

对一个独立的值——一个日志级别、一个缓存 TTL——几秒的混合状态无伤大雅。危险出现在**两方必须一致**的时候。假设你抬高了一个消息格式的版本号,或者翻动了一个改变生产者与消费者之间契约的功能开关。在那几秒里,一个 v2 生产者发出的消息可能到达一个解析不了它的 v1 消费者。症状令人抓狂:一阵错误恰好在配置推送的那一刻开始,几秒后又自己消失,日志里什么可复现的东西都没留下。

治理台把这个窗口画了出来。把一次配置改动推给一组实例,看实例一台台翻新——一条绿色进度条追着改动跑,还有一个计数器数着有多少请求掉进了混合状态的缝里。把机群加大、或把中间件放慢,窗口就变长。

| 窗口的贡献者 | 典型影响 |
|-------------|---------|
| 中间件传播延迟 | 几十到几百毫秒 |
| Bean 重建 + 重连 | 毫秒级;若连接池重新初始化则到秒级 |
| 机群规模 | 实例越多,尾巴越长 |
| 某个慢 / 停顿的实例(GC) | 可能整个错过事件 |

## 灰度、版本化、回滚

你没法让刷新变原子,那就绕着它设计。给每次配置改动**版本化**(一次 Git 提交,或一个 `version` 字段),让生产者和消费者去协商而不是假设。让改动在一个发布周期内**向后兼容**——消费者先能读懂新旧两种,生产者再开始发新的——这样混合状态从构造上就是安全的。像给代码做金丝雀一样给配置做**灰度**:先推一个实例或一个命名空间,观察,再铺开。并且把**回滚**留在一步之遥:Git 后端就 revert 那次提交再广播一次——回来的路上一样有这个窗口,所以要回滚到一个你确知两边都能容忍的版本。

## 练习

1. 在治理台上把一次配置改动推给 30 个实例,记录混合状态窗口的长度;再把机群加到 100、把中间件调慢,描述窗口怎么变。
2. 给一个 Bean 标上 `@RefreshScope`,暴露 `/actuator/busrefresh`,用文字追一遍从你发 POST 到值在一个对等实例上生效的完整事件序列。
3. 设计一个「两次发布」的方案,把消息格式从 v1 改到 v2,使得任何混合状态窗口都不可能产生一条解析不了的消息(提示:先教会消费者读懂两种)。
4. 给定一个 Git 后端的配置中心,写出回滚一次坏改动的确切步骤,并解释为什么回滚和当初的推送有着同一个危险窗口。
