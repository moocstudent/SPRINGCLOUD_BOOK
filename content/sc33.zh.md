## 团队不只有 Java:那个 Python 服务怎么接

这本书到这里为止,默认每个服务都是一个 Spring Boot 应用:加一个 `@EnableDiscoveryClient`,它就自己注册进 Nacos、自己发心跳、自己被 `lb://` 找到。可现实里,总有一个服务不是 Java 写的——一个模型推理、一段数据清洗、一个部门三年前用 Flask 写好、谁也不敢动的脚本。它得和这套系统协作,而它对 Spring Cloud 一无所知:不会注册、不发心跳、别的服务不知道去哪找它。

先把问题拆清楚。一个服务要真正「进入」Spring Cloud,靠的是两条独立的通道,别把它们混成一件事:

- **入口通道**——外部请求怎么打到它。这是**网关**的活,和语言无关。
- **发现通道**——系统内部怎么知道它在哪、还活着没有、有几个实例。这是**注册中心**的活,而它默认假设你是个会发心跳的 JVM 应用。

一个 Python 服务可以只接第一条、不接第二条,也可以两条都接。搞清楚你到底需要哪条,是这一章所有决定的起点。

## 边缘代理:一条静态路由就能白嫖网关

先说入口。当你把网关用作**边缘代理**(edge proxy)——让所有外部流量只从网关这一个口进来、后端服务全藏在内网——你其实已经有了接 Python 的最省事办法:一条**静态路由**。

```
- id: python-static
  uri: http://python-host:8000      # 写死一个地址
  predicates: [ Path=/py/** ]
```

就这么点。网关是个反向代理加一条过滤器链,它在 HTTP 层根本不关心后端是 Java 还是 Python。请求打到 `/py/**`,它转给那个地址,拿回响应。Python 不用注册、不改一行代码。

而且——这是很多人没意识到的白赚——挂在网关后面的那一刻,Python 就**继承了网关的全部横切能力**。你在网关上配的 JWT 校验、令牌桶限流、CORS、访问日志、灰度权重,对 `/py/**` 这条路由**一样生效**。你没为 Python 写任何鉴权代码,它却已经被鉴权保护;你没在 Python 里写限流,它却已经被限流。对「我只想让这个 Python 服务有个统一入口、顺便被鉴权和限流管起来」的需求,静态路由到此就够了,别再往下做。

代价也要说清楚,别以为白赚没成本。静态路由里那个 `uri` 是**一个写死的地址**:网关不知道你其实起了三个 Python 实例,负载全压在这一个上;这个地址一挂,网关照样往它转,整条路由 502,直到有人发现、手工改配置或重启。网关对它**没有负载均衡、没有健康感知**。而且它进不了服务发现,别的微服务没法用 `lb://python-service` 按名字调它,它也纳不进统一的熔断和链路追踪。这些,正是第二条通道要解决的。

## 要不要注册:Sidecar 让 Python 进 Nacos

如果你要的不只是「有个入口」,而是让 Python 变成系统里一个正经的、可被发现、能负载均衡、死了会被自动摘掉、别人能按名字调的服务——那它就得进注册中心。

问题回到原点:Python 不是 JVM,它不会自己注册、自己发心跳。有两条路让它进 Nacos:

- **Python 自己注册(直连 SDK)**:用 `nacos-sdk-python` 这类客户端,在 Python 里加几行——启动时调 `add_naming_instance` 注册自己,再起个后台任务每几秒 `send_heartbeat` 续租。干净、直接,代价是**侵入 Python 代码**,而且团队得自己维护这套心跳逻辑。

- **Sidecar(边车)模式**:一个**轻量的 Spring Boot 小进程**贴着 Python 一起跑(`spring-cloud-alibaba-sidecar`)。它替 Python 注册进 Nacos、替 Python 发心跳、并周期性地去访问 Python 的 `/actuator/health`——Python 健康,它就报活;Python 挂了健康检查失败,它就让 Nacos 把这个实例摘掉。关键是:**Python 一行都不用改**,它甚至不知道 Sidecar 存在。这就是「多语言服务接入 Spring Cloud」的标准答案。

@fig sc33-sidecar

两条路进了 Nacos 之后,效果是一样的,而这个效果正是静态路由给不了的。网关的路由从 `uri: http://python-host:8000` 换成 `uri: lb://python-service`,`lb://` 意味着「从注册表里当前存活的实例里挑一个」。现在你起 N 个 Python 实例,流量就均摊到 N 个;其中一个宕机,Nacos 在**一个检测窗口**(心跳间隔 × 判死心跳数,比如 5s × 3 = 15s)内把它摘掉,只有这段窗口里打到那台的请求会失败(配上网关重试还能救回大半),之后流量自动重分到其余实例。别的 Java 服务也能用 `lb://python-service` 按名字调它,它也进了统一的熔断、追踪与配置体系。

治理台把这三种接入方式摆在一起,让你亲手对比:同样起 N 个实例、其中一个宕机,静态路由丢多少请求、要等人工多久;注册进 Nacos 后又是多快自愈。你会看到那个差距不是一点半点——静态路由的损失是「速率 × 人工响应的几百秒」,注册后的损失是「单实例份额 × 十几秒的检测窗口」。

那到底该选哪条?**只要一个统一入口 + 网关的鉴权限流**——静态路由,别过度设计。**要 Python 融进整个服务治理**(负载均衡、发现、熔断、被别人按名字调)——注册进 Nacos,能改 Python 就用直连 SDK,不能改就用 Sidecar。

## 守约定:追踪头、JWT、配置

接进来只是第一步。要拿到本书前面那套完整治理,Python 还得**守和 Java 服务同样的约定**——网关能把请求转给它,不等于它就自动融进了追踪、鉴权和配置。有三件事必须两边对齐。

**链路追踪**。M6 讲过,一条请求跨八个服务时,靠的是一个贯穿全链路的 traceId,每一跳都把它往下传。如果 Python 这一跳收到请求却不读、不传这个头,链路追踪就在 Python 这里**断了**——瀑布图上它成了一个黑洞,你再也看不清那 800 毫秒花在哪。约定就是那个 W3C 的 `traceparent` 头:Python 收到时读出来,发起下游调用时带上。最省心的办法是两边统一用 **OpenTelemetry**——它是跨语言的,Java 侧新版 Spring 的 Micrometer Tracing 底层就是它,Python 侧也有成熟的 OTel SDK,自动帮你接收和透传。

**鉴权**。网关在边缘把 JWT 校验过一次,再把请求转给后端。Python 这边有两种姿态:要么**信任网关**——认定内网流量都已过网关这道关(得配合网络隔离,别让人绕过网关直连 Python);要么**自己复验一遍**——拿网关用的公钥,在 Python 里再校验一次 JWT 的签名和过期。零信任要后者,图省事用前者,取决于你的威胁模型。但无论哪种,**别让 Python 自己发明一套鉴权**,那就和「统一入口」的初衷背道而驰了。

**配置**。Java 服务从 Nacos 配置中心热加载配置,Python 默认不会。要么用 `nacos-sdk-python` 的配置客户端去拉(它也支持监听变更),要么退一步、用环境变量把配置塞给 Python 容器。后者简单,代价是改配置要重启——这对一个大多数时候不怎么改配置的 Python 服务,通常可以接受。

一句话收尾:**网关让 Python 有了入口,注册中心让它被发现,而这些约定才让它真正成为系统的一员**,而不只是一个挂在边上、能被访问但看不见、管不着的外挂。
