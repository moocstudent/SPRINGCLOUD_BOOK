## 两种报文

CM1 里你用 OpenFeign 让 OrderService 调 InventoryService,消息本质上是走 HTTP、用 JSON 传输的——微服务的默认选择。这是个好默认:JSON 人可读、任何语言和工具都认、用 curl 或浏览器就能看、上面还能叠 HTTP 缓存。但 JSON 也很啰嗦:每条消息都把字段名当文本重复一遍,给值加引号,还要为花括号和逗号花掉字节。

gRPC 做了另一种取舍。它用 **Protobuf**(一种由 `.proto` 模式定义的二进制格式)序列化消息。在线上,Protobuf 发的是一个很小的字段**编号**加一个变长的值,而不是字段名——所以同一个对象,JSON 要约 280 字节,Protobuf 常常只要约 60–70 字节,大概是四分之一。上面的治理台会按你选的消息大小现算这个比值;这个比例很稳,而且它最要紧的地方,恰恰是最容易被忽略的地方:服务之间频繁的内部调用——那里,带宽和解析文本花掉的 CPU 会迅速累积。

## 两种传输

报文只是故事的一半,传输是另一半。REST 通常走 **HTTP/1.1**,一条连接一次只能承载一个请求——并发调用要么开多条连接,要么互相排队(队头阻塞)。gRPC 强制用 **HTTP/2**,它在一条长连接上用二进制帧多路复用许多并发流,于是上百个在途调用共享一条连接、互不阻塞。对一个每秒发出成千上万次调用的服务,这个差别就是更低的延迟和少得多的 socket。(REST 也能跑在 HTTP/2 上,但很少用到 gRPC 为之而生的流式和帧的好处。)

## 契约与流式

gRPC 的第三个优势是**契约**。`.proto` 文件是唯一真相来源,`protoc` 从它给你需要的每种语言生成强类型的客户端和服务端桩。你改了字段名、换了类型,坏的是编译,而不是生产环境。REST 的契约更松——OpenAPI 描述它,但没有什么强制客户端和服务端一致,漂移要到运行时才发现,甚至根本发现不了。

gRPC 还原生带**流式**,共四种形态:

| 模式 | 形态 |
|---|---|
| 一元 Unary | 一次请求,一次响应(像 REST) |
| 服务端流 | 一次请求,一串响应 |
| 客户端流 | 一串请求,一次响应 |
| 双向流 | 两边在一条连接上同时流 |

REST 只有请求-响应;要流式就得请出 Server-Sent Events 或 WebSocket,是外挂上去的,而非原生。

## 对内选 gRPC,对外选 REST

这些都不能让 gRPC 成为普适赢家——它的优势各自都有实打实的代价:

| | gRPC | REST |
|---|---|---|
| 报文 | Protobuf 二进制,紧凑 | JSON 文本,冗长 |
| 传输 | HTTP/2,多路复用 | HTTP/1.1 常见 |
| 契约 | `.proto`,强类型代码生成 | OpenAPI,松散 |
| 流式 | 原生,四种模式 | 请求-响应(SSE/WS) |
| 浏览器 | 需 grpc-web 代理 | 任何客户端直连 |
| 调试 | 二进制,需工具 | curl 可读 |
| 缓存 | 无 | HTTP 缓存 |

健康的经验法则是按受众分层。在你自己的服务之间——内部、高频、强契约、偶尔要流式——gRPC 物有所值。在系统边缘,面向浏览器、第三方和公网,这里可读性、通用性和缓存比省几个字节更重要——REST 才是对的工具。很多真实系统两者都用:网格内部跑 gRPC,再由一个 API 网关把外部的 REST 调用翻译成内部的 gRPC。因为那道边界正是网关(模块 IV),你可以按层各选各的,而不必给整个系统强加一种协议。

## 练习

1. 为订单定义一个 `.proto`,生成桩,把服务用两种方式各调一遍——一次用 gRPC 客户端,一次用等价的 REST。用 Wireshark 抓下两次请求,对比线上的字节数。
2. 拿同一条消息,分别用 JSON 和 Protobuf 序列化,量出大小差,再乘以你真实的调用频率,看看每天的带宽差距有多大。
3. 用 gRPC 实现一个服务端流的 RPC(比如订单状态更新);再用 REST + Server-Sent Events 实现同样的功能,记下各自的代价。
4. 把你的 gRPC 服务放到一个对外暴露 REST 的 API 网关后面;确认浏览器能调 REST 边缘,而服务之间调的是 gRPC 内核。
