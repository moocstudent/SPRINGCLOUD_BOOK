## 比容器活得更久的日志

指标说「有问题」。追踪说「问题在哪个服务」。但当你要弄清那个服务内部到底发生了什么——具体是哪个异常、哪个参数是 null、走了哪个分支——你还是得回到读日志。微服务同时从两个方向破坏了「读日志」这件事,而两者都来自同一个根:进程不再被钉在一台你能登录进去的机器上。

容器是易逝的。它被调度到某个节点上、跑起来,而当它被重新发布、崩溃、或被 Kubernetes 重新调度时,它就被销毁,它的本地文件系统——包括 `/var/log`——也随之消失。那行能解释昨晚故障的日志,可能就住在一个凌晨三点已经不复存在的容器里。所以微服务的日志必须做两件单体从不需要做的事:**集中**和**关联**。

### 集中:把日志运下机器

集中,是指每个节点上有一个采集器(Fluent Bit、Filebeat、Promtail)追着容器的标准输出,把每一行转发到一个存储里,于是你在一个地方搜索整个集群,而不必 SSH 到那些可能已经不在了的机器上。两套技术栈占主流,而它们下的是相反的注:

| | ELK(Elasticsearch) | Loki |
|---|---|---|
| 索引什么 | 每个字段、全文 | 只索引标签(服务、级别、pod) |
| 存储成本 | 高——倒排索引很大 | 低——压缩块存在对象存储里 |
| 查询 | KQL/Lucene,任意搜索都快 | LogQL,在按标签选出的流上做 grep |
| 适合 | 丰富的临时搜索、审计、安全 | 高吞吐应用日志、对成本敏感、已经在用 Grafana |

Elasticsearch 索引一切,于是任何搜索都快,任何存储都贵。Loki 只索引少数几个标签、其余靠 grep,于是它运行起来便宜得多,在未索引的搜索上更慢。对于聒噪的应用日志,Loki 这一注通常赢。

### 关联:traceId 就是连接键

光集中,给你的是一个巨大的干草垛。真正的魔法是**关联**,而那把钥匙就是追踪那一章里同一个 traceId。给每一行日志都打上它所属请求的 traceId,那么你在 Zipkin 里发现的一条慢 trace,就变成了一次查询——`{traceId="4bf92..."}`——它把这次请求在每个服务里写下的每一行都捞出来,按时间排好,把整个故事作为一条时间线交到你手上。治理台做的正是这件事:按一个 traceId 过滤一条多服务日志流,看那些散落的碎片啪地拼成一段有序的叙事。

有两件事让 traceId 免费地出现在每一行上。Micrometer Tracing 把 `traceId` 和 `spanId` 写进 SLF4J 的 **MDC**(映射诊断上下文),而一个 JSON 编码器把 MDC 复制进每一条日志事件。结构化日志——用 JSON 而不是纯文本——是另一半:机器能在十亿行里用毫秒级过滤出 `level=ERROR AND service=payment`,而这件事它对着自由格式的文本靠不住地做不到。

```xml
<configuration>
  <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
      <includeMdcKeyName>traceId</includeMdcKeyName>
      <includeMdcKeyName>spanId</includeMdcKeyName>
    </encoder>
  </appender>
  <root level="INFO">
    <appender-ref ref="JSON"/>
  </root>
</configuration>
```

(Spring Boot 3.4+ 可以原生做这件事:`logging.structured.format.console=logstash`,不需要额外的编码器依赖。)

### 采样与留存:日志是要花钱的

日志是三个信号里最占体量的——一个繁忙的集群一天写下几百 GB 到 1 TB,而为此付的 Elasticsearch 存储费,是一个会被要求你解释的开支项。所以你砍两刀。**留存(retention)**按年龄分层:7 天热、可搜索,然后 30–90 天便宜地冷存在对象存储里,再然后删除。**采样(sampling)**按重要性分层:WARN 和 ERROR 全留,但对 INFO/DEBUG 采样——或者更好,对被采样过或出错的 trace 保留其全部日志,其余丢弃。这个取舍很尖锐,失败模式也很具体:采样太狠,你凌晨三点要复原的那一条请求,恰好就是你扔掉的那一条。全都留,那么变成故障的就不是宕机,而是账单。

## 练习

1. 给一个服务加上 `logstash-logback-encoder` 和上面那份 `logback-spring.xml`;确认每一行日志现在都是带 `traceId`/`spanId` 字段的 JSON。发一条被追踪的请求,从 Zipkin 里把它的 traceId 复制出来。
2. 用 Docker Compose 搭起 Loki + Promtail + Grafana(或 ELK),把两个服务的日志送进去,用任务 1 里的那个 traceId 做过滤查询——确认你能在一条时间线上看到来自两个服务的日志。
3. 在请求进行到一半时杀掉并重新发布一个容器(`docker rm -f` 或 `kubectl delete pod`);确认它的本地日志消失了,但集中存储里还在。
4. 估算你的集群每天的日志量(行/秒 × 字节/行 × 服务数 × 86400),再设计一个「留存 + 采样」策略,把存储砍掉 5–10 倍,同时仍保留每一条 ERROR 和每一条被采样的 trace。
