## 把横切关注点搬出代码

到目前为止,你搭的一切都默认「治理住在应用里」:Resilience4j 负责重试和熔断、Spring Cloud LoadBalancer 挑实例、Micrometer 发出追踪、你的代码校验 JWT。只要每个服务都是引了同一批库、并同步升级的 Spring Boot 应用,这套就工作得很漂亮。可一旦系统里混进一个 Go 服务、一个 Node 服务、或一个 Python 模型服务,它就不灵了:它们谁都不懂 Resilience4j,于是你的重试策略、mTLS、追踪在整个集群里变得参差不齐。

**服务网格**去掉了这个前提。它在每个服务的 Pod 旁注入一个 **sidecar**——一个小小的代理,几乎总是 Envoy——并重新配置这个 Pod,让服务所有进出的流量都先过它的 sidecar。应用只跟 localhost 说话,真正的网络活儿由 sidecar 干。而因为 sidecar 坐在每个请求的必经之路上,它就能把请求需要的一切横切能力——双向 TLS、重试、超时、熔断、负载均衡、灰度切分、遥测——全部做掉,而应用既不知道也不必关心,并且对 Go 服务和对 Java 服务一模一样。

## 数据平面与控制平面

网格分两半。**数据平面**是那一大群 sidecar 代理——每个 Pod 一个——它们真正承载并治理流量。**控制平面**(Istio 里是 Istiod,Linkerd 里是它的 controller)是大脑:它盯着集群,把配置和证书下发给每一个 sidecar。你不会逐个去配代理;你把策略写一次——「订单流量按 90/10 切分」「这个命名空间强制 mTLS」「库存重试 3 次」——控制平面就把它分发给相关的 sidecar。正是这个控制平面/数据平面的分工,让一套规则能治理成千上万个代理。

关键在于,网格的策略都是 Kubernetes 资源——路由和重试用 `VirtualService`,负载均衡和离群检测(它的熔断器)用 `DestinationRule`,mTLS 用 `PeerAuthentication`。这些由平台团队拥有;应用团队不再写这些代码。

## 网格 vs Spring Cloud:谁来管

现在说那个让人不舒服的部分:网格做的很多事,Spring Cloud 已经在做了。两边都能重试。两边都能熔断。两边都能做 mTLS、负载均衡、追踪。它们大量重叠,而这个重叠是个坑。

| 关注点 | Spring Cloud(进程内) | 服务网格(sidecar) |
|---|---|---|
| mTLS | 逐服务手配 TLS/JWT | 自动,零代码 |
| 重试/超时 | Resilience4j `@Retry` | VirtualService retries |
| 熔断 | `@CircuitBreaker` | outlierDetection |
| 负载均衡 | Spring Cloud LoadBalancer | Envoy |
| 灰度/切分 | 网关权重(仅边缘) | 服务间权重 |
| 追踪 | Micrometer 埋点 | Envoy 自动生成 span |

规则是:**每个关注点只选一个归属。** 如果你的 `@Retry` 和网格都重试,尝试次数会相乘——应用重试 3 次乘以网格重试 3 次就是 9 次调用,一场你不小心亲手造出来的重试风暴。如果两边都做 mTLS,你就白付了两遍。所以当你上网格时,要把对应的 Spring Cloud 配置删掉,代码里只留网格无法理解的东西:业务专属的兜底逻辑(库存挂了该返回什么,是产品决策,不是网络决策)。用上面的治理台把每个关注点分配一遍,体会这个取舍。

## 代价

网格不是免费的,而它的代价恰恰解释了为什么不是每个团队都该上。第一是**延迟税**:每一跳现在都要多穿过两个代理(出调用方的 sidecar,进被调方的 sidecar),每个多加零点几毫秒——单跳很小,但乘以一条深调用链、乘以每一个请求就不小了。第二是**资源**:每个 Pod 一个 sidecar,意味着成百上千个 Envoy 进程,各自吃 CPU、常常还吃约 100MB 内存——在集群规模上是一笔实打实的开销。第三是**运维复杂度**:你现在要部署和升级一个控制平面加一个数据平面,要排查那些不再按应用以为的路径走的流量,还多了一层会出故障的东西。

对一个小的、全 JVM 的系统,Spring Cloud 进程内可能更简单也更便宜。网格真正物有所值,是当你多语言、规模大、或者需要一套你没法信任每个团队都在代码里实现得一模一样的统一安全与流量策略时。

## 练习

1. 在 kind/minikube 集群上装 Istio,给一个命名空间打上 `istio-injection=enabled`,部署一个服务,确认 `kubectl get pod` 显示 `2/2`(应用 + sidecar)。
2. 把重试和超时从 Resilience4j 配置搬进 VirtualService;再把 `@Retry` 注解删掉,验证行为不变——而且你不再双重重试了。
3. 用 PeerAuthentication 打开严格 mTLS;抓一下两个 Pod 之间的流量,确认它现在已加密,而且一行代码都没改。
4. 做一次服务间灰度——用 VirtualService 把流量按 90/10 切到两个版本——再和你在网关(模块 IV)做过的边缘灰度对比。
