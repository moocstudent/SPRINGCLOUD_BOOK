## Validate the token once, at the door

A JWT (JSON Web Token) is a signed statement of identity: a header, a claims payload (user id, roles, expiry), and a signature the issuer computed with its private key. Because the signature is self-contained, any party holding the public key can verify the token without a database lookup. That makes the gateway the natural place to check it: **verify the signature once at the edge**, confirm it has not expired, extract the user identity, and forward that identity to the backend in a trusted header (say `X-User-Id`) while stripping any client-supplied one. The hundred backends then trust the header and never re-verify — they sit on a private network the gateway guards.

The trade-off is CPU. Verifying an RSA-2048 signature costs tens of microseconds; at 20,000 requests per second that is real core-time on cryptography at the edge. The tempting "optimisation" is to cache the verification result by token, or skip verification on "internal" paths — and both reopen security holes. Caching a decoded token means a **revoked or expired** token keeps working until the cache entry ages out; trusting an internal path means anyone who reaches the gateway's network can forge the identity header. The honest answer is to verify every request, scale the gateway horizontally (it is stateless, so this is easy), and prefer the markedly cheaper **EdDSA / ES256** over RSA when verification cost bites.

## The token bucket: rate cap and burst in one

The second edge job is rate limiting, and the algorithm that has won is the **token bucket**. Picture a bucket holding up to `burstCapacity` tokens, refilling at `replenishRate` tokens per second. Every request must take one token; if the bucket is empty, the request is rejected. Two numbers give you two independent controls:

- **replenishRate** sets the sustained average rate — the long-run requests per second you allow.
- **burstCapacity** sets how large a momentary spike you tolerate — a full bucket can be spent all at once before the refill rate takes over.

@fig sc11-bucket

| Setting | replenishRate | burstCapacity | Behaviour |
|---------|--------------:|--------------:|-----------|
| Strict | 100 | 100 | steady 100/s, no slack |
| Bursty | 100 | 500 | 100/s average, absorbs a 500-token spike |
| Misconfigured | 100 | 100000 | a "limit" that never triggers under real bursts |

This is exactly the **peak-shaving** the bench visualises. Pour a burst of ten times the sustained rate in and watch three lines move: admitted requests track the refill rate plus the one-time bucket drain, throttled requests are the overflow, and backend load stays flat at its provisioned rate. The tenfold spike that would have flattened the database becomes a survivable steady stream plus a pile of rejections — the database never sees the spike.

## Redis rate limiter and the KeyResolver

Because the gateway runs as many instances, the bucket must be **shared** — otherwise five gateways each allow 100/s and the real limit is 500/s. Spring Cloud Gateway's `RequestRateLimiter` filter keeps the bucket in Redis, so all instances draw from one bucket. A `KeyResolver` decides *what* is limited — per user, per IP, or globally:

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: orders
          uri: lb://ORDER-SERVICE
          predicates:
            - Path=/api/orders/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
                key-resolver: "#{@userKeyResolver}"
```

```java
@Bean
KeyResolver userKeyResolver() {
    return exchange -> Mono.justOrEmpty(
            exchange.getRequest().getHeaders().getFirst("X-User-Id"))
        .defaultIfEmpty("anonymous");
}
```

Limiting per user (above) stops one abusive client without touching everyone else; limiting per IP is coarser but works before authentication; a single global key protects a fragile backend regardless of who calls.

## 429, not a queue

When the bucket is empty, the gateway returns **HTTP 429 Too Many Requests** immediately — it does not hold the request and wait for a token. This is the crucial design choice. Queuing overflow feels gentler but is a trap: held requests consume memory and connections, latency climbs for everyone, and the client — already timing out — retries, adding yet more load. That is **slow death**: the system degrades for all callers at once and takes minutes to recover. A fast 429 is **back-pressure** the caller can act on — back off, retry later with jitter, or shed the work. Rejecting the 1,000 requests you cannot serve keeps the 100 you can serve fast. A 429 should carry a `Retry-After` header so well-behaved clients know when to return.

1. On the bench, set replenishRate=50 and burstCapacity=50, pour 500 requests into one second, and record the admitted-vs-throttled split; then raise burstCapacity to 250 and explain which requests now get through that did not before.
2. Write a KeyResolver that limits by client IP instead of `X-User-Id`, and give one scenario where per-IP is wrong (hint: many users behind one NAT).
3. Configure the RequestRateLimiter to return a `Retry-After` header on 429, and describe what a well-behaved client should do with it.
4. Estimate the CPU cost of verifying 20,000 RSA-2048 signatures per second at about 30 microseconds each, and decide how many gateway cores you would provision with 50% headroom.
