## 两种拆错:太粗的伪服务与太细的分布式单体

拆分是微服务里最贵的一个决定,因为它最难回退。拆错有两种,而且它们朝相反的方向失败。

**太粗。** 你把单体拆成两三个大服务,它们仍然共享数据、仍然一起变。你现在付出了网络延迟和部署协调,却没换来任何独立性——一个**伪服务**。你干了最累的活,得到的是一个更慢的单体。

**太细。** 你把「小即是美」追进纳米服务:一张表一个、一个实体一个。于是一次下单要扇出十几个同步调用(**喋喋不休**),更糟的是,一条必须原子成立的业务规则——既扣库存**又**扣款——被拆到了不同服务里,于是你在日常路径上就需要一个**分布式事务**。你用一个 `@Transactional` 换来了一个 Saga。

## 限界上下文:一个服务拥有一块领域

对的那道缝来自领域驱动设计:按**限界上下文(bounded context)**切,而不是按表切。限界上下文是一条边界,在它内部每个词都只有一个意思。「客户」在销售里(一个带管道阶段的线索)不是「客户」在计费里(一个带支付方式的账户),也不是「客户」在客服里(一段工单历史)。**语言的含义在哪里发生变化,哪里就有一道缝。**

拿它跟按表切对比。做一个 `UserService` 拥有 user 表、一个 `OrderService` 拥有 order 表,那么渲染一个订单页面——用户 + 订单 + 地址——就变成一次跨网络的扇出:你把一句 SQL `JOIN` 变成了三次 RPC。限界上下文能避开这个,因为一个上下文拥有回答自己问题所需的**全部**数据,它天生就是内聚的。让服务对齐**业务能力**——商品、下单、库存、支付、发货——每一个都是一个上下文,拥有自己的数据,对外只暴露行为。

## 每个服务拥有自己的数据,不共享库

这是让其余一切成立的规则,也是团队最常破的一条:**一个服务的表是私有的。** 别的服务不能直接读它、写它——只能通过属主的 API 或它发出的事件。

@fig sc3-split

为什么这么严?共享 schema 是**世上最紧的耦合**。两个服务一旦从同一张表 `SELECT`,你就再也不能改这张表的结构,除非做一次多服务同步部署,而「独立部署」——你当初拆分的全部理由——就此死掉。共享数据库给你的是单体的耦合**外加**网络的开销:两头最差的都占了。所以跨服务的数据要靠「问属主」拿,或者做成一个由属主事件更新的本地读模型,于是一致性变成**最终一致**(第五模块的主题)。

```yaml
# order-service —— 自己的库,别人碰不到
spring:
  datasource:
    url: jdbc:postgresql://db-order:5432/order_db     # 不是 inventory 的库
# inventory-service —— 物理上独立的另一个库
spring:
  datasource:
    url: jdbc:postgresql://db-inv:5432/inventory_db
```

如果你有两个服务的 `datasource` 指向同一个 schema,那你没有两个服务。

## 粒度的 U 形曲线,与耦合判据

把总成本对粒度画出来,你会得到一个 **U**。左臂高(太粗:局部无法独立扩容或部署,爆炸半径大)。右臂高(太细:跨服务调用、分布式事务、每个需求摊到更多基础设施和认知负担)。谷底——最优点——由**你的领域实际的耦合**决定,而不是由「越小越好」决定。**在治理台里拖动粒度滑块,看跨服务调用数和分布式事务的牵连范围在细的一侧陡峭爬升**,同时「单次改动的爆炸半径」缩小;两条曲线的交叉处,就是你的最小值。

怎么判断某道边界切错了?用**耦合判据**——也就是**分布式单体**的症状:

| 你观察到的症状 | 它意味着什么 | 处理 |
| --- | --- | --- |
| 两个服务总是一起发布 | 它们的变更理由相同 | 合并 |
| 一次业务操作要穿过很多服务 | 一个能力被拆散了 | 围绕它重划边界 |
| 服务之间共享一张表 / 一个库 | 它们共享同一个事实源 | 归一个所有,对外暴露 API |
| 一个需求经常同时改两个服务 | 高内聚被从中切开 | 移动边界 |

底下那条原则是软件里最古老的一条:**服务内部高内聚,边界之间低耦合。** 如果一道拟议的边界从一簇「总是一起变」的东西里切过,那这道边界的位置就是错的。两个服务如果总是一起变、总是一起发、或者需要一个分布式事务才能保持正确,那它们本来就是**一个被你硬掰开的服务**——把它们合回去,到耦合真正低的地方再切。这把刀挥下去便宜,收回来极贵,所以只在领域本就薄的地方下刀。

## 练习

1. 挑一个你最近上线的需求,列出它的改动碰过的每一个服务(或模块)。如果碰了三个,提出一道能让它只碰一个的边界。
2. 对一个你熟悉的领域做一次事件风暴(event storming):把每个领域事件都写成「某事已发生」,聚类,再围绕这些簇画出候选的限界上下文。标出任何一个在两个簇里含义不同的词(比如「订单」)。
3. 在你手上的系统里(或者虚构一个合理的)找出两个服务之间共享的一张表。设计那个 API 调用或事件,让其中一个服务拥有它、另一个不再直接读它。
4. 在治理台里把粒度推到最细的极端,记下分布式事务的数量;再找出让总成本最小的那个粒度,解释是哪一条领域事实把最优点钉在了那里。
