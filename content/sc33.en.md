## Not just Java: onboarding that Python service

Up to here the book has assumed every service is a Spring Boot app: add one `@EnableDiscoveryClient` and it registers itself into Nacos, heartbeats itself, and is found by `lb://`. But in reality there is always one service that is not Java — a model inference, a data-cleaning step, a Flask script a department wrote three years ago that nobody dares touch. It has to cooperate with this system, and it knows nothing about Spring Cloud: it will not register, sends no heartbeat, and other services have no idea where to find it.

First, split the problem cleanly. A service truly "joins" Spring Cloud through two independent channels — do not conflate them:

- **The entry channel** — how external requests reach it. That is the **gateway's** job, and it is language-agnostic.
- **The discovery channel** — how the system's insides know where it is, whether it is alive, and how many instances there are. That is the **registry's** job, and it assumes by default that you are a JVM app that heartbeats.

A Python service can take the first channel and skip the second, or take both. Working out which you actually need is the starting point for every decision in this chapter.

## Edge proxy: one static route already inherits the gateway

Start with entry. When you use the gateway as an **edge proxy** — all external traffic entering through that single door, backend services hidden on the internal network — you already have the least-effort way to onboard Python: a **static route**.

```
- id: python-static
  uri: http://python-host:8000      # one hard-coded address
  predicates: [ Path=/py/** ]
```

That is all. The gateway is a reverse proxy plus a filter chain, and at the HTTP layer it does not care whether the backend is Java or Python. A request hits `/py/**`, it forwards to that address, it returns the response. Python registers nothing and changes not a line.

And here is the part people miss — the free lunch: the moment it sits behind the gateway, Python **inherits the gateway's full set of cross-cutting concerns**. The JWT validation, token-bucket rate limiting, CORS, access logging and canary weights you configured on the gateway **apply equally** to the `/py/**` route. You wrote no auth code for Python, yet it is already protected by auth; you wrote no rate limiting in Python, yet it is already rate-limited. For "I just want this Python service to have one front door, and to be governed by auth and rate limiting along the way", the static route is where you stop — do not build further.

State the cost too; do not mistake the free lunch for free. That `uri` in a static route is **one hard-coded address**: the gateway does not know you actually started three Python instances, so all load lands on this one; when this address dies, the gateway keeps forwarding to it and the whole route 502s until a human notices and hand-edits config or restarts. The gateway has **no load balancing and no health awareness** of it. And it is not in discovery: other services cannot call it by name with `lb://python-service`, nor does it fold into the unified breaking and tracing. Those are exactly what the second channel solves.

## To register or not: the sidecar brings Python into Nacos

If you want more than "it has an entry" — you want Python to become a proper, discoverable, load-balanced service that is auto-evicted when it dies and callable by name — then it has to enter the registry.

Back to the root problem: Python is not a JVM, so it will not register or heartbeat itself. Two roads get it into Nacos:

- **Python registers itself (direct SDK)**: with a client like `nacos-sdk-python`, add a few lines in Python — call `add_naming_instance` on startup to register, then a background task every few seconds to `send_heartbeat` and renew the lease. Clean and direct, at the cost of **intruding into Python's code**, and your team maintains that heartbeat logic.

- **The sidecar pattern**: a **lightweight Spring Boot process** runs alongside Python (`spring-cloud-alibaba-sidecar`). It registers Python into Nacos for it, heartbeats for it, and periodically hits Python's `/actuator/health` — Python healthy, it reports alive; Python's health check fails, it lets Nacos evict that instance. The key: **Python changes not a line**, and does not even know the sidecar exists. This is the standard answer for "onboarding a polyglot service into Spring Cloud".

@fig sc33-sidecar

Once either road puts it into Nacos, the effect is the same — and it is precisely the effect a static route cannot give. The gateway's route changes from `uri: http://python-host:8000` to `uri: lb://python-service`, where `lb://` means "pick one from the currently live instances in the registry". Now you start N Python instances and traffic spreads across N; when one dies, Nacos evicts it within **one detection window** (heartbeat interval × missed beats to evict, say 5s × 3 = 15s), and only the requests hitting that node during the window fail (a gateway retry saves most); traffic then rebalances to the rest. Other Java services can also call it by name with `lb://python-service`, and it joins the unified breaking, tracing and config.

The bench lays these three modes side by side so you can compare directly: with N instances and one dying, how many requests a static route loses and how long it waits for a human, versus how fast registration self-heals. The gap is not marginal — the static loss is "rate × a few hundred seconds of human response", the registered loss is "one instance's share × a ten-odd-second detection window".

So which road? **Just a single entry plus the gateway's auth and rate limiting** — static route, do not over-design. **Python folded into the whole service governance** (load balancing, discovery, breaking, callable by name) — into Nacos: direct SDK if you can edit Python, sidecar if you cannot.

## Follow the conventions: trace headers, JWT, config

Onboarding is only step one. To earn the full governance the book built earlier, Python must **follow the same conventions as the Java services** — the gateway forwarding to it does not mean it automatically joins tracing, auth and config. Three things must line up on both sides.

**Distributed tracing.** As M6 showed, when a request crosses eight services it relies on a traceId that runs through the whole chain, each hop passing it along. If the Python hop receives a request but does not read and forward that header, tracing **breaks** at Python — it becomes a black hole in the waterfall and you can no longer see where those 800 ms went. The convention is the W3C `traceparent` header: Python reads it on arrival and carries it on outbound calls. The easiest path is unifying on **OpenTelemetry** across both sides — it is cross-language, it underlies the newer Spring's Micrometer Tracing on the Java side, and there is a mature OTel SDK on the Python side that receives and propagates it for you.

**Auth.** The gateway validates the JWT once at the edge, then forwards to the backend. Python then has two postures: **trust the gateway** — treat internal traffic as already past that gate (pair this with network isolation so nobody bypasses the gateway to hit Python directly); or **re-validate itself** — take the gateway's public key and check the JWT's signature and expiry again in Python. Zero trust wants the latter, convenience takes the former, depending on your threat model. Either way, **do not let Python invent its own auth scheme** — that defeats the whole point of a single front door.

**Config.** Java services hot-reload config from the Nacos config center; Python does not by default. Either use `nacos-sdk-python`'s config client to pull it (it supports watching for changes), or step back and pass config into the Python container as environment variables. The latter is simpler, at the cost that a config change means a restart — usually acceptable for a Python service whose config rarely changes.

One line to close: **the gateway gives Python an entry, the registry makes it discoverable, and these conventions make it truly a member of the system** — rather than a bolt-on hanging off the side, reachable but invisible and ungoverned.

1. On the bench pick "static route", 4 instances at 600 rps, and set the first instance down; note the lost requests and the self-heal mode. Switch to "sidecar" with the same parameters and compare the two numbers.
2. Turn both "heartbeat interval" and "missed beats to evict" to maximum and watch the detection window and lost requests rise; then both to minimum and watch them fall — and think about what setting them too low costs you (recall false eviction from the RD module).
3. In the gateway config, add JWT validation and a rate-limit filter to the `python-lb` route too; confirm Python is protected without changing any Python code.
4. Draw the trade-off table for "direct SDK" vs "sidecar": what each makes you change, what each makes you run, where the operational cost sits. When would you rather edit Python code than run one more sidecar process?
