## 为什么要版本

微服务的全部承诺,是每个服务能按自己的节奏发布。这个承诺有一道锋利的边:订单服务的接口有调用方——别的服务、手机 App、第三方——它们也按各自的节奏发布。在单体里,你改一个方法签名,编译器会找出每一个调用点,你一次提交全改完。跨网络你没有这份奢侈:你无法原子地同时升级调用方和被调方,因为它们是不同团队(有时是不同公司)拥有的、各自独立的部署单元。于是,你一旦做了老调用方看不懂的改动,那个调用方就会挂——在生产环境、在半夜三点、为一个从没同意过你发布日期的人。

API 版本管理,就是让接口能在老调用方继续工作的前提下演进。但在动手加版本之前,先学会它最重要的一课:**大多数改动根本不需要版本。**

## 先别急着加版本:向后兼容的演进

一个改动如果能让原封不动的老调用方继续对着新接口工作,它就是向后兼容的。规则简单而严格:

- **只加,不删不改名。** 一个新增的可选字段或端点,对不主动要它的调用方是隐形的。
- **绝不改语义或类型。** 把 `status` 从字符串改成枚举、把 `amount` 从「分」改成「元」,即使字段名一模一样,也是破坏性的。
- **调用方用宽容的读取器。** 一个会忽略不认识字段(而不是整个拒绝响应)的客户端,能自动扛过每一次加法改动。

守住这些,你可以演进好几年而从不切出 v2。上面的治理台就能看到:选「向后兼容」,被打断的调用方是 0、你要维护的版本数保持 1。只有当你必须做真正破坏性的改动——删字段、改类型、重构资源——才去动真正的版本。

## 版本放哪

当你确实需要版本时,你得决定这个版本号放在哪。常见有三个位置,而这个选择是取舍,不是品味:

| 方式 | 示例 | 优点 | 缺点 |
|---|---|---|---|
| URI 路径 | `GET /v2/orders` | 直观、在网关极易路由、可缓存 | 「版本进 URL」被 REST 纯粹派诟病 |
| 请求头 | `X-API-Version: 2` | URL 干净、资源标识唯一 | 不可见、缓存要按它区分、curl 不便 |
| 媒体类型 | `Accept: application/vnd.shop.v2+json` | 内容协商、最「正确」 | 最难测试、调试和缓存 |

在 Spring Cloud 系统里,URI 路径通常胜出,原因很实际:它对网关来说极容易路由。`/v1/**` 去 order-service-v1,`/v2/**` 去 order-service-v2——就是你在网关那章见过的一行断言。请求头和媒体类型版本让 URL 保持干净,但把路由逻辑塞进断言、还逼你的缓存按版本区分,这很容易出错。

## 并行运行与退场

一个版本是你必须兑现的承诺,而同时兑现两个是有代价的。一旦切出 v2,你就要让 **v1 和 v2 并行运行**,直到每个调用方都迁移过去——在那之前,你要修 bug、打安全补丁、为两套代码路径付钱。这正是你不该随便加版本的原因。

有纪律地退掉旧版本的办法,叫**扩展-收缩**(也叫并行变更),分三步:

1. **扩展 Expand**——让 v2 与 v1 并存,两个都活着。
2. **迁移 Migrate**——把调用方迁到 v2,看着 v1 的流量往零掉。
3. **收缩 Contract**——过了公布的日落日期,删掉 v1。

你用标准 HTTP 头来通知截止日期:`Deprecation: true` 标记一个端点正在退场,`Sunset: <日期>` 说明它何时被移除,再用一个 `Link` 指向后继版本。给调用方一个真实的窗口——是几周,不是几天——并监控 v1 的流量,让你凭证据、而不是凭祈祷来退役它。治理台把代价摆明:破坏性改动配上版本并行,打断 0 个调用方,但多出几周的双版本维护;同样的改动就地做,则一次打断所有调用方。

## 练习

1. 拿一个真实端点做一次纯加法改动(加一个可选字段)。确认一个用宽容读取器的老客户端仍能工作,且不用升版本。
2. 再做一次破坏性改动,把它以 `/v2` 暴露;用网关断言把 `/v1` 和 `/v2` 路由到两个后端,验证两者同时可用。
3. 给你的 v1 响应加上 `Deprecation` 和 `Sunset` 头;写一个小客户端,在看到它们时打一条告警日志。
4. 在一个玩具服务上把扩展-收缩走一遍:发布 v2,迁移一个客户端,看着 v1 流量掉下去,然后删掉 v1。
