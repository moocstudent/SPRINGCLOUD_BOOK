## 一个请求,一整本书

这本书里的一切,最终都汇聚到一行生产流量上:`POST /checkout`。跟着这一个请求在系统里走一遍,你学过的每一个模块都会依次登场、各司其职。这里没有任何新东西——综合实战不是又一个组件,而是那二十三个机制能协同工作的证明。

@fig sc24-arch

这段旅程,逐跳来看:

| # | 跳 | 发生了什么 | 模块 |
|---|---|---|---|
| 1 | 客户端到网关 | 终止 TLS;校验 JWT 签名与 `exp`;令牌桶限流;按路径路由 | m4、m8 |
| 2 | 网关到订单 | 通过注册中心找到实例,由客户端负载均衡挑选 | m2、m3 |
| 3 | 订单到库存 | OpenFeign 调用,外面裹着一个超时 1 秒的熔断器 | m3 |
| 4 | 订单:全局事务 | Seata 把「扣库存 + 扣支付」协调成一个整体 | m5 |
| 5 | 订单到消息中间件 | 通过 Spring Cloud Stream 向 Kafka 发出 `order.created` | m5 |
| 6 | 积分 / 通知 | 异步消费这个事件,各自按自己的节奏 | m5 |
| - | 每一跳 | 一个 `traceId` 串起所有 span;指标被采集;日志被关联 | m6 |
| - | 每个副本 | 配置来自配置中心;调度在 K8s 上、由 HPA 伸缩;两机房异地多活 | m4、m7 |

同步主干(第 1 到 4 步)必须全部成功,否则整次下单作为一个整体失败;异步尾巴(第 5 到 6 步)是发完就走,所以发积分可以慢上几秒而不让顾客等待,通知消费者挂了也永远不会挡住一笔订单。这个切分——在钱的地方求强一致,在不涉及钱的地方接受最终一致——是整张图里最重要的一个设计决定。

```java
@GlobalTransactional(timeoutMills = 10000, name = "checkout")   // Seata:一个全局事务
public OrderResult checkout(CheckoutCmd cmd) {
    inventory.deduct(cmd.sku(), cmd.qty());                     // Feign + 熔断(分支)
    payment.capture(cmd.userId(), cmd.amount());                // 分支事务
    Order order = orders.save(Order.created(cmd));
    stream.send("order-out-0",
        new OrderCreated(order.id(), cmd.userId(), cmd.amount())); // 异步事件
    return OrderResult.ok(order.id());
}
```

## 相互牵制的权衡

综合实战真正难的地方在于:你没法孤立地调每一个机制——拧动一个旋钮会带动别的。

- **一致性吃掉弹性。** Seata 的 AT 模式,从 `deduct` 起就锁住库存行和支付行,直到全局提交。假设每次下单持锁 40 毫秒,那么一个爆款 SKU 的行,就把对它的每一笔订单串行化了——此刻的天花板是数据库上的锁争用,而不是副本上的 CPU。把订单服务从 3 个副本自动扩到 12 个,在这里一点也帮不上,因为第 12 个副本排的,还是第 3 个副本排的那把锁。更强的一致性(2PC / XA)只会更糟;而带补偿的 Saga,用「放弃这把锁」换来了「写对补偿逻辑」这个更难的问题。
- **激进的自动扩容放大冷启动。** 把 HPA 调得反应很快,它会在负载一冒尖就加副本——可一个全新的 JVM 副本要 30 到 45 秒才能启动、预热连接池、把热点路径 JIT 编译好。如果它在真正热起来**之前**就注册进了服务发现,负载均衡器就会把真实流量打给它,它头几个响应就撞破那 1 秒超时,于是调用方的熔断器在一个只是「冷」、并没有「坏」的副本上跳开了。本想缓解负载的扩容,反倒制造了超时。就绪探针和预热,存在的意义正是堵住这个缝。

## 单点与瓶颈

把图画出来,风险就自己亮起来了:

- **有状态的存储**——订单数据库和 Seata 的事务协调器(TC)——才是真正的单点;副本是牲口,数据库是宠物。大多数事故都住在这里。
- **消息中间件**是整条异步尾巴的共享依赖;给它分好区、定好容量,否则积分的积压会变成所有人的积压。
- **网关层和认证中心**坐在每一个南北向请求上。把它们做成水平扩展的集群;而如果你选了不透明令牌,别忘了认证中心现在每个请求都要吃一次内省调用。
- **注册中心**是所有人都在读的那张地图;正是客户端缓存(m2)让一次下单在注册中心短暂抖动时仍能走完。

## 一份成熟度自评

合上书之前,给你自己的团队打个分。八个模块每一个都是一个维度;每个维度从 0(临时凑合)打到 3(成熟),那些低分就是你的路线图。

| # | 维度 | 0 到 3:从临时凑合到成熟 |
|---|---|---|
| 1 | 边界与拆分 | 按 DDD 限界上下文拆,而不是靠共享表 |
| 2 | 注册与发现 | 没有写死的地址;注册中心抖一下也扛得住 |
| 3 | 通信与韧性 | 每个远程调用都有超时 + 熔断 + 安全重试 |
| 4 | 网关与配置 | 单一入口;改配置不用重新发布 |
| 5 | 消息与事务 | 消费者幂等;有一个刻意选定的一致性模型 |
| 6 | 可观测性 | 一个 traceId 贯穿全链路;你按 p99 告警,而不是平均值 |
| 7 | 部署、伸缩与多机房 | HPA 调好了;有一个你真正演练过的 RPO/RTO |
| 8 | 安全与混沌 | 零信任鉴权;韧性靠混沌演练验证过 |

一个大多打 0 到 1 的团队,手里是一个多了网络延迟的分布式单体;一个大多打 3 的团队,手里是一个会降级、而不是会崩溃的系统。治理台把这整条链路渲染成一块仪表盘——给它加压、跳开一个熔断器、挂掉一个机房——让你亲眼看着你刚给自己打的那个分,变成真实的行为演出来。

## 练习

1. 在你自己的系统里追踪一个真实请求,端到端地把上面那张旅程表填出来,换成你真实的组件和模块。哪一跳没有超时、也没有熔断?
2. 量一量你最热的那个分布式事务里锁被持有的时长,再算出它把一个 SKU 上的多少并发订单串行化了——你真正的瓶颈,是 CPU 还是这把锁?
3. 用上面八个维度给你的团队打分,每个分数都配一条证据。圈出最低的两项——那就是下个季度的活儿。
4. 在治理台上,在下单进行到一半时挂掉一个机房。记录流量多久才恢复(你观测到的 RTO),以及有没有丢失任何在途订单(你的 RPO)。
