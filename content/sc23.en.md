## "Configured" is not "working"

You spent the last seven modules installing breakers, timeouts, retries, bulkheads, replicas and cross-DC failover. Here is the uncomfortable question: which of them have you ever actually seen fire? A line in a config file that reads `circuitBreaker.enabled: true` is a claim, not a guarantee. The breaker can be present and still be dead three ways:

- the **threshold is wrong** — it opens at a 90% failure rate over a 100-call window, so a downstream that fails 60% of calls for thirty seconds never trips it;
- it was **overridden** — someone pushed `enabled: false` through the config server for a load test in March and never reverted it;
- the **fallback is buggy** — the breaker opens correctly, calls the fallback, and the fallback throws its own NullPointerException, so the caller fails anyway.

Chaos engineering starts from a blunt premise: **a fault-tolerance mechanism you have never verified under real failure should be assumed broken.** Confidence has to be earned by watching the thing work, not by reading that it is enabled.

## The steady-state hypothesis: define "normal" as a number

An experiment needs a pass/fail line drawn *before* you break anything. That line is the **steady-state hypothesis** — a measurable statement of healthy behaviour, ideally a business metric, not a machine one. "CPU under 70%" is weak; "checkout success rate stays above 99.5% and p99 latency stays under 800 ms" is a hypothesis, because it is what the user actually feels and it is a number you can watch second by second during the experiment.

## Bound the blast radius

The difference between an experiment and an outage is control. You **bound the blast radius**: start where a failure is cheap — staging first, then one instance, then 1% of traffic, at an off-peak hour, with an abort button wired in — and widen only after the system holds. Then inject failure and watch whether the steady-state metric survives:

@fig sc23-chaos

| Fault injected | Real event it simulates | Resilience it verifies | Expected under hypothesis |
|---|---|---|---|
| Kill 1 of 3 order pods | crash, rolling deploy | registry eviction + client-LB retry | success stays above 99.5% |
| +500 ms latency on inventory | GC pause, slow query | Feign timeout + breaker | p99 under 1 s, no thread pileup |
| 30% HTTP 500 from payment | partial downstream outage | breaker trip + fallback | success above 99% (degraded path) |
| Sever order-to-inventory network | partition | timeout + bulkhead isolation | order thread pool not exhausted |

Say the inventory breaker is set to open at a 50% failure rate over a 20-call window with a 1 s timeout. Inject 500 ms of latency on one inventory pod: within a couple of seconds the failure rate crosses 50%, the breaker opens, the fallback (a "reserve later" path) serves, and checkout success holds at 99%. Now suppose the threshold was miswired to 90% — the breaker never opens, order threads block on the 1 s timeout, the pool drains, and success collapses to 60%. Either way you learned the truth **in a drill you scheduled, not an incident at 3 a.m.**

## Inject, observe, fix — and a real spec

Modern tooling makes injection declarative and, crucially, self-reverting. Chaos Mesh, Litmus and ChaosBlade run inside Kubernetes; Netflix's Chaos Monkey pioneered random instance kills. Here is a Chaos Mesh experiment that adds latency to exactly one inventory pod for two minutes:

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: inventory-latency
spec:
  action: delay
  mode: one                 # blast radius: a single pod
  selector:
    namespaces: [shop]
    labelSelectors:
      app: inventory
  delay:
    latency: "500ms"
    jitter: "100ms"
  duration: "120s"          # auto-revert after 2 minutes
```

Note `mode: one` and `duration: 120s` — the blast radius and the abort are written into the spec, so the experiment cleans up after itself even if you walk away from the terminal.

The loop is: define steady state, form a hypothesis, bound the radius, inject, observe, and **fix what broke** — then keep the experiment. The highest-value discipline is turning every real incident into a permanent experiment: whatever took you down once becomes a repeatable game-day drill, so the same failure can never surprise you twice. On the bench you inject each fault above into a service dependency graph and watch it either stay contained at one service's border or spread up the call chain when the guard you assumed was there is not.

## Exercises

1. Write the steady-state hypothesis for your own checkout (or busiest) flow as two numbers you can pull from live dashboards right now.
2. Take one breaker in your codebase and read its actual threshold, window and timeout. Compute the failure rate and duration required to trip it — is that a rate your downstream would realistically reach before it takes you down?
3. Run the Chaos Mesh spec above (or the bench equivalent) against a non-critical service in staging. Record whether your steady-state metric held, and what the fallback actually returned.
4. Pick your last real incident. Write it up as a chaos experiment — fault, blast radius, hypothesis — that would have caught it, and put it on the calendar.
