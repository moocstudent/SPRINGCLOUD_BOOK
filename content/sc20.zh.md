## 承诺,以及承诺下面的小字

弹性是微服务对外兜售的核心能力:平时跑三个副本扛日常流量,大促涌进十倍负载时长到十几个,峰一过再缩回去——只为你真正用掉的容量付费。这个承诺是真的。小字部分是:伸缩是一个带滞后的控制回路,而三个坑就住在这段滞后里。这一章讲的就是怎么把这个回路调乖。

## HPA 控制回路

HPA(水平 Pod 自动伸缩器)盯着一个指标,调整副本数把它维持在目标附近。你给它一个目标——「把平均 CPU 保持在 60%」或者「每个副本每秒 100 个请求」——它大约每 15 秒重算一次:

    期望副本数 = 向上取整( 当前副本数 × 当前指标 / 目标指标 )

三个副本平均 90% CPU、目标 60%,得到 ceil(3 × 90 / 60) = 5,于是扩到五个。当指标掉回目标以下,它就缩容。算术很简单;所有难的地方都在时间上。

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - { type: Pods, value: 4, periodSeconds: 15 }
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - { type: Percent, value: 50, periodSeconds: 60 }
```

`minReplicas: 3` 是你的地板——永远不缩到三个以下,这样单台节点丢失也不会让你只剩一个副本。`maxReplicas: 20` 是天花板,保护你的账单和数据库不被一个失控的回路拖垮。

## 坑一:冷启动滞后

HPA 可以在一个 15 秒的周期里决定加一个副本。但这个副本还得过一阵子才能干活。一个跑在 JVM 上的 Spring Boot 服务,在第一批请求全速跑起来之前,要先付出镜像拉取、JVM 启动、Spring 上下文刷新、连接池预热、JIT 编译的成本——通常是 20 到 60 秒。而在它的就绪探针通过之前,Kubernetes 根本不会把流量路由给它:

```yaml
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  initialDelaySeconds: 15
  periodSeconds: 5
  failureThreshold: 3
```

在这段空档里,原来的三个副本仍在独自吸收整个突增,仍是 100% CPU,仍在把真实请求拖成超时。扩容不是瞬时的——你想要的那张图(负载上去、副本上去、延迟平的)是幻想;真实的图在新容量变绿之前的那几秒里有一个延迟尖峰。缓解手段直接冲着启动成本去:在已知的大促前预留余量、把最小副本数抬高,或者干脆缩短 JVM 启动本身——用 CRaC(检查点/恢复,几十毫秒就能恢复一个预热好的镜像),或者用启动不到 100 毫秒的 GraalVM 原生镜像。

## 坑二:抖动

假设流量恰好卡在对应「5 个还是 6 个副本」的那条边界上。没有阻尼的话,HPA 扩容 → 指标下降 → 缩容 → 指标上升 → 再扩容——副本数每个周期都在横跳,而每一次扩容都白白再付一遍冷启动成本。解药是稳定窗口。`scaleDown.stabilizationWindowSeconds: 300` 告诉 HPA 把一次缩容按住五分钟,取这个窗口内见过的最高建议值,于是它慢吞吞、不情愿地释放容量。扩容一般留快(窗口为 0),因为晚加容量会伤到用户,而晚减容量只是多花一点钱。

## 坑三:成本与延迟余量的拉锯

你挑的那个目标值,是一个伪装成数字的业务决定。目标定高,每个副本都塞得很满——便宜,但余量很薄,于是突增在新 Pod 到来之前就先把你的延迟吃掉。目标定低,每个副本都半闲着——延迟很平,账单很肥。

| 目标 CPU | 余量 | 峰值副本数(同样负载) | 3 倍突增下的 P99 | 相对成本 |
|---|---|---|---|---|
| 80% | 薄 | 8 | 飙到秒级 | 1.0× |
| 60% | 适中 | 11 | 短暂抬头 | 1.4× |
| 40% | 充裕 | 16 | 基本平 | 2.0× |

没有正确答案,只有一个你的业务能为之辩护的答案。治理台给你一条起伏的流量曲线和同样这三个旋钮——目标值、冷启动时间、稳定窗口——让你看着副本追流量、超时在扩容空档里冒出来、月账单随你留的余量一起动。

## 练习

1. 手推 HPA 公式:4 个副本、75% CPU、目标 50%,下个周期几个副本?再看 30% 时——会缩容吗,缩到几个?
2. 把 `scaleUp.stabilizationWindowSeconds` 设为 0、`scaleDown` 设为 300,然后用一句话解释为什么扩容要快、缩容要慢。
3. 测一个服务的冷启动:从容器启动到就绪探针通过的时间。它更接近 20 秒还是 60 秒,换成原生镜像会改变什么?
4. 在治理台上把稳定窗口降到 0,把流量推到正好压在副本边界上。看它抖动,再把窗口恢复,确认它稳定下来。
