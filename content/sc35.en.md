## A dashboard wants push, not pull

Last chapter, the Python time-series service published anomaly events to Kafka. But an event sitting in a topic that nobody watches is not monitoring. The last mile of monitoring is that it must **appear in real time on the wall screen ops is staring at** — a device goes wrong and a red alert pops up on the board at once, not when someone happens to refresh.

Make it concrete: how does a web dashboard (a browser) get, in real time, the anomaly events the server keeps producing? There is a directional hurdle here: HTTP is inherently "client asks, server answers" — a **pull**; but a dashboard wants the server to actively **push**.

A newcomer's first instinct is a `setInterval` that polls an alerts endpoint every few seconds. It runs, but it is using pull to fake push, and so it is stuck in a lose-lose trade-off: poll too often — say once a second — and a thousand screens mean a thousand requests a second hammering the server, and when anomalies are sparse, the vast majority come back with "no new alerts", pure waste; poll too rarely — say every 10 seconds — and an alert waits 5 seconds on average to reach the screen, and for a power anomaly that can hurt people, those 5 seconds may be the incident. The bench makes the bill visible: a thousand screens at a 5-second interval already forces the server to carry 200 req/s of polling, most of it empty.

Polling is not useless — with few screens and loose latency it is the least effort, and it is stateless with none of the fan-out problem below. But for a monitoring wall that needs real-time alerts, the right answer is to let the server **push**.

## Three transports: polling / SSE / WebSocket — a dashboard picks SSE

For real-time push between browser and server, there are three mainstream options, sorted by "who can send unprompted":

**Polling** — covered above. The client pulls repeatedly; the server answers passively. Simple, stateless, but wasteful and laggy.

**SSE (Server-Sent Events)** — a **one-way** server→browser stream. The browser opens a long-lived connection with one line, `new EventSource(url)`, and thereafter the server pushes events down that connection as it likes. Several of its traits are tailor-made for a dashboard: it is **plain HTTP** (`Content-Type: text/event-stream`), so it passes straight through Spring Cloud Gateway and reuses your existing auth and TLS with no extra protocol; it has **built-in reconnection** — if the connection drops the browser reconnects on its own, carrying `Last-Event-ID` so the server can resume from where it left off; and it is inherently one-way, which is exactly the shape of this case (the server pushes alerts, the screen just displays).

**WebSocket** — **full-duplex**, browser and server can each send unprompted. It is more powerful than SSE but heavier: it is its own protocol (`ws://`), and handshakes, heartbeats and reconnection are yours to arrange (the browser does not auto-reconnect the way SSE does). You need it only when the screen must **send things back** — ops clicks "mute this device" or "only show workshop A" on the board, and those commands go from browser to server. If the screen merely displays the alerts pushed to it, reaching for WebSocket is using a sledgehammer on a nut.

The one-line choice: **push-only to the screen → SSE; the screen also sends commands back → WebSocket; want no fuss and can tolerate lag → polling.** For "the dashboard consuming anomaly events", the default answer is SSE.

## The scaling trap: a shared consumer group makes screens miss alerts

You picked the transport and think you are done — until you scale the push service from 1 instance to 3 to carry more screens. Then alerts start **randomly vanishing**, and you cannot reproduce it in dev no matter what.

This is the one trap worth remembering from the whole chapter. Recall the mechanism: the push service consumes anomaly events from Kafka and pushes them to the screens connected to it. With just 1 instance, it consumes every anomaly and pushes to every screen — all fine. But when you scale to 3 instances that **share one Kafka consumer group** — a consumer group's semantics are "each message is taken by exactly one consumer in the group" (that is exactly what sc13 taught: groups spread load). So each anomaly is consumed by only **one** of the 3 instances. And a screen is connected, via the gateway's load balancing, to some random one instance. The result: an anomaly is consumed by instance 1, but your screen is on instance 2 — it never receives that alert. **Delivery drops straight to 1/M.**

With M=1 in dev everything is perfect and you ship with confidence; scale out and alerts start "inexplicably dropping" — and randomly (depending on which event lands on which instance and which screen is on which instance), the hardest kind to debug. The bench draws the collapse: switch to "SSE·shared group", pull instances from 1 to 3, and watch delivery fall from 100% to 33% with the screens-per-alert cut to a third.

The root cause: **a consumer group is for "spreading", but dashboard push needs "broadcast" — every instance must get every event.** Two fixes:

- **A per-instance consumer group**: give each push instance a unique group (e.g. splice the instance ID into the group name). Then each anomaly is consumed once per group, i.e. every instance gets the full stream and fans out to its own connections. Simple, at the cost of M copies of consumption on Kafka.
- **Redis broadcast / Pub-Sub**: one consumer reads anomalies from Kafka, then Redis Pub/Sub broadcasts each event to all instances, and each pushes to its own screens. One extra Redis hop, but fan-out is cleanly gathered into one layer, unfazed by how many instances there are.

The bench's "SSE·broadcast" setting is what it looks like fixed: no matter which instance a screen is on, delivery is 100%.

## Reconnect and snapshot: the screen can't blank on refresh

The last piece is keeping the screen alive. Two real problems:

**Reconnection.** A wall screen hangs there 365 days a year without closing; the network will hiccup and the connection will drop. The good news is SSE reconnects itself — on a drop the browser reconnects with no heartbeat code from you. But cooperate on the server: tag each event with an `id`, and on reconnect the browser puts the last id it saw into the `Last-Event-ID` header, from which the server resumes, so the few seconds' worth of alerts during the drop are not lost (WebSocket has no built-in mechanism for this — you implement it yourself).

**First-paint snapshot.** Picture ops refreshing the board, or opening a new screen. If you only push "increments" — alerts produced from this moment on — the screen starts out **blank**: the dozens of alerts currently red get shown none, until the next new alert arrives. For a monitoring wall that is unacceptable. The fix: the moment a screen connects, the server first pushes a **snapshot of all currently-open alerts** (the first paint fills immediately), then seamlessly switches to the increment stream. In code, that is stitching the SSE stream as "snapshot ++ live stream" (see `Flux.concat(snapshot, live)` in the code panel).

One line to close: **a dashboard wants real-time alerts, so let the server push with SSE; on scale-out use broadcast or per-instance groups so every screen receives; add reconnection and a first-paint snapshot, and the screen neither misses nor blanks.** With that, the chain finally closes — from Python turning data into anomaly signals (sc34) to those signals landing in real time on the screen in front of ops (sc35).
