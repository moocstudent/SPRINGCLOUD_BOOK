## Config that lives outside the jar

Dozens of services, each in dev / test / prod, means hundreds of config files. If a database password, a rate-limit threshold, or a feature flag lives in each service's own `application.yml`, changing one means editing a file, rebuilding the jar, and redeploying — minutes of work and a full release's risk for a one-line change. A **config server** pulls this out: services fetch their configuration from a central source at startup instead of baking it in.

Two implementations dominate. **Spring Cloud Config** backs its store with **Git** — every change is a commit, so history, diffs and rollback come for free. **Nacos Config** stores config in its own server with a web UI and pushes changes over a long poll — faster to edit, and integrated with Nacos discovery. A client points at either through configuration imported before the app context builds:

```yaml
spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://config:8888"
  cloud:
    config:
      profile: prod
      label: main          # the Git branch/tag
```

The server resolves `order-service` + `prod` + `main` to a file at a specific commit; the **label** lets you pin every instance to one Git tag and know exactly what they loaded.

## Refresh without a restart

Fetching config at startup is only half the value. The other half is **dynamic refresh**: change a value and have running instances pick it up without a restart. Spring implements this with **`@RefreshScope`**. A bean marked with it is re-created the next time it is used after a refresh event, so it reads the new values:

```java
@RefreshScope
@Component
@ConfigurationProperties(prefix = "orders")
public class OrderProps {
    private int maxPerSecond = 100;   // rebinds after a refresh
    // getters / setters
}
```

One instance refreshes when you POST to its Actuator endpoint `/actuator/refresh`. But you have thirty instances, and hitting each by hand is absurd. **Spring Cloud Bus** solves this: it links every instance over a message broker (RabbitMQ or Kafka), so a single POST to `/actuator/busrefresh` on any instance **broadcasts** a refresh event to all. With Nacos, the push happens automatically on save. The sequence: change the source, broadcast, each `@RefreshScope` bean rebuilds, new value live — no restart, no dropped connection.

## The danger window: refresh is not atomic

This is the reef this chapter warns you about. A broadcast refresh is **not atomic across instances**. The event reaches thirty instances over a broker, each rebuilds its beans, and all of that takes time — typically hundreds of milliseconds to a few seconds end to end. During that window, **some instances run the new config and some the old.**

@fig sc12-refresh

For an independent value — a log level, a cache TTL — a few seconds of mixed state is harmless. The danger appears when **two parties must agree**. Suppose you bump a message-format version, or flip a flag that changes a producer/consumer contract. For those seconds, a v2 producer's message may reach a v1 consumer that cannot parse it. The symptom is maddening: a burst of errors that begins at the config push and vanishes seconds later, leaving nothing reproducible in the logs.

The bench makes this window visible. Push a config change to a fleet and watch instances flip one at a time — a bar of green catching up to the change, and a counter of requests caught in the mixed-state gap. Widen the fleet or slow the broker and the window grows.

| Contributor to the window | Typical effect |
|--------------------------|----------------|
| Broker propagation delay | tens to hundreds of ms |
| Bean rebuild + reconnect | ms; seconds if pools reinitialise |
| Fleet size | more instances, longer tail |
| A slow / paused instance (GC) | may miss the event entirely |

## Canary, version, roll back

You cannot make refresh atomic, so you design around it. **Version** every config change (a Git commit, or a `version` key) so producers and consumers negotiate, not assume. Make changes **backward-compatible** for one release — the consumer understands both old and new before the producer emits new — so mixed state is safe by construction. **Canary** the config: push to one instance or namespace, watch, then widen. And keep **rollback** one action away: with Git-backed config, revert the commit and re-broadcast — the same window applies coming back, so roll back to a version both sides tolerate.

1. On the bench, push a config change to 30 instances and record the mixed-state window; grow the fleet to 100 and slow the broker, and describe how it changes.
2. Mark a bean `@RefreshScope`, expose `/actuator/busrefresh`, and trace the full sequence of events from your POST to the value going live on a peer instance.
3. Design a two-release plan to change a message format from v1 to v2 such that no mixed-state window can produce an unparseable message (hint: teach the consumer to read both first).
4. For a Git-backed config server, write the steps to roll back a bad change, and explain why the rollback has the same danger window as the push.
