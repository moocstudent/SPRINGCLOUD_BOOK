## Two payloads

When your OrderService calls InventoryService with OpenFeign (CM1), the message travels as JSON over HTTP — the microservice default. It is a good default: JSON is human-readable, every language and tool speaks it, you can inspect it with curl or a browser, and HTTP caching works on top of it. But JSON is also verbose: every message repeats its field names as text, wraps values in quotes, and spends bytes on braces and commas.

gRPC makes a different trade. It serializes messages with **Protobuf**, a binary format defined by a `.proto` schema. On the wire, Protobuf sends a small field *number* and a variable-length value — not the field name — so the same object that is ~280 bytes of JSON is often ~60–70 bytes of Protobuf, roughly a quarter of the size. The bench above computes this for a message of the size you choose; the ratio holds, and it matters most exactly where it is easiest to ignore: internal, high-frequency, service-to-service calls, where bandwidth and the CPU spent parsing text add up fast.

## Two transports

The payload is only half the story; the transport is the other half. REST is usually spoken over **HTTP/1.1**, where a connection carries one request at a time — concurrent calls need multiple connections or queue behind each other (head-of-line blocking). gRPC mandates **HTTP/2**, which multiplexes many concurrent streams over a single long-lived connection with binary framing, so a hundred in-flight calls share one connection without blocking each other. For a service that makes thousands of calls a second, that difference is lower latency and far fewer sockets. (REST can run over HTTP/2 too, but rarely gets the streaming and framing benefits gRPC is built around.)

## Contract and streaming

gRPC's third advantage is the **contract**. The `.proto` file is the single source of truth, and `protoc` generates typed client and server stubs from it in every language you need. A field you renamed or a type you changed breaks the build, not production. REST's contract is looser — OpenAPI describes it, but nothing forces client and server to agree, and drift is caught at runtime, if at all.

gRPC also has **streaming** built in, in four shapes:

| Mode | Shape |
|---|---|
| Unary | one request, one response (like REST) |
| Server streaming | one request, a stream of responses |
| Client streaming | a stream of requests, one response |
| Bidirectional | both stream at once, over one connection |

REST is request-response only; to stream you reach for Server-Sent Events or WebSockets, bolted on rather than native.

## gRPC inside, REST at the edge

None of this makes gRPC a universal winner — its strengths come with real costs:

| | gRPC | REST |
|---|---|---|
| Payload | Protobuf binary, compact | JSON text, verbose |
| Transport | HTTP/2, multiplexed | HTTP/1.1 typical |
| Contract | `.proto`, typed codegen | OpenAPI, loose |
| Streaming | native, four modes | request-response (SSE/WS) |
| Browser | needs grpc-web proxy | any client, direct |
| Debugging | binary, needs tooling | curl-readable |
| Caching | none | HTTP caching |

The healthy rule of thumb is to layer them by audience. Between your own services — internal, high-frequency, strong contracts, sometimes streaming — gRPC pays for itself. At the edge, facing browsers, third parties and the public internet, where readability, ubiquity and caching matter more than a few bytes, REST is the right tool. Many real systems run both: gRPC in the mesh, and an API gateway that translates external REST calls into internal gRPC. Because that boundary is the gateway (Module IV), you can choose per layer without forcing one protocol on the whole system.

## Exercises

1. Define a `.proto` for an order, generate the stubs, and call the service two ways — once with a gRPC client, once with the REST equivalent. Capture both requests with Wireshark and compare the bytes on the wire.
2. Take one message, serialize it as JSON and as Protobuf, measure the size difference, and multiply by your real call rate to see the daily bandwidth gap.
3. Implement a server-streaming RPC in gRPC (e.g. order-status updates); then implement the same feature over REST with Server-Sent Events, and note what each costs you.
4. Put your gRPC service behind an API gateway that exposes REST to the outside; confirm a browser can call the REST edge while services call the gRPC core.
