## 一个假装是本地方法的网络调用

OpenFeign 让你把一次远程 HTTP 调用声明成一个 Java 接口:打上 `@FeignClient`,用你写 Controller 时一模一样的 Spring MVC 注解描述每个端点,Feign 就在背后生成一个代理,替你序列化请求、通过负载均衡挑一个实例、发出去、再把响应反序列化回来。

```java
@FeignClient(name = "inventory")
public interface InventoryClient {

    @GetMapping("/api/stock/{sku}")
    StockLevel getStock(@PathVariable("sku") String sku);

    @PostMapping("/api/reserve")
    ReserveResult reserve(@RequestBody ReserveCommand cmd);
}
```

调用 `inventoryClient.getStock("A-91")`,读起来和调一个本地方法没有任何区别。这正是它的卖点,也正是它的陷阱。本地方法要么纳秒级返回、要么抛异常,它绝不会「卡在那里」;而这一行要穿过一个 TCP 连接、一个负载均衡器、一段网络、另一个 JVM 的线程池、一个数据库——其中任何一环都可能不是快而是慢、不是在而是不在。这行语法瞒过了一件 CPU 瞒不过的事实:它可能阻塞三十秒。

## 两个必须你亲手设的超时

Feign 底层的 HTTP 客户端,如果你什么都不说,会等得比任何用户的耐心都久。你必须设两个独立的上限,它们各自防的是不同的故障。

| 超时 | 防的是 | 什么时候触发 | 合理起点 |
|---|---|---|---|
| `connectTimeout` | 建立 TCP 连接 | 实例已死、主机不可达、网络断了 | 500–1000 毫秒 |
| `readTimeout` | 连上之后等响应 | 下游收了请求但很慢——GC、锁竞争、慢查询 | 800–2000 毫秒 |

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          default:            # 对所有客户端生效
            connectTimeout: 1000
            readTimeout: 2000
          inventory:          # 按 @FeignClient 的 name 单独覆盖
            connectTimeout: 500
            readTimeout: 800
```

把 `readTimeout` 留在它那个慷慨的默认值上,故障模式是这样的:你的服务跑在 Tomcat 上,200 个工作线程。库存服务劣化了,响应从 40 毫秒变成 8 秒。现在每个请求都会把一个 Tomcat 线程占住 8 秒。每秒 100 个请求,两秒内 200 个线程就全被占满,接受队列排满,你的服务开始拒绝**一切**请求——包括那些根本不碰库存的健康端点。一个慢下游,耗尽了你的线程池,把你一起拖下水。一个收紧的 `readTimeout`,能把这种慢性失血变成快速的、可计数的失败,让你有机会去响应它。

## 重试风暴

再看更隐蔽的危险。OpenFeign 默认带的是 `Retryer.NEVER_RETRY`,但只要你像无数教程教你的那样塞进一个 `Retryer.Default` bean,你就得到了每次调用最多 5 次尝试,而负载均衡器还能在实例之间再叠一层自己的重试。重试感觉上像是韧性。面对一个**正在挣扎**的下游,它恰恰相反。

@fig sc7-retry

设想一条两跳的链路,边缘 → 订单 → 库存,每一跳最多重试 3 次。一个原始请求到库存那里可能变成 3 × 3 = 9 个请求。库存健康时这看不出来;库存已经过载、开始超时时,每一次超时都触发一次重试,于是每秒 1000 个真实请求会以最多每秒 9000 个的量到达。多出来的负载让它更慢,更多调用超时,又触发更多重试——一个正反馈回路,把一次本可恢复的抖动,变成一个再也起不来的下游,因为它自己的调用方不肯停手。这就是重试风暴,一次五秒的小故障就是这样变成半小时宕机的。

## 安全的重试:退避、抖动、幂等、熔断

重试本身没错,无条件的重试才错。四条规则让它安全。

- **只重试幂等调用。** `GET` 是安全的。一个裸的 `POST`——扣一次款、发一次货——绝不能盲目重试,重试就等于重复扣款。要重试它,先把这个写操作设计成幂等(一个幂等键)。
- **尝试次数压低,并做指数退避。** 两次,不是五次。等 100 毫秒,再等 400 毫秒——给下游喘息的空间,而不是往死里捶。
- **加抖动。** 没有随机成分,所有失败的调用方会在同一瞬间重试,整群请求以同步的波次重新砸过来。抖动把它们摊开。
- **前面放一个熔断器。** 下游明显已经死了,熔断器(见 sc9)会把重试整个停掉——对着一具尸体重试没有意义。

在治理台上,给下游注入延迟,打开重试,看着下游收到的请求数翻着番涨、成功率往下掉;再加上退避和熔断,看风暴怎么平息下去。

## 练习

1. 给你某个服务里的一个 `@FeignClient` 加上 `connectTimeout` 和 `readTimeout`,然后把它指向一个「接受连接但永不回复」的端口(`nc -l`),确认是哪个超时触发了。
2. 在治理台上,把下游延迟设到刚好略高于 `readTimeout`,分别记录关闭重试和打开重试时调用方线程池的占用,注意池在哪里饱和。
3. 为你一条真实的调用链算一算最坏放大倍数:把每一跳的最大尝试次数相乘。有没有哪个下游正面对着两位数的倍率?
4. 挑一个系统里非幂等的 `POST`,写下盲目重试会造成什么后果,再勾勒出那个能让重试变安全的幂等键。
