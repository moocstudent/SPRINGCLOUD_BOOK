## 单体的三个真痛点,和三个假痛点

动手拆之前,先诚实分辨:你真正的痛到底是哪个。单体有三个**真**痛点,而且它们无一例外都是组织层面的。**同一趟发布火车:** 四十个工程师合入同一个可部署单元,于是最冒险的那个改动决定了所有人的节奏,一个坏提交能把整条队列堵死。**绑定扩容:** 某一个接口吃 CPU,你却只能把整个进程一起扩,为了拿到 CPU 而付出你并不需要的内存。**全员共用一套技术栈:** 那个特别想换语言、换运行时、换某个库的团队做不到,因为一切都链接进同一个制品里。

注意这三者的共同点:它们说的是**团队和交付**,不是代码跑得慢。再看三个**假**痛点。「代码库太大了」——大不是问题,乱才是;一个模块化良好的百万行单体,比十二个互相喋喋不休的服务好维护得多。「单体扩不动」——一个无状态单体挂在负载均衡后面,能水平扩到极大的流量,大多数系统一辈子都用不完。「微服务更快」——单次请求几乎总是**更慢**,因为你把进程内调用换成了网络调用。

一句话讲完这笔交易:**微服务几乎所有的好处都是组织性的,几乎所有的代价都是技术性的——一笔你在生产环境里天天要还的账。**

## 分布式税:可用率、延迟、复杂度三张账单

这笔税有三个明细项。**可用率:** 曾经的一次方法调用,现在要穿过一张会丢包、会延迟、会分区的网络,于是一个请求碰到的服务越多,它失败的方式也越多(公式见下)。**延迟叠加:** 每一跳都要加上序列化、一个网络往返、以及排队等待;五个串行跳,每跳 5 毫秒,还没干正事就先花掉 25 毫秒纯开销,而**尾部**叠加得比平均值更狠——一跳变慢就把整个请求的 P99 拖下水。**运维复杂度:** 为了把单体白送给你的可靠性重新挣回来,你现在得跑服务发现、客户端负载均衡、熔断器、分布式追踪、配置中心和消息中间件。后面二十来章的存在,唯一目的就是偿还这一个明细项。

这里也藏着一个好处——**更小的故障域。** 单体里一处内存泄漏就能把一切拖垮;拆得好,推荐服务里的一个 bug 不该殃及下单。但这个好处是**有条件的**:如果下单串行地硬依赖推荐,那爆炸半径又变回整条链路了。更小的故障域,要靠第三模块的舱壁和熔断才能真正挣到。

## 组合可用率:0.999 的十次方是多少

把一个请求建模成一条必须串行调用 N 个服务的链,每个服务各自独立地有 99.9% 的时间在线。请求只有在 **N 个全部在线**时才成功,所以组合可用率就是 0.999 自乘 N 次:

| 链上的服务数(各 99.9%) | 组合可用率 | 年度不可用时长 |
| --- | --- | --- |
| 1 | 99.90% | 约 8.8 小时 |
| 3 | 99.70% | 约 26 小时 |
| 5 | 99.50% | 约 44 小时 |
| 10 | 99.00% | 约 3.7 天 |
| 20 | 98.02% | 约 7.2 天 |

N = 10 时正好落在 0.999 的 10 次方 ≈ 99.0%:你一个 bug 都没写,可用率却掉了十倍,年度不可用从九小时涨到将近四天。**在上面的治理台里把 N 拉到 10,看那条组合可用率曲线往下沉**,再把重试和熔断开关打开,看它爬回来——因为一个降级(fallback)会把**硬**依赖变成**软**依赖,让那个服务从成功率的计算里彻底退出。

这是一个故意取悲观的模型:独立失败、硬串行依赖、每个服务都关键。真实系统会用缓存、异步调用、降级把它软化——而这恰恰是本书剩下部分要做的事。重点不是「99.0% 是你的宿命」,而是「99.0% 是你的**起跑线**」,比它更好的一切都得你亲手造出来。

```java
// 单体:进程内调用——永不超时、不丢包、不分区
BigDecimal price = pricingService.quote(cart);

// 微服务:一模一样的一行,现在是一次网络调用——
// 它会超时、会返回 503、会一直挂到调用方线程被耗尽
BigDecimal price = pricingClient.quote(cart);   // OpenFeign,走 HTTP
```

## 什么时候该留在单体里

三个具体信号在说:**别拆——至少现在别拆。**

1. **团队太小。** 八个工程师却要造十五个服务,意味着没人能端到端地拥有一个服务,而组织上的回报——多个团队各自独立发布——根本不存在。你会付掉全部技术税,却没人来领那份奖励。经验法则:大致要「一个服务配一个团队」。
2. **领域边界不清或还在剧烈变化。** 如果业务每周还在变形,你就还不知道缝在哪;而切错缝是本书里最贵的错误——把一个职责从这个服务边界挪到那个,是跨仓库、跨团队、跨部署的重构,不是改个名。
3. **数据强耦合。** 如果两坨逻辑总在同一个事务里读写彼此的数据,把它们拆开就等于让每一次这样的操作都变成一个分布式事务——拿你看得懂的 `@Transactional`,换一个你会在凌晨三点调试的 Saga。

成熟的默认做法是**先做模块化单体(modular monolith)**:在**代码里**强制模块边界(独立的包、禁止跨模块读表),把缝到底在哪验证清楚,只有当某个模块确实需要独立部署、独立扩容、或归属另一个团队时,才把它抽成服务。微服务应该是你**挣来**的一次抽取,而不是一开始就摆出的形状。

## 练习

1. 挑一个你熟悉的系统里的真实请求,数一数它往下有几跳。假设每个依赖 99.9% 可用,算出组合可用率;再找出那个「一挂最要命」的单跳,描述一个降级会把数字改成什么样。
2. 在本地起两个 Spring Boot 服务,让 A 通过 HTTP 调 B,然后杀掉 B。分别测量:不设超时时 A 的调用方是什么体验,以及设了 500 毫秒读取超时后又是什么体验——记下两种情况下一个线程各卡多久。
3. 就你当前的系统,写下三个「别拆」信号里哪几个成立。如果你仍然要拆,给每个拟议中的服务点名一个具体的负责团队。
4. 在治理台里把每个服务设成 99.95%,找出组合可用率第一次跌破 99.9% 时的 N。向同事解释为什么「就多加一个服务」从来都不是免费的。
