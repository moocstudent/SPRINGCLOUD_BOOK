## 配置会漂移

GW3 讲了一次配置变更怎么在集群里刷新,以及传播时那段短暂的「新旧混跑」窗口。那是个瞬时问题,几秒就过去了。这一章讲的是它那个缓慢、慢性的表亲:**配置漂移**——实例实际跑着的配置,一点点地和你声明的配置分了家,而且就那么一直分着。

漂移有三个经典来源。第一是**手动救火**:凌晨三点,出事了,工程师 SSH 上机器(或者点了个 Actuator 端点、改了个环境变量),改一个值先止血。事故结束,大家回去睡觉,而这个改动再也没被同步回配置仓库——这台实例现在跑着一份任何版本控制系统都不知道的配置。第二是**漏刷**:一次变更推了,但只到了一部分实例(网络抖一下、某个 Pod 正在重启),于是整个集群不一致了——是永久的,不只是刷新窗口那几秒。第三是**环境分家**:一个修复上了 prod 却没上 staging,于是 staging 悄悄地不再是 prod 的忠实副本,再也复现不了 prod 的 bug。

## 声明态 vs 运行态:那道无声的缝

想清楚漂移的干净办法,是把它看成两个状态。**声明态**是你的真相来源——一个 Git 仓库、一个配置中心、一组清单——说配置「应该」是什么样。**运行态**是那些进程此刻「实际」在用的。在一个纪律完美的系统里,这两者完全一致;而漂移,就是它们之间的任何缝隙。

漂移之所以危险,在于这道缝是无声的。它裂开时,什么都不报错。一切看起来都正常——直到某台实例因为一个谁调高了又忘了的限额、或者一个救火时被关掉又没再打开的安全检查,而和它的兄弟们行为不同;或者你直接从 Git 拉起一套全新环境,它跑得跟生产完全两样,然后你花一整天才发现:生产环境其实从来就不是 Git 描述的那样。漂移不会主动报到;是你去找它的,而且通常是在查别的问题的时候。

## 检测:配置指纹与审计

看不见的东西修不了,所以第一步是让漂移可见。窍门是一个**配置指纹**:让每个实例算一个它有效配置的哈希——是它真正解析出来的那些值,经过默认值、文件、环境变量、配置中心层层叠加之后的结果——并把它暴露出来(一个小小的 Actuator 端点)。如果集群同步,每台报的哈希都一样;一旦有一台不同,你就找到了一台漂移的实例,而不必手工去比对成千上万个键。

**定期审计**把它变成一个流程:按计划收集每台实例的指纹,和从 Git 推导出的期望值对比,任何不一致就报警。这确实能发现漂移——但只有审计间隔那么快,而且发现不等于修复。总得有人去排查、去纠正,所以在审计抓到和人工解决之间,永远有一批在途的漂移。

## 纠偏:GitOps 与不可变基础设施

检测告诉你漂移发生了;纠偏让它无法长期存在。声明式的 **GitOps** 答案是一个控制器(Argo CD、Flux),它持续把运行态和 Git 声明的状态对比、把两者往一块拽——而且关键是,自动回退漂移。打开 `selfHeal`,一次对线上配置的手改会在一个同步周期内被撤销:Git 是唯一真相,不在 Git 里的东西不被允许存活。漂移还能发生,但活不长。

最强的保证是用**不可变基础设施**从根上消除可能:把配置烤进一个不可变的镜像,禁止运行时修改,要改什么就部署一个新镜像。如果没有东西能被就地编辑,就没有东西能漂移。几种做法和它们的代价:

| 做法 | 干了什么 | 代价 |
|---|---|---|
| 无检测 | 什么都不做;漂移无声累积 | 无法复现的事故 |
| 定期审计 | 按计划指纹+对比,报警 | 能发现,但要人工修;受间隔限制 |
| GitOps(selfHeal) | 持续对帐,自动回退到 Git | 要运行一个控制器;少了随手改的自由 |
| 不可变基础设施 | 配置烤进镜像,禁止运行时改 | 漂移不可能;也没了就地快改 |

它们共同的主线是一条纪律:指定一个唯一真相,让其它一切都向它看齐。治理台把回报摆出来——当你从「无检测」走到「审计」再走到「GitOps」,漂移的实例数和配置事故都在下降,发现时延从「永不」塌缩到几分钟。

## 练习

1. 加一个 `/actuator/confighash` 端点,把你的特性开关和限额哈希一下;部署三个副本,确认三个报的哈希一致。
2. 手动改掉其中一个副本的值(通过环境变量或 Actuator),再看哈希;看着一个分叉出去——你刚刚检测到了漂移。
3. 写出审计循环:把每个副本的哈希和配置中心的值对比,打印出漂移的那些。
4. 把同一份配置放到 Argo CD 下、开 `selfHeal: true`;手改线上值,看着它被回退;然后讨论一下什么时候你想要、什么时候你不想要这种行为。
