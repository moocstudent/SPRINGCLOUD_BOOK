## 一个进程里的两件工具

Nacos 在中文 Spring Cloud 圈里几乎是默认选择,它相对 Eureka 的第一个优势是范围:它把**注册中心和配置中心装进了同一个服务端**。一个集群同时回答「订单服务在哪」和「它当前的数据库 URL 和功能开关是什么」——而且关键在于,它能把配置变更推给运行中的实例,不用重启。把两者合一很方便,却逼出一个 Eureka 从来不必回答的问题,因为服务发现和配置想要的是*相反*的一致性保证。Nacos 真正的课,是它如何回答这个问题。

## 命名空间、分组、DataId

先说组织。一家真实公司在好几个环境里跑着几百个服务,Nacos 用三个维度把它们隔开:

| 层级 | 隔离什么 | 例子 |
|---|---|---|
| 命名空间 Namespace | 环境 | `dev`、`test`、`prod`(各是一个独立 UUID) |
| 分组 Group | 业务线 / 集群 | `ORDER_GROUP`、`PAY_GROUP` |
| DataId | 单个配置文件 | `order-service-prod.yaml` |

命名空间是承重的那一层:一个指向 `prod` 命名空间的生产客户端,物理上就看不到、读不了 `dev` 的配置,正是这一点挡住了一个测试改动流到生产实例上。这里搞错,环境之间就会互相渗漏。

## Distro 与 Raft:两种一致性

现在说核心。Nacos **同时带着两套一致性协议**,按数据类型把它们分流到其中一套。

- **Distro(AP)** 管*临时*实例——普通的、会发心跳的服务。它是一套没有 leader 的 gossip 式复制协议:每个节点拥有一部分注册数据、再同步给其他节点。分区时每个节点都继续提供读取、接受注册。
- **Raft(CP)** 管*持久*实例和*全部配置*。它是一套基于 leader 的多数派协议:一次写入必须得到多数节点确认才能提交。失去多数派,写入就停。

| | Distro(AP) | Raft(CP) |
|---|---|---|
| 用于 | 临时实例(发现) | 持久实例 + 配置 |
| 一次写入需要 | 任一节点(异步复制) | 多数派 quorum |
| 分区时 | 各方都可写,可能分叉 | 少数派拒绝写入 |
| 实例生命周期 | 约 5s 心跳,15s 判不健康,30s 移除 | 跨节点重启存活 |

## 为什么发现选 AP、配置选 CP

这是整章的要害,而且它一点都不随意。**发现能容忍过时。** 如果你的实例清单比现实慢了几秒,你可能会调到一个刚离开的实例——被重试或熔断器兜住——或者短暂地看不到一个刚上线的实例。都活得下去。你活不下去的,是*注册中心本身*在分区时哑掉、把每个调用方都冻住,所以发现选可用性。

**配置不能容忍分叉。** 推一个新的数据库连接串,或翻一个功能开关,如果配置由一套 AP 协议来提供,你的机群就可能一半读到新值、一半读到旧值。于是一半实例往新库写、一半往旧库写;一半执行新业务规则、一半不执行。这不是过时,是*分裂*——脏数据加上任何监控都解释不了的行为。宁可让一个少数派分区拒绝新配置,也不能让机群悄悄分叉,所以配置选一致性。

## 分区时,亲手切一次

治理台把这件事变具体:它把一个 Nacos 集群切成多数派和少数派两边,让你把一份数据在 AP 和 CP 之间切换。

- **AP(Distro):** 两边都继续提供发现、接受注册。分裂期间它们的视图逐渐分叉,链路恢复后靠 gossip 重新收敛。没人被拒绝,一些读取是过时的。
- **CP(Raft):** 多数派一边保住 leader、接受配置写入;少数派一边组不成 quorum,于是拒绝写入、只提供最后一次已提交的值。不会脑裂,但少数派失去了写可用性。

你用一个开关为每次注册选定协议:

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: prod          # 环境隔离
        group: ORDER_GROUP
        ephemeral: true          # true -> Distro/AP(默认);false -> Raft/CP
```

把 `ephemeral: false` 翻过去,这个服务就通过 Raft 注册成一个持久的 CP 实例——适合一块固定的基础设施,却不适合一个会自动扩缩的无状态 Pod。

## 练习

1. 起一个单机 Nacos,建 `dev` 和 `prod` 两个命名空间,把同一个服务分别注册进去。确认一个绑定到 `prod` 的客户端看不到 `dev` 的实例。
2. 用 `ephemeral: true` 注册一个服务、用 `ephemeral: false` 注册另一个;把两个都杀掉,看哪个在心跳超时后消失、哪个仍然留着。
3. 在 Nacos 配置里放一个 `feature.enabled` 值,用 `@RefreshScope` 接上,在控制台改它——确认运行中的应用不重启就拿到了新值。
4. 跑一个 3 节点 Nacos 集群,停掉 2 个节点打破 quorum,再尝试发布一次配置变更。观察写入被拒绝,然后解释为什么这对配置是*正确*行为、对发现却是错的。
