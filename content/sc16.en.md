## When one log stops being enough

In a monolith, "checkout is slow" is a five-minute problem: grep one file, find the request, read the stack top to bottom. Split that checkout across a gateway, order, inventory, promotion, payment and notification service, and the same request writes six logs on six machines, each with its own clock. Nothing links them. You are left guessing which hop was slow — and guessing is how a twenty-minute incident becomes a three-hour one.

Distributed tracing rebuilds the link, and the idea is small. Every request that enters the system is stamped with one **traceId** — a 128-bit value, sixteen bytes, written as thirty-two hex characters, globally unique. Every unit of work under that request — a service handling it, an outbound HTTP call, a database query — opens a **span**: a record of a start time, an end time, the service that owns it, and a pointer to its parent span. A trace is therefore a tree of spans sharing one traceId, and because each span carries a parent, the tree reconstructs exactly who called whom.

### Context has to ride along

The traceId is useless if it stops at the first service. It must travel on every hop, and it travels in HTTP headers. The W3C standard header is `traceparent`, worth knowing byte for byte because one day you will read it in a packet capture:

| Field | Example | Meaning |
|---|---|---|
| version | `00` | format version |
| trace-id | `4bf92f3577b34da6a3ce929d0e0e4736` | 16 bytes — the whole request |
| parent-id | `00f067aa0ba902b7` | 8 bytes — the calling span |
| trace-flags | `01` | sampled (01) or not (00) |

The older B3 format (from Zipkin/Brave) splits the same information across `X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentSpanId` and `X-B3-Sampled`. Whichever you pick, both ends of every call must agree, or the trace snaps in half.

### The waterfall pins the slow hop

Once the spans are collected, draw them on one time axis — each span a horizontal bar from its start to its end, children nested under parents. That is a **waterfall**, and it is the whole payoff. A request that took 900 ms is no longer a mystery: you see 40 ms in the gateway, 30 ms in order, 20 ms in inventory, and one 800 ms bar where payment called the bank. The slow hop is not argued about; it is pointed at. The bench renders exactly this — a real multi-service call as an interactive waterfall — so drag the spans and watch the longest bar announce itself.

### Spring Boot 3: Micrometer Tracing

On Spring Boot 3 the instrumentation is **Micrometer Tracing**, which replaced Spring Cloud Sleuth (Sleuth never made the jump to Boot 3). You add a bridge to a tracer — `micrometer-tracing-bridge-brave` (Brave) or `-bridge-otel` (OpenTelemetry) — plus a reporter such as `zipkin-reporter-brave` to ship spans, and `spring-boot-starter-actuator`, which owns the tracing autoconfiguration. Backends are interchangeable: Zipkin for a quick start, Grafana Tempo for cheap object-store retention, or an OTLP collector that fans out to anything.

```yaml
management:
  tracing:
    sampling:
      probability: 0.10                 # keep 10% of traces
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans
logging:
  pattern:
    level: "%5p [%X{traceId:-},%X{spanId:-}]"   # traceId into every log line
```

That last line matters for the next chapter: Micrometer puts the traceId into the logging MDC, so the same id that draws the waterfall also tags every log.

### Sampling is a bill you pay per trace

`probability: 0.10` is the load-bearing number. Tracing every request at 10,000 req/s means 10,000 traces per second to serialise, transmit and store — the storage and network cost is real, and 1–3% is common in production. But sampling is a gamble. Head-based sampling decides at the entry point, before it knows the request will fail or run slow, so the one trace you desperately want is the one most likely dropped. Tail-based sampling (in an OTel collector) buffers spans and keeps the interesting ones — all errors, everything over 500 ms — at the price of a stateful collector holding spans in memory. The failure mode to fear is silent: a thread-pool handoff, an `@Async` boundary or a message queue that does not propagate the header, and the trace simply ends there, leaving a stump instead of a tree.

## Exercises

1. Add `micrometer-tracing-bridge-brave` + `zipkin-reporter-brave` to two services (a caller and a callee), run Zipkin in Docker (`openzipkin/zipkin`), fire one request through both, and find the single trace in the Zipkin UI. Confirm the two services share one traceId and the callee's span is a child of the caller's.
2. Set `management.tracing.sampling.probability` to `1.0`, then `0.1`, then `0.0`. At each, send 20 requests and count how many traces appear in Zipkin. Explain the counts.
3. Add an `@Async` method or a raw `new Thread(...)` inside the caller and watch the trace break at that boundary. Then restore context propagation (a `taskDecorator`) and confirm the child span reappears.
4. In the bench, load the waterfall, find the longest span, and write one sentence naming which hop you would optimise first and why.
