## 方框落到机器上那一刻

架构图上,订单服务是一个干净的矩形。可到了生产环境,它是一个 JVM 进程:必须落在某一台具体的机器上,和邻居们共享这台机器的 CPU 与内存,并在这台机器重启的一瞬间跟着一起消失。「哪个服务放哪台机器」听起来是运维的杂活,实际上它精确地决定了一台硬件出故障时你会损失什么——所以它值得单开一章。

## 容器化:一个不可变镜像

第一步,别再发布源码,改成发布镜像。Docker 镜像把服务的 jar 连同它精确的 JRE、时区数据、本地库一起打包,于是通过 CI 的那个产物,和跑在生产上的那个产物,是逐字节相同的。「在我机器上能跑」在这里就死了,因为现在只剩一台「机器」——镜像本身。用两阶段构建,让臃肿的 JDK 和 Maven 缓存永远进不了生产,运行层只带一个 JRE。

```dockerfile
# ---- 构建阶段:完整 JDK + Maven ----
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q -DskipTests package

# ---- 运行阶段:仅 JRE ----
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/order-service.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75.0","-jar","app.jar"]
```

这一拆通常能把一个 460 MB 的镜像降到约 190 MB;镜像越小,每一次扩容拉取就越快——一旦自动扩容开始每小时把它拉上四十次,这点差别就没听起来那么小了。

## 放置就是装箱

现在你手里有二十个服务(每个都是一个镜像)和八台机器。放置要回答的就是:哪个 Pod 放哪儿?Kubernetes 把它当成装箱问题来解。每个 Pod 声明自己的 `requests`(CPU 和内存)——这是调度器要从节点可分配容量里扣掉的预留量。一台可分配 4 vCPU、8 GiB 的节点,装每个 request 为 500m CPU、1 GiB 的 Pod,能装下八个;第九个只能 `Pending`,因为没有任何一台节点还有空位。

`requests` 和 `limits` 是两个不同的旋钮,而且两个都会咬人。`requests` 是调度器事先预留的量;`limits` 是内核在运行时强制执行的上限。requests 设太低,你就超售了节点——那些在测试环境安安静静的 Pod 在高峰一起醒来,争抢真实内存,内核就把下一个申请内存的 Pod OOMKill 掉。设太高,你就把钱烧在闲置的预留上,本可以塞十二个的地方只塞了四个。

## 反亲和:别把鸡蛋都放一个篮子

只靠装箱,调度器会兴高采烈地把订单服务的三个副本全堆到那台空闲内存最多的节点上。高效,但要命:这台节点一重启,三个副本一起消失,明明有三副本,服务却挂了。`podAntiAffinity` 禁止这种堆叠,按 `topologyKey` 把副本分散到不同主机、不同机架、不同可用区。亲和则是它的镜像——把一个服务和它频繁访问的缓存放在同一节点上,省掉一跳网络。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  selector:
    matchLabels: { app: order-service }
  template:
    metadata:
      labels: { app: order-service }
    spec:
      containers:
        - name: order
          image: registry.example.com/order-service:1.8.0
          resources:
            requests: { cpu: "500m", memory: "1Gi" }
            limits:   { cpu: "1",    memory: "1Gi" }
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels: { app: order-service }
              topologyKey: kubernetes.io/hostname
```

`requiredDuringScheduling` 是硬规则——任何两个订单 Pod 都不许共享一台主机,哪怕因此让第三个 Pod 因为凑不出节点而一直 `Pending`。`preferredDuringScheduling` 是软愿望,能满足就满足。对那些「绝对不能一起死」的服务,选硬的那种。

## 爆炸半径

下面这一课,盖过前面所有内容:一台机器死的时候,哪些东西跟着一起死。为了省一台机器,把订单服务和支付服务放在同一节点上,一次重启就把两个都带走——整条下单链路没了,而其他每一台机器都还是绿的。治理台把这件事变得可触摸:把服务拖到机器上、设好反亲和、随机干掉一台机器,看哪些服务变红。

| 订单 + 支付的放置(各 3 副本) | 用几台节点 | 死一台节点 | 下单还能用吗? |
|---|---|---|---|
| 所有副本挤在一台节点 | 1 | 损失 100% | 不能 |
| 两个服务、无反亲和、3 节点 | 3 | 各损失约 1/3 | 降级 |
| 每个服务按主机反亲和、分散到 3 节点 | 3 | 各损失 1 个副本 | 能 |
| 跨 3 个可用区反亲和 | 3+ | 损失一整个可用区 | 能——扛得住一次机房级故障 |

密度省钱,分散保命。治理台让你亲手感受那个临界点:省下的那一台机器,从哪一刻起变成了一次挂掉的下单。

## 练习

1. 给你自己的某个服务写一个多阶段 Dockerfile,再用 `docker images` 对比单阶段 JDK 构建的体积——目标是至少砍掉一半。
2. 取一台可分配 4 vCPU / 8 GiB 的节点和一批 request 为 500m / 1 GiB 的 Pod。算出能装几个;再把某个 Pod 的 CPU request 降到 250m,重新推导装箱结果。是 CPU 还是内存先成为瓶颈?
3. 在一个 2 节点集群、3 副本的 Deployment 上,按 `topologyKey: kubernetes.io/hostname` 加一条 `requiredDuringScheduling` 反亲和,并解释为什么恰好有一个 Pod 停在 `Pending`。
4. 在治理台上,把订单和支付放到同一台机器上,干掉它,记录爆炸半径。再用「每服务跨三台机器反亲和」重跑一次,对比下单的表现。
