## When a box lands on a machine

On the architecture diagram the order service is a clean rectangle. In production it is a JVM process that must live on a specific machine, share that machine's CPU and memory with its neighbours, and vanish the instant that machine reboots. Which service sits on which machine reads like a boring ops chore. It is really the decision that sets exactly what you lose when hardware fails — so it earns a chapter.

## Containerisation: one immutable image

The first move is to stop shipping source and start shipping images. A Docker image bundles the service jar with its exact JRE, timezone data and native libraries, so the artifact that passed CI is bit-for-bit the artifact that runs in production. "Works on my machine" dies here, because there is only one machine now — the image. Build it in two stages so the fat JDK and the Maven cache never reach production; the runtime layer carries only a JRE.

```dockerfile
# ---- build stage: full JDK + Maven ----
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q -DskipTests package

# ---- runtime stage: JRE only ----
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/order-service.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75.0","-jar","app.jar"]
```

That split typically drops a 460 MB image to about 190 MB, and a smaller image pulls faster on every scale-up — which matters more than it sounds once autoscaling starts pulling it forty times an hour.

## Placement is bin-packing

Now you hold twenty services, each an image, and eight machines. Placement is the question: which pod goes where? Kubernetes answers it as bin-packing. Every pod declares `requests` for CPU and memory — the reservation the scheduler subtracts from a node's allocatable capacity. A node with 4 vCPU and 8 GiB allocatable, packing pods that each request 500m CPU and 1 GiB, holds eight of them; the ninth stays `Pending` because no node has room.

`requests` and `limits` are different knobs and both bite. `requests` is what the scheduler reserves up front; `limits` is the ceiling the kernel enforces at runtime. Set requests too low and you oversubscribe the node — pods that were quiet in test all wake under load, contend for real memory, and the kernel OOMKills whichever one asks next. Set them too high and you burn money on idle reservations, fitting four pods where twelve would have been safe.

## Anti-affinity: not every egg in one basket

Bin-packing alone will cheerfully stack all three replicas of the order service on the one node with the most free memory. Efficient, and catastrophic: when that node reboots, all three vanish together and the service is down despite having three replicas. `podAntiAffinity` forbids it, spreading replicas across hosts, racks or availability zones by `topologyKey`. Affinity is the mirror image — keep a service on the same node as the cache it hammers, to save a network hop.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  selector:
    matchLabels: { app: order-service }
  template:
    metadata:
      labels: { app: order-service }
    spec:
      containers:
        - name: order
          image: registry.example.com/order-service:1.8.0
          resources:
            requests: { cpu: "500m", memory: "1Gi" }
            limits:   { cpu: "1",    memory: "1Gi" }
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels: { app: order-service }
              topologyKey: kubernetes.io/hostname
```

`requiredDuringScheduling` is a hard rule — no two order pods share a host, even if that leaves the third `Pending` for want of a node. `preferredDuringScheduling` is a soft wish honoured when possible. Choose the hard form for the services you cannot afford to lose together.

## Blast radius

Here is the lesson that outranks the rest: what dies together when one machine dies. Co-locate the order and payment services on the same node to save a box, and one reboot takes out both — the whole checkout chain is gone while every other machine stays green. The bench makes this visceral: drag services onto machines, set anti-affinity, kill a random machine, and watch which services turn red.

| Placement of order + payment (3 replicas each) | Nodes | One node dies | Checkout survives? |
|---|---|---|---|
| All replicas crammed on one node | 1 | loses 100% | no |
| Both services, no anti-affinity, 3 nodes | 3 | ~1/3 of each gone | degraded |
| Anti-affinity per service across 3 nodes | 3 | one replica each gone | yes |
| Anti-affinity across 3 zones | 3+ | a whole zone gone | yes — survives a zone outage |

Density saves money; spread saves availability. The bench lets you feel the exact point where one saved machine turns into a dead checkout.

## Exercises

1. Write a multi-stage Dockerfile for one of your services and compare `docker images` size against a single-stage JDK build — aim to at least halve it.
2. Take a node with 4 vCPU / 8 GiB allocatable and pods requesting 500m / 1 GiB. Compute how many fit; then cut a pod's CPU request to 250m and re-derive the packing. Which resource — CPU or memory — binds first?
3. Add a `requiredDuringScheduling` podAntiAffinity on `topologyKey: kubernetes.io/hostname` to a 3-replica Deployment on a 2-node cluster, and explain why exactly one pod stays `Pending`.
4. On the bench, co-locate order and payment on one machine, kill it, and record the blast radius. Re-run with per-service anti-affinity across three machines and compare what checkout does.
