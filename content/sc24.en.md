## One request, the whole book

Everything in this book converges on a single line of production traffic: `POST /checkout`. Follow that one request through the system and every module you studied shows up, in order, doing its job. Nothing here is new — the capstone is not another component, it is the proof that the twenty-three mechanisms cooperate.

@fig sc24-arch

The journey, hop by hop:

| # | Hop | What happens | Module |
|---|---|---|---|
| 1 | Client to Gateway | TLS terminates; JWT signature and `exp` verified; token-bucket rate limit; route by path | m4, m8 |
| 2 | Gateway to Order | instance found via the registry, picked by client-side load balancer | m2, m3 |
| 3 | Order to Inventory | OpenFeign call, wrapped in a breaker with a 1 s timeout | m3 |
| 4 | Order: global txn | Seata coordinates inventory-deduct + payment-capture as one unit | m5 |
| 5 | Order to broker | publishes `order.created` to Kafka via Spring Cloud Stream | m5 |
| 6 | Points / Notification | consume the event asynchronously, at their own pace | m5 |
| - | every hop | one `traceId` stitches the spans; metrics scraped; logs correlated | m6 |
| - | every pod | config from the config server; scheduled on K8s, HPA-scaled; active-active across 2 DCs | m4, m7 |

The synchronous spine (steps 1 to 4) must all succeed or the whole checkout fails as a unit; the asynchronous tail (steps 5 to 6) is fire-and-forget, so awarding loyalty points can lag by seconds without making the customer wait, and a dead notification consumer never blocks an order. That split — strong where the money is, eventual where it is not — is the single most important design choice in the diagram.

```java
@GlobalTransactional(timeoutMills = 10000, name = "checkout")   // Seata: one global txn
public OrderResult checkout(CheckoutCmd cmd) {
    inventory.deduct(cmd.sku(), cmd.qty());                     // Feign + breaker (branch)
    payment.capture(cmd.userId(), cmd.amount());                // branch txn
    Order order = orders.save(Order.created(cmd));
    stream.send("order-out-0",
        new OrderCreated(order.id(), cmd.userId(), cmd.amount())); // async event
    return OrderResult.ok(order.id());
}
```

## Trade-offs that constrain each other

The hard part of the capstone is that you cannot tune each mechanism in isolation — turning one knob moves others.

- **Consistency eats elasticity.** Seata's AT mode holds row locks on the inventory and payment rows from `deduct` until the global commit. Hold them for, say, 40 ms per checkout and one hot SKU's rows serialise every order for it — the ceiling is now lock contention on the database, not CPU on the pods. Autoscaling the order service from 3 pods to 12 buys you nothing here, because the twelfth pod queues on the same lock the third did. Stronger consistency (2PC / XA) makes this worse; a Saga with compensations trades the lock away for the harder problem of writing correct compensations.
- **Aggressive autoscaling amplifies cold starts.** Set the HPA to react fast and it adds pods the instant load spikes — but a fresh JVM pod needs 30 to 45 s to start, warm its connection pools and JIT-compile the hot path. If it registers in discovery *before* it is warm, the load balancer sends it real traffic, its first responses breach the 1 s timeout, and the callers' breakers trip on a pod that is merely cold, not broken. Scaling meant to relieve load has manufactured timeouts. Readiness probes and pre-warming exist to close exactly this gap.

## Single points and bottlenecks

Draw the diagram and the risks light up:

- **The stateful stores** — the order database and Seata's transaction coordinator — are the true single points; pods are cattle, the database is a pet. Most incidents live here.
- **The message broker** is a shared dependency for the whole async tail; partition it and size it, or the loyalty backlog becomes everyone's backlog.
- **The gateway tier and auth server** sit on every north-south request. Run them as horizontally-scaled clusters, and if you chose opaque tokens, remember the auth server now takes one introspection call per request.
- **The registry** is the map everyone reads; client-side caching (m2) is what lets a checkout still complete during a brief registry blip.

## A maturity self-assessment

Close the book by scoring your own team. Each of the eight modules is a dimension; rate each from 0 (ad hoc) to 3 (mature), and the low numbers are your roadmap.

| # | Dimension | 0 to 3: from ad hoc to mature |
|---|---|---|
| 1 | Boundaries & decomposition | services split by DDD contexts, not shared tables |
| 2 | Registry & discovery | no hard-coded addresses; survives a registry blip |
| 3 | Communication & resilience | every remote call has timeout + breaker + safe retry |
| 4 | Gateway & config | one edge; config changes without a redeploy |
| 5 | Messaging & transactions | idempotent consumers; a deliberate consistency model |
| 6 | Observability | one traceId end-to-end; you alert on p99, not averages |
| 7 | Deploy, scale & multi-region | HPA tuned; a known RPO/RTO you have actually tested |
| 8 | Security & chaos | zero-trust auth; resilience verified by chaos drills |

A team scoring mostly 0 to 1 has a distributed monolith with extra latency; mostly 3s is a system that degrades instead of collapsing. The bench renders this whole flow as one dashboard — load it, trip a breaker, fail a data centre — and lets you watch the score you just gave yourself play out as behaviour.

## Exercises

1. Trace one real request in your own system end-to-end and fill in the journey table with your actual components and modules. Which hop has no timeout or breaker?
2. Measure a lock-held duration in your hottest distributed transaction, then compute how many concurrent orders on one SKU that serialises into — is your real bottleneck CPU or the lock?
3. Score your team on all eight dimensions above, with one piece of evidence for each score. Circle the lowest two — that is next quarter's work.
4. On the bench, fail one data centre mid-checkout. Record how long until traffic recovers (your observed RTO) and whether any in-flight order was lost (your RPO).
