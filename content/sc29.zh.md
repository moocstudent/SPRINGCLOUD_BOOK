## 单机限流不够:N 倍问题

GW2 里你在一个服务前面放了个令牌桶,把它限在比如每秒 1000 次。这对一个进程有效。可你在生产里从不只跑一个网关;为了高可用和吞吐,你会在负载均衡后面跑一群网关副本,十个、二十个。于是你精心设的那个限额,悄悄就失效了。

原因是每个副本都有自己的桶,在自己的内存里。如果你在十个网关上都配 `replenishRate: 1000`——这是最顺手的做法,也是现场最常见的错误——那么每个都放一千,一万个就进来了。你那个「1000 rps 的限流」现在变成了 10000 rps。本地的桶不会相加成一个全局的桶;它们相乘。

那个「显而易见的修法」——给每个副本 1/N 的额度、每台 100 rps——也是错的,只是错得更隐蔽。负载均衡不会把流量分得绝对均匀。某个恰好接到超过自己份额流量的副本会把它那 100 用光、开始拒绝,而别的副本还没到上限——于是全局明明远没到 1000,你却拒了合法请求。治理台把两种翻车都摆出来:本地桶设成全局值就超额,平分后遇到倾斜就少放。

## 共享计数器与原子性

要强制一个全局限额,唯一的办法是把计数放在一个所有副本都去查的共享位置。实践中这个位置就是 Redis:每个请求,网关都对一个按客户端做键的计数器(或令牌桶)做「检查并扣减」。因为所有副本打的是同一个键,无论有多少网关、负载多倾斜,额度都是精确的。

这里有个不注意就会坑你的细节:检查和扣减必须**原子**。如果一个网关读到「还剩 1 个令牌」,而第二个网关在第一个写回「0」之前也读到「还剩 1 个」,两个都放行,你就超额了。你不能在应用侧「先读后写」;整个操作必须是一个不可分割的步骤。Redis 恰好用服务端的 **Lua 脚本**提供了这个能力——脚本在 Redis 上一口气跑完,中间不会插进别的操作。Spring Cloud Gateway 的 `RequestRateLimiter` 正是这么造的:一个 Redis 支撑的令牌桶,它的「续桶+扣减」是一段 Lua 脚本,而 `replenishRate` 和 `burstCapacity` 是全局的、覆盖整个集群的值。

## 三种算法

计数共享之后,你还要选「怎么数」。常见算法在精确度和成本之间权衡:

| 算法 | 思路 | 取舍 |
|---|---|---|
| 固定窗口 | 每 1 秒一个桶,到边界清零 | 最便宜;有边界突刺(边界处最多 2 倍) |
| 滑动窗口日志 | 存每个请求的时间戳,数最近 1 秒 | 精确;费内存(每请求一条) |
| 滑动窗口计数 | 按重叠给当前窗口和上一个窗口加权 | 削平边界突刺、便宜,略近似 |
| 令牌桶 | 按速率续令牌,每请求花一个 | 平滑且容许突发;网关的默认 |

固定窗口的边界突刺问题值得记牢:按秒清零时,一个客户端可以在 0.999 秒发 1000 个、再在 1.001 秒发 1000 个——约两毫秒内 2000 个,却都「在限额内」。滑动窗口计数和令牌桶都能避开这一点,这也是为什么你真正想要的是它们,而不是朴素的固定窗口。

## 代价

共享限流器是对的,但它不免费,而它的代价塑造了真实的设计。每个请求现在都要先做一次 **Redis 往返**才被路由——零点几毫秒,却在每个调用的热路径上。而 Redis 现在要扛整个集群每请求一次操作,这让它成了**热点和单点**:Redis 慢,每个请求都慢;Redis 挂了,你就得决定是「失败即放行」(全放)还是「失败即拒绝」(全拒)。

生产系统用**本地+全局的混合**来缓解:每个网关保留一小份本地额度,只定期和 Redis 同步,于是大多数请求在本地就判了、Redis 看到的流量少得多——用边界处一点点精度换取往返次数的大幅下降。要记住的规则是:全局限额需要共享存储,共享存储需要原子性,而它带来的那次往返,就是一个真正管用的限额的价钱。

## 练习

1. 跑两个网关副本,用本地(内存)限流器各设 1000;加压,确认约 2000 个穿过。再切到 Redis 限流器,确认它稳在 1000。
2. 读一读 Spring Cloud Gateway 的 `request_rate_limiter.lua`,追一追续桶和扣减是怎么在一次原子调用里完成的。
3. 演示固定窗口的边界突刺:发一波跨在窗口边界上的流量,观察最多 2 倍的限额;再切到滑动窗口,看它消失。
4. 在限流器运行时把 Redis 杀掉,观察「失败即放行」与「失败即拒绝」的行为;想清楚你的 API 该选哪个,并配置它。
