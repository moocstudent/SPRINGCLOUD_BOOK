## @Transactional 到哪里为止

`@Transactional` 是单个数据库的能力。在它之下,Spring 握着一个 JDBC 连接,`commit`/`rollback` 是这个连接对这一个数据库的原子操作。一旦你的下单跨了订单库、库存库、账户库——三个服务、三个数据源——就没有任何一个连接能同时看见这三者,于是也没有任何东西能把它们一起提交或一起回滚。如果订单先提交了、接着账户扣款抛异常,订单那行数据**已经持久化**了;Spring 没法伸手到一个它并不拥有的数据库里,去撤销一个已经提交的事务。原子性的边界就是那个连接,而它不跨网络。下面每一种方法,都是在这道鸿沟上重建「要么全成、要么全败」——而每一种都收一笔不同的费。

## 2PC / XA:强一致,把可用性押上去

两阶段提交在参与的资源管理器前面放一个**协调者**。**第一阶段(准备)**里,每个参与者把活干了、写好 undo/redo 日志、*持有它的锁*,然后回答「准备好了」——但不提交。**第二阶段(提交)**里,协调者收齐一致的「准备好了」之后,通知所有人提交;只要有一个「不行」,就变成全局中止。这个保证是货真价实的强:要么全提交,要么全不提交。

代价写在「持有」这个词里。每个参与者从准备一直握着行锁,直到第二阶段的决定到来——跨两个网络往返,以最慢那个参与者的速度。一个本地事务也许只锁一行 1 毫秒;同一行在 XA 下要锁上几十毫秒,于是一有争用,吞吐就崩。更糟的是,如果协调者在准备*之后*崩了,参与者就**阻塞**在那里,握着锁,在它回来之前既不敢安全提交也不敢中止——2PC 把整个组的可用性押在了一个协调者身上。这种阻塞正是 XA 很少被用在繁忙微服务之间的原因(XA 是标准,JTA 是它的 Java 接口)。

## TCC 与 Saga:短锁 vs 补偿链

**TCC(Try-Confirm-Cancel)** 用**业务预留**替换数据库锁。*Try* 做预留——冻结 100 元余额,不是把那行跨网络锁住,而是把钱挪到一个「冻结」列里并立即提交。*Confirm* 花掉这笔预留;*Cancel* 释放它。锁又短又本地,吞吐高,但你在代码上付费:每个操作三个方法,而且 Confirm/Cancel 必须幂等,还要处理「空回滚」(Cancel 比 Try 先到)和「悬挂」(Try 比 Cancel 后到)这类边界情况。

**Saga** 更进一步,干脆不持有任何锁。它是一串本地事务 T1…Tn,各自独立提交,每一步配一个**补偿** C1…Cn。如果 T3 失败,saga 就反向执行 C2、C1。让人栽跟头的一点是:**补偿不是回滚。** T2 提交时是*真的扣了*账户;C2 没法让它没发生过,所以 C2 是一个*新的*事务,把钱再打回去。在 T2 提交到 C2 执行之间,有一段真实的时间,旁观者会看到钱被扣了却没有订单——一个**能被观察到的不一致窗口**。Saga 不给你任何隔离性,所以你要用显式状态来兜(订单在整条链完成前一直是 `PENDING`)。作为回报,它是唯一能扩展到长时间、高吞吐流程的选项。

## Seata 的四种模式,和那一个洞见

Seata 是 Spring Cloud Alibaba 世界里事实上的分布式事务框架。一个独立的 **TC(事务协调者)** 跟踪全局事务;你的服务里带着 **TM**(发起全局事务)和 **RM**(注册每个分支)。

- **AT(自动事务)** 是最省心的模式,也是人们选 Seata 的理由。它拦截你的 SQL,把*前镜像*和*后镜像*写进同一个本地事务里的 `undo_log` 行,并拿一把全局锁。如果全局事务失败,Seata 读 `undo_log`、替你生成补偿 SQL——**零业务代码**。你付出的是一把全局锁(真实存在,只是隔离性弱于 XA),而且因为是基于补偿的,仍有一个小窗口。
- **TCC / Saga / XA 模式** 把上面那些手写模式封装起来:TCC 用于精确的资源控制,Saga(一个状态机)用于长流程,XA 用于你确实必须要真正强一致的时候。

```java
@GlobalTransactional(name = "place-order", rollbackFor = Exception.class)
public void placeOrder(OrderCmd cmd) {
    orderClient.create(cmd);       // 分支 1 -> 订单库
    inventoryClient.deduct(cmd);   // 分支 2 -> 库存库
    accountClient.debit(cmd);      // 分支 3 -> 账户库(抛异常 -> 全局回滚)
}
```

| 模式 | 一致性 | 锁时长 | 业务代码 | 耦合 |
|------|-------|-------|---------|------|
| 2PC / XA | 强 | 长(两个阶段) | 无 | 紧(所有 RM 都要支持 XA) |
| TCC | 最终(短) | 短预留 | 重(3 个方法) | 高 |
| Saga | 最终(可见窗口) | 无 | 中(补偿) | 中 |
| Seata AT | 最终(全局锁) | 短(到提交为止) | 无(undo_log) | 低 |

要带走的唯一洞见:**没有免费的强一致。** 2PC 用长锁和协调者阻塞换来它;Saga 用手写补偿和一个可见窗口换来可用性;TCC 和 AT 夹在中间。按业务选——一笔低争用、和钱有关的扣款也许值得上 XA/AT,而一条又长、量又大的履约流程要的是 Saga。在治理台上,把失败注入到第三步,对比 2PC 的锁持有时间和 saga 的补偿链,看成功率、锁时长、补偿成本怎么此消彼长。

## 练习

1. 用两句话解释:为什么「先提交订单、再调账户服务」可能留下一笔没扣的钱,以及为什么把顺序对调也修不好它。
2. 为「从账户扣 100」写出一个 TCC 实现的 Try、Confirm、Cancel 三步,并说明如果 Cancel 比 Try 先到,Cancel 必须做什么。
3. 拿一个三步 saga(订单 → 库存 → 支付),给每一步写出补偿;标出外部观察者可能看到总额不一致的确切窗口。
4. 在治理台上,让同一个会失败的事务分别在 XA 和 Saga 下运行;记录各自的锁持有时间和端到端延迟,并决定:一个每秒 500 单的下单,你会上哪一个。
