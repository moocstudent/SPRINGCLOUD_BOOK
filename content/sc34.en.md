## A power-anomaly service: where does its data come from?

The last chapter got a Python time-series service into Spring Cloud — gateway, registration, discovery all wired; it can be reached and discovered. But the hardest step for a service that actually ships is still open. Picture a concrete scenario: an ERP needs power monitoring and anomaly detection, you train a time-series model, and you wrap it as a Python service. The question now is not "how does it get called" but **where does its data come from and where do results go** — and this is where most people go wrong on day one.

Almost everyone's first instinct is to point Python straight at the Java business service's database: the data is all in there, so a single `create_engine("mysql://...")` and away we go. Online anomaly check? Query the DB. Training? `SELECT` three months of history. Simple, direct, running the same day.

What this chapter makes clear is why that shortest path is wrong, and how the right path splits by load into "online" and "training". The core is one sentence: **business data is owned by the Java service, and Python never connects to its OLTP database directly.**

## The red line: don't share the business DB (OLTP)

"Python connects to the business DB directly" has a formal name in microservices: the **shared-database anti-pattern**. Its cost comes in three layers, each more painful than the last.

**Schema coupling.** Your Python code now hard-codes the Java service's table structure. The day the Java team runs a migration — renames a column, splits a table, adds a not-null constraint — they will not tell you, because to them that is their service's internal implementation. And so your service breaks one morning with no warning. Microservices are supposed to let two teams evolve independently; a direct connection to the business DB throws that premise away.

**Bypassing business logic.** The validation, permissions, audit and state machines all live in the Java service's code layer, not in the database. Your Python direct-connect bypasses that whole layer — you may read unvalidated intermediate state, and anything you write skips every business rule. For an anomaly-detection service that must trigger alerts and open tickets, "skips the business rules" is nearly the definition of causing an incident.

**Contending for transactional resources.** This is the most fatal layer, and the most underestimated. The business OLTP database is for high-frequency, short transactions, and it fears two things: locks and big scans. Your training pull is exactly a multi-million-row big scan. When that scan fights the normal business for the same DB, the business's P99 degrades faster than you expect — not linearly, but as a **non-linear explosion** in the queueing-theory sense: the closer utilization gets to 1, the more latency shoots up. The bench shows this with a real queueing model: push business load to 2000 qps, then let a direct-connect training run scan the DB, and utilization jumps to 0.83 with business P99 nearly tripling; add a little more load and the system overloads — one training pull just took down the transactional system with your own hands.

## Online via events, training via CDC→analytics store

"No direct connection" does not mean "only call the API". The key insight: **online and training are two completely different loads, and they should take two completely different roads.**

**Online real-time — go through events.** Scoring each new reading for anomalies is a "triggered as data arrives" load — event-driven by its very shape. Have the Java side, when it saves a reading, publish a telemetry event to Kafka (Spring Cloud Stream); Python subscribes to the topic and scores one as each arrives. It does not query or poll — data is pushed to it; it is also naturally decoupled (Java need not know a Python is listening) and can scale parallelism by partition count. On this road, Python never touches the business DB.

**Batch training — go through CDC to an analytics store.** Pulling millions of historical rows to feed a model has two tempting options you must both reject: one, force it through a REST API with pagination — too slow (pagination plus serialization), and the requests still land on the business DB; two, connect to the primary and scan — the red line from the last section. The right move is a data pipeline: use **CDC (Debezium/Canal)** to tail the business DB's binlog and replicate OLTP row changes **incrementally** into a dedicated **analytics store** (TimescaleDB / ClickHouse). Python connects to that analytics store and runs SQL.

Here is where many people get stuck: **isn't connecting to the analytics store also a "direct DB connection"? Why is this one allowed?** Because the red line was never about "any database" — it is about "another service's transactional database". The analytics store is the data side's own, columnar, read-optimized store; its entire reason for existing is this kind of bulk analytical read; its schema is a modeled, stable analytics layer, and that table itself is the contract. Connecting to it neither couples you to Java's transactional tables nor competes for OLTP resources (CDC only tails the binlog, it runs no big queries). **OLTP for transactions, OLAP for analytics, physically separate** — a decades-old rule in the data world, which microservices only make more binding.

As for what Python itself computes — the model file, features, each reading's anomaly score, thresholds — that is Python's own data, stored in Python's own database. The business DB is not its home.

## Backflow: write results back through Java too

Getting the data-in path right is only half. There is the **results-out path.** Python detects an anomaly and now has to trigger an alert, open a ticket, notify ops — how should it write that result back into the system?

The answer is symmetric with the way in: **do not INSERT into the business DB — publish an anomaly event back to Kafka.** Have Java's alert/ticket service subscribe to that event, and let it persist, open the ticket, and run the approval flow. Why the detour? Because "open a ticket" is not one DB write, it is a chain of business logic: validate the device exists, decide the ticket's severity by rule, write audit, prevent duplicates. All of that lives in the Java service. A Python direct INSERT into the ticket table skips all of it — you get a ticket in the wrong state, no approval run, and possibly duplicated.

"Preventing duplicates" matters especially here. Anomaly events can be redelivered (Kafka's at-least-once), and the same "device A power anomaly at 12:03" may arrive twice. So the consumer must be **idempotent**: dedup by `(device, timestamp)`, recognize on the second arrival that "this ticket was already opened", and skip (recall idempotency and the outbox from TX3). Anomaly-detection services trip here often — the model fires several alerts for one stretch of anomaly, and without idempotency, ops gets buried at 3 a.m. under dozens of tickets for the same fault.

One line to close: **data in — online via events, training via CDC→analytics store; results out — back through Java, idempotently.** The Python time-series service thereby becomes a clean, decoupled member of the system that neither drags down the business DB nor bypasses the business rules — it only does its job: turning data into anomaly signals.
