## Two cores

Spring Cloud Stream lets you swap Kafka for RabbitMQ by changing a dependency and a few lines of YAML. That is genuinely useful — but it can mislead you into thinking the two are interchangeable. They are not. Underneath the shared programming model sit two fundamentally different machines, and the bench above scores them against your requirements precisely because the right answer depends on the workload, not on fashion.

**Kafka** is a distributed, partitioned commit log. A topic is split into partitions; each partition is an append-only sequence of messages on disk, kept for a retention period (hours, days, or forever). Producers append to the end; consumers read by holding an **offset** — a pointer into the log — and advance it as they go. Nothing is deleted when a consumer reads it; the message stays until retention expires. Throughput is enormous because appending to a log is sequential disk IO and messages are batched, and it scales horizontally by adding partitions.

**RabbitMQ** is a smart broker built around the AMQP model. Producers do not publish to a queue; they publish to an **exchange**, which routes each message to zero or more queues according to bindings and a routing key. Consumers subscribe to a queue and are *pushed* messages; they acknowledge each one, and on ack the message is removed from the queue. The broker does the routing work — which is powerful — but the broker is also the bottleneck.

## Replay, ordering, acking — one word, two meanings

The clearest way to feel the difference is three capabilities that sound the same but behave differently.

**Replay.** In Kafka, because messages persist and consumers track their own offset, any consumer group can rewind to offset 0 and reprocess the entire history — invaluable for event sourcing, rebuilding a read model, or recovering from a bug in a consumer. In RabbitMQ, once a message is acked it is gone; there is no rewind for a classic queue. (The newer Streams plugin adds log-like replay, but that is RabbitMQ borrowing Kafka's model.)

**Ordering.** Kafka guarantees order *within a partition*. If all events for one order must be processed in order, you key by order id so they land in the same partition. RabbitMQ preserves order within a single queue read by a single consumer — but the moment you add competing consumers for throughput, or a message is requeued after a failure, ordering is no longer guaranteed.

**Acking and delivery.** Kafka consumers pull and commit offsets; a slow consumer simply lags behind, and back-pressure is natural. RabbitMQ pushes messages up to a prefetch limit and expects a per-message ack, which gives fine-grained control — reject, requeue, or dead-letter a single message — at lower latency, at the cost of more per-message bookkeeping.

## Routing

This is where RabbitMQ shines. Its exchange types — direct, topic, fanout, headers — let the broker route one published message to many queues by flexible rules, without the producer knowing who consumes. Fanout broadcasts to everything bound; topic matches routing keys like `order.*.eu`; headers matches on attributes. Kafka has no exchange: routing is topic plus a partition key, and any finer selection happens in the consumer, which reads everything and filters. If your system needs rich, server-side routing topologies, RabbitMQ expresses them directly; in Kafka you build them yourself.

## Choosing by workload

There is no universal winner. Match the broker to the requirement, as the bench does:

| Requirement | Favours | Why |
|---|---|---|
| Very high throughput (100k+/s) | Kafka | partitioned log, sequential IO, scales with partitions |
| Replay / event sourcing | Kafka | messages retained, consumers rewind by offset |
| Strict per-key ordering | Kafka | ordered within a partition |
| Complex routing topologies | RabbitMQ | exchanges: direct / topic / fanout / headers |
| Task queues / work distribution | RabbitMQ | competing consumers, per-message ack, requeue |
| Low-latency, per-message control | RabbitMQ | push delivery, fine-grained ack, dead-letter |

A rough rule: reach for **Kafka** when the data is a *stream of events* you may want to keep, replay, and process at high volume; reach for **RabbitMQ** when the data is *work to be handed to a worker*, routed cleverly, and acknowledged one item at a time.

And remember the previous chapter: because Stream abstracts the binder, you can defer the decision, prototype on whichever your team knows, and switch later by changing configuration rather than code:

```yaml
# same bindings, different binder — see the Code panel for the full pair
spring.cloud.stream.kafka.binder.brokers: kafka:9092      # or...
spring.cloud.stream.rabbit.bindings...:  exchange-type: topic
```

The one thing you *cannot* cheaply change is a requirement the broker fundamentally does not serve — so let that requirement, not the binder, drive the choice.

## Exercises

1. Bring up Kafka and RabbitMQ with docker compose, point the same Stream service at each via `application-kafka.yml` / `application-rabbit.yml`, and confirm the Java is byte-for-byte unchanged.
2. On Kafka, set `start-offset: earliest` and restart a consumer group — watch it reprocess the whole topic. Attempt the same on a RabbitMQ classic queue and observe there is no equivalent.
3. On RabbitMQ, declare a topic exchange and bind two queues with routing keys `order.*.eu` and `order.*.us`; publish with different keys and watch the broker route. Reproduce the same fan-out in Kafka and note what you had to build yourself.
4. Add a second competing consumer on one RabbitMQ queue and on one Kafka partition; push a keyed, ordered stream through both and compare whether ordering holds.
