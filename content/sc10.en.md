## One door, not a hundred

Behind a mature system sit forty, eighty, a hundred services, each with its own host and port that changes on every deploy and scale-out. You cannot hand that list to a mobile app or a partner's server. Worse, every cross-cutting concern — authentication, rate limiting, CORS, request logging, TLS termination — would be re-implemented in all hundred, then re-released a hundred times when a rule changes. An **API gateway** collapses this into a single entry point: one address the outside world talks to, one place those shared concerns live.

Spring Cloud Gateway is the officially maintained gateway today; it replaced Netflix **Zuul 1**, whose one-thread-per-request blocking model capped throughput. Gateway is built on the **reactive** stack — Project Reactor over Netty — so a handful of event-loop threads carry thousands of concurrent, mostly-waiting connections. That is the right shape for a proxy, whose job is largely waiting on upstreams. The cost of reactive is real: you must never call blocking code inside a filter, or you stall an event loop and throughput collapses.

## Predicates: does this request take this route

A route is a **predicate** (does this request match?) plus a **target URI** plus a list of **filters**. The gateway walks routes in order and hands the request to the first whose predicate is true. Predicates are cheap boolean tests over the incoming request:

| Predicate | Matches on | Example |
|-----------|-----------|---------|
| Path | URL path | `/api/orders/**` |
| Method | HTTP verb | `GET`, `POST` |
| Header | header presence / regex | `X-Region: eu` |
| Query | query parameter | `?debug=true` |
| Weight | random share within a group | 90 / 10 |
| After / Before | wall-clock time | open a launch at 09:00 |

Combine them with AND: `Path=/api/orders/** AND Method=GET` routes only order reads. This is how one gateway fronts a hundred services — each owns a path prefix, and the registry (via `lb://ORDER-SERVICE`) resolves that prefix to live instances.

## Filters: the work before and after forwarding

Predicates decide *whether*; filters decide *what happens*. Each filter runs in a **pre** phase (before the request is forwarded) and/or a **post** phase (after the response returns), forming a chain around the proxy call. Pre-filters add or strip headers, rewrite the path, check a token, or enforce a rate limit; post-filters rewrite the response, add CORS headers, or record latency for tracing. Concretely: strip the public `/api` prefix before forwarding, inject an `X-Request-Id`, drop the client's `Authorization` header and replace it with a verified identity header for the backend. Doing this once at the edge is the whole point — the hundred backends never re-implement it.

## Weighted routing: a canary you roll back in one line

The **Weight** predicate is deceptively powerful. Two routes in the same weight group split traffic by ratio, so pointing 90% at v1 and 10% at v2 gives you a **canary release**: real production traffic exercises the new version while the blast radius is capped at one request in ten. Watch error rate and P99 on the canary; if it holds, ramp 10 -> 30 -> 60 -> 100 over minutes or hours; if it spikes, set the new version's weight to 0 and every request instantly returns to v1 — a rollback that touches one config value, not a redeploy.

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: orders-v1
          uri: lb://ORDER-SERVICE-V1
          predicates:
            - Path=/api/orders/**
            - Weight=orders-group, 90
          filters:
            - StripPrefix=1
        - id: orders-v2-canary
          uri: lb://ORDER-SERVICE-V2
          predicates:
            - Path=/api/orders/**
            - Weight=orders-group, 10
          filters:
            - StripPrefix=1
            - AddResponseHeader=X-Canary, true
```

The bench is a hands-on version of exactly this: set the predicates and the two weights, pour a stream of requests through, and watch which backend each one lands on. Push the canary above 10% and the v2 bar grows; note that weighting is **statistical**, not exact — over 50 requests a "10%" route may take 3 or 8, and only over thousands does it converge on the ratio. That variance is why you never canary a low-traffic route by weight alone: 10% of 20 requests a minute is 2 — too few to conclude anything before you have shipped to everyone.

## Exercises

1. Configure two routes in one weight group at 80/20, send 200 requests through the bench, and record how many actually reach the 20% route; compare against the expected 40.
2. Add a Header predicate (`X-Beta: true`) as a second route to ORDER-SERVICE-V2 so internal testers always hit v2 regardless of weight; verify a request with and without the header lands correctly.
3. Write a filter chain that strips the `/api` prefix and adds an `X-Request-Id` header; confirm the backend sees the rewritten path.
4. Starting at 5% canary, ramp to 100% in four steps while watching the simulated error rate. At which step would you roll back if v2's error rate hit 4%? Set its weight to 0 and confirm traffic returns to v1.
