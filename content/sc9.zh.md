## 一个慢下游怎么把一切拖垮

先看这一整章存在的意义所要防的那个故障。你的服务用一个 200 线程的池处理请求。你调的一个下游平时 50 毫秒返回,于是每个线程每秒能干完 20 个调用,池子轻松扛住每秒 4000 个调用。

下游劣化了——一次糟糕的发布、一把锁、一条慢查询——现在每个调用要 5 秒。每个线程每秒只能干完 0.2 个调用。每秒进来 1000 个请求,200 个线程在 200 毫秒内就全卡在等待上,接受队列排满,你的服务开始拒绝**每一个**请求——包括那些根本不需要那个生病下游的请求。你不是 CPU 或内存耗尽,你是**线程**耗尽,全部停在等一个依赖上。然后调**你**的人看到**你**超时,他们的线程也开始堆积,故障就这样顺着调用图一层层往上爬。这就是雪崩,而这一章的四个模式,就是你在某个边界上把它拦住的办法。

## 熔断器的三个状态

熔断器是给调用用的保险丝。它包住一个下游、盯着调用的结果,有三个状态。

@fig sc9-breaker

- **关闭**——正常。请求照常通过,熔断器把每次结果记进一个滑动窗口(比如最近 100 次调用)。一旦失败率越过阈值——在足够样本上达到 50%——它就跳到**打开**。Resilience4j 还会把慢过某个时长的调用算作「慢调用」,所以它能在这些调用还没失败之前、就因为慢而跳闸。
- **打开**——已跳闸。每个调用**立即**以 `CallNotPermittedException` 失败,一个都不放到下游去。这正是重点:调用方不再把线程停在一个明显已死的依赖上,而是把这段等待的时间用来恢复。它保持打开一段固定的 `wait-duration-in-open-state`,比如 10 秒。
- **半开**——探活。等待期过后,熔断器放进固定的一小批试探调用(比如 5 个)。它们大多成功,就合上、恢复正常流量;它们还在失败,就再次打开、再等一个周期。这是它在没有人干预、也不会把全量流量猛砸到一个可能还很脆弱的下游上的前提下,自动恢复的办法。

```java
@CircuitBreaker(name = "inventory", fallbackMethod = "stockFallback")
public StockLevel getStock(String sku) {
    return inventoryClient.getStock(sku);
}

// 参数和被保护的方法一致,末尾多一个 Throwable
private StockLevel stockFallback(String sku, Throwable t) {
    return StockLevel.unknown(sku);   // 一个安全的默认值,而不是抛异常
}
```

那些阈值不是摆设——它们**就是**熔断器的行为:

```yaml
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 100
        minimum-number-of-calls: 20          # 别因头两次失败就跳闸
        failure-rate-threshold: 50           # % 失败 -> 打开
        slow-call-duration-threshold: 2s
        slow-call-rate-threshold: 80         # % 慢过 2s -> 打开
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 5
```

`minimum-number-of-calls` 设得太低,两个请求的抖动就能让熔断器跳闸;`failure-rate-threshold` 设得太高,该跳的时候它永远不跳。在治理台上你直接拨这几个参数:把下游压到过载,看失败率爬过阈值、熔断器啪地打开,再看半开的探针在下游恢复后让它自愈。

## 另外三件事:限流、降级、隔离

熔断器是在失败**攒够之后**才反应。它的三个兄弟盖住其余的角度。

| 模式 | 防的是 | 机制 | 陷阱 |
|---|---|---|---|
| 熔断 | 下游已死或很慢 | 跳开、快速失败、探活恢复 | 阈值调错,要么跳太早要么永不跳 |
| 限流 | 流量超过你的容量 | 在门口拒掉超预算的调用(429) | 设得低于真实容量,就把好流量也甩了 |
| 降级 | 失败或跳闸的调用仍需一个答案 | 返回一个安全默认值 | 降级成一个**错的**答案,比报错更糟 |
| 舱壁 | 一个依赖耗尽所有线程 | 每个下游独立的池/信号量 | 池切得太多太小,反而浪费容量 |

**限流**把决定挪到前门:超过容量,就用一个 429 快速拒绝,而不是收下你干不完的活。**降级**用一个安全默认值回应一次失败的调用——缓存数据、空列表、「当作缺货处理」——但绝不能是一个像模像样的谎;返回一个假的「支付成功」,远比一个诚实的报错糟糕。**舱壁**给每个下游各自的线程池或信号量,让第一节里的雪崩根本发生不了:把跟生病服务说话的那个池耗尽,健康服务的池丝毫不受影响。

## Resilience4j 还是 Sentinel

两者四个模式都做,区别在运维模型。

- **Resilience4j**——一个轻量 Java 库,按实例在代码或 YAML 里配置,用注解驱动,接进 Micrometer 出指标。它是 Hystrix 退役后 Spring Cloud Circuit Breaker 抽象背后的默认实现。配置基本上是每次部署时静态定好的。
- **Sentinel**(阿里)——一个带控制台的运行时,规则可以从 Nacos 动态推下来,还有热点参数限流和系统自适应保护。跑起来更重,但你不用重新部署就能重调阈值——当运维必须在一个大集群上实时改限流规则时,就选它。

## 练习

1. 在治理台上,把下游失败率分别压到刚好高于和低于 `failure-rate-threshold`,确认熔断器一种情况跳、另一种不跳。
2. 给一个真实调用加上 `@CircuitBreaker` 和 `fallbackMethod`;制造失败,验证降级方法确实运行、并返回一个**安全**的值,而不是一个误导人的值。
3. 给两个下游各自独立的 Resilience4j 舱壁,然后把其中一个压满,证明对另一个的调用仍然成功。
4. 为一个真实依赖写下它的 `failure-rate-threshold`、`wait-duration-in-open-state` 和半开探针数,并用那个依赖真实的恢复时间为每个数字辩护。
