## 同步调用的隐藏成本

订单服务用三个阻塞式 HTTP 调用去调库存、积分、通知,看起来是再普通不过的代码,但你已经悄悄买下了**时间耦合**:这四个服务必须在同一瞬间都健康,而且调用方要一直占着一个线程,直到最慢的那个返回。账单落在两个维度上。延迟是**叠加**的——如果每个下游的 p99 是 200 毫秒,串行下来就是 600 毫秒用户才看到结果,而这段时间订单线程一直被钉住。可用率是**连乘往下掉**的——三个各自 99.9% 的依赖,下单最多只有 0.999 × 0.999 × 0.999 ≈ 99.7%,你每挂上一个下游,它就更低一档。最糟的是,如果三个里最不重要的通知服务挂了,一个天真的同步下单会因为一件用户根本没在意的事**让整单失败**。

## 发出去一次,谁关心谁订阅

事件驱动通过反转「谁在等」来打破耦合。订单服务提交自己那行数据,发出一个事实——`OrderCreated`——然后就返回。它不知道、也不关心谁去消费。库存去扣减,积分去累加,通知去发邮件,各干各的,谁也不知道对方存在。三个性质随之而来:

- **解耦。** 加一个第四种反应——比如风控评分——只是新增一个订阅者;订单服务不改代码、不重新部署,甚至不需要知道。
- **削峰。** 一场秒杀把每秒 10000 笔订单砸向一个每秒只能写 2000 次的数据库,同步链路会当场垮掉。变成事件后,多出来的量只是排队;消费者按自己稳定的节奏消化,用延迟换生存。
- **韧性。** 如果库存消费者崩了,它的消息会**留在队列里**等它回来,恢复后再处理。同步版本没有这种宽限:调一个死掉的服务立刻失败,而且是在用户的请求上失败。

作为交换你接受的代价是:世界变成了**异步、最终一致**——订单先存在,几百毫秒后库存才真正被扣,你必须为这段间隙做设计(见 sc14–sc15)。

## Spring Cloud Stream 的函数式模型

Spring Cloud Stream 让你写这套东西时不必直接碰 Kafka 或 RabbitMQ 的客户端。你把每个角色写成一个普通的 `java.util.function` Bean:

- `Supplier<T>`——只发不收的源(生产者),
- `Function<T,R>`——收了再发(处理器),
- `Consumer<T>`——只收不发的汇。

一个 **binder(绑定器)** 把这些 Bean 接到真正的中间件上;把 `spring-cloud-stream-binder-kafka` 换成 `...-binder-rabbit`,同一份代码就从 Kafka 搬到了 RabbitMQ,源码一行不改。

```java
@Bean
public Consumer<OrderCreated> orderEvents() {
    return event -> inventory.decrement(event.sku(), event.qty());
}
```

```yaml
spring:
  cloud:
    function:
      definition: orderEvents
    stream:
      bindings:
        orderEvents-in-0:          # <bean 名>-in-0 是输入通道
          destination: order.created
          group: inventory-svc     # 一个消费组 = 互相竞争的消费者
          consumer:
            concurrency: 3         # 线程数,上限由分区数决定
      kafka:
        binder:
          brokers: localhost:9092
```

关键在 `group` 这个词:`inventory-svc` 的每个实例都加入同一个组,分区在它们之间*被瓜分*,所以每条消息由整个组处理一次,而不是每个实例各处理一次。

## 分区、积压与重平衡

并行度有一个硬上限:**分区数**。Kafka 把每个分区只分给组里的一个消费者,所以六个分区最多只能跑六个有用的消费者——第七个只能**空转**,占着一个连接却什么也不做。

| 分区数 | 组内消费者 | 干活的 | 空闲的 |
|-------|-----------|-------|-------|
| 6 | 3 | 3(各读 2 个分区) | 0 |
| 6 | 6 | 6(各读 1 个分区) | 0 |
| 6 | 9 | 6 | 3 个白占 |

**积压(lag)** 是最新生产偏移量和消费组已提交偏移量之间的差。当生产速率超过消费速率,积压会无上限地涨——生产 5000 条/秒、消费 3000 条/秒,你每秒就落后 2000 条,而这堆欠账*就是*你多出来的端到端延迟。在治理台上把生产速率推到消费者消化不了的程度,看积压往上爬,再把消费者加到分区数以内,看它掉下来。

**重平衡(rebalance)** 在任何一个消费者加入或离开时发生:组会短暂暂停,重新分配分区。在这个「停顿」窗口里没有消息被处理,而任何还没提交的在途消息可能被重新投递给新的属主——这正是为什么每个消费者都必须幂等(见 sc15)。
