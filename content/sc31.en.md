## Config drifts

GW3 showed how a config change refreshes across a fleet, and the brief "mixed old and new" window while it propagates. That is a transient problem, gone in seconds. This chapter is about its slow, chronic cousin: **config drift**, where the configuration an instance is actually running gradually diverges from the configuration you declared — and stays diverged.

Drift has three classic sources. The first is the **manual hotfix**: it is 3 a.m., something is broken, and an engineer SSHes into a box (or hits an Actuator endpoint, or edits an env var) and changes a value to stop the bleeding. The incident ends, everyone goes back to bed, and the change is never put back into the config repository — that instance now runs a configuration no version-control system knows about. The second is the **missed refresh**: a change was pushed but only reached some instances (a network blip, a pod that was restarting), so the fleet is now inconsistent — permanently, not just for the refresh window. The third is **environment divergence**: a fix lands in prod but not in staging, and staging quietly stops being a faithful copy of prod, so it can no longer reproduce prod's bugs.

## Declared vs running state — the silent gap

The clean way to think about drift is two states. The **declared state** is what your source of truth — a Git repo, a config server, a set of manifests — says the configuration should be. The **running state** is what the processes are actually using right now. In a perfectly disciplined system these are identical; drift is any gap between them.

What makes drift dangerous is that the gap is silent. Nothing errors when it opens. Everything looks fine — until one instance behaves differently from its siblings because of a limit someone raised and forgot, or a security check someone disabled during an incident and never re-enabled, or you spin up a fresh environment straight from Git and it behaves nothing like production, and you lose a day discovering that production was never really what Git described. Drift does not announce itself; you go looking for it, usually while debugging something else.

## Detection: fingerprints and audits

You cannot fix what you cannot see, so the first move is to make drift visible. The trick is a **config fingerprint**: have each instance compute a hash of its effective configuration — the values it actually resolved, after all the layering of defaults, files, env vars and the config server — and expose it (a small Actuator endpoint). If the fleet is in sync, every instance reports the same hash; the moment one differs, you have found a drifted instance without diffing thousands of keys by hand.

A **periodic audit** turns that into a process: on a schedule, collect every instance's fingerprint, compare against the expected value derived from Git, and alert on any mismatch. This genuinely finds drift — but only as fast as the audit interval, and finding it is not fixing it. Someone still has to investigate and remediate, so there is always some drift in flight between an audit catching it and a human resolving it.

## Reconciliation: GitOps and immutable infrastructure

Detection tells you drift happened; reconciliation makes it not persist. The declarative, **GitOps** answer is a controller (Argo CD, Flux) that continuously compares running state to the Git-declared state and drives them together — and, crucially, auto-reverts drift. Turn on `selfHeal` and a hand-edit to the live configuration is simply undone within a sync cycle: Git is the source of truth, and anything not in Git is not allowed to survive. Drift can still occur, but it cannot last.

The strongest guarantee is to remove the possibility entirely with **immutable infrastructure**: bake configuration into an immutable image, forbid runtime changes, and deploy a new image to change anything. If nothing can be edited in place, nothing can drift. The approaches and their costs:

| Approach | What it does | Cost |
|---|---|---|
| No detection | nothing; drift accumulates silently | un-reproducible incidents |
| Periodic audit | fingerprint + diff on a schedule, alert | finds drift, but manual fix; interval-limited |
| GitOps (selfHeal) | continuous reconcile, auto-revert to Git | a controller to run; less ad-hoc freedom |
| Immutable infra | config baked in, no runtime edits | no drift possible; no quick in-place tweaks |

The through-line of all of them is one discipline: name a single source of truth, and make everything else answer to it. The bench shows the payoff — as you move from none to audit to GitOps, drifted instances and config incidents fall, and time-to-detect collapses from "never" to minutes.

## Exercises

1. Add an `/actuator/confighash` endpoint that hashes your feature flags and limits; deploy three replicas and confirm all three report the same hash.
2. Manually change one replica's value (via env or Actuator) and re-check the hashes; watch one diverge — you have just detected drift.
3. Write the audit loop: compare every replica's hash to the config-server value and print the drifted ones.
4. Put the same config under Argo CD with `selfHeal: true`; hand-edit the live value and watch it get reverted, then discuss when you would and would not want that.
