## At-least-once: redelivery is normal, not an accident

A broker can offer three delivery semantics, and it is worth being precise about them:

| Semantic | Guarantee | Cost |
|----------|-----------|------|
| At-most-once | never redelivers; may lose | cheap, unsafe for money |
| At-least-once | never loses; may redeliver | the practical default |
| Exactly-once | neither loses nor repeats | expensive, and local to one system |

Real brokers give you **at-least-once**, and the reason is structural. A consumer reads a message, does its work, and *then* commits the offset (Kafka) or acks (RabbitMQ). If it crashes after the work but before that commit, the broker has no idea the work was done and redelivers on restart. A dropped ack does the same: the consumer finished, the network ate the acknowledgement, the broker redelivers. So a "deduct 100" message can genuinely arrive twice, and a naive handler charges the user 200. Note that Kafka's "exactly-once" is real only *inside* Kafka (idempotent producer plus transactions); it cannot make your database write and an external payment gateway atomic. So you stop fighting redelivery and instead make the handler **idempotent**.

## Idempotency: a unique id plus a dedup check

Idempotent means running the handler N times has the same effect as running it once. The recipe: give every message a **unique business id** — an `orderId`, or a dedicated `messageId` — and check whether that id has already been processed before applying the effect.

Two implementations, with a sharp difference in correctness:

- **DB unique key (source of truth).** Insert the id into a `processed_message` table *in the same local transaction* as the business write. A redelivery hits the primary-key constraint, the transaction rolls back, and the effect never repeats. Atomic and durable.
- **Redis SET NX (fast filter).** `SET id 1 NX EX 86400` is quick, but Redis is a different system from your DB, so a crash between "Redis says new" and "DB commit" can wave a duplicate through. Use Redis to cheaply reject obvious repeats, and the DB unique key as the real guarantee.

One trap decides the whole thing: the dedup mark and the business effect must be in **one transaction**. Write the effect, then separately mark "seen", and a crash in between leaves the effect done but unmarked — the redelivery redoes it. And prefer **naturally idempotent** writes where you can: `UPDATE order SET status='PAID' WHERE status='PENDING'` affects zero rows on the second run, whereas `balance = balance - 100` deducts again every time.

## The dual-write problem

Now the harder half. Your handler usually must do **two** things: write the business row (to the DB) and publish an event (to the broker). These are two systems with no shared transaction, and no ordering saves you:

| Order | Crash lands… | Result |
|-------|--------------|--------|
| DB, then publish | after commit, before publish | event **lost** — downstream never told |
| Publish, then DB | after publish, before commit | **false** event — downstream acts on nothing |

Write the database first and the process can die before the event goes out: the order exists, inventory is never told, stock drifts. Publish first and the DB write can roll back: you have announced an order that does not exist, and inventory decrements for nothing. You cannot wrap a database and a broker in one ACID transaction without XA over heterogeneous systems — exactly the long-lock, low-availability path sc14 told you to avoid.

## The outbox pattern

The fix is to make the two writes **one** write. In the same local transaction that saves the business row, also insert the outgoing event into an **outbox** table in the same database. Now both commit or neither — ordinary single-DB ACID, no dual write left:

```sql
CREATE TABLE outbox (
  id           BIGINT       PRIMARY KEY AUTO_INCREMENT,
  aggregate_id VARCHAR(64)  NOT NULL,   -- e.g. the order id
  event_type   VARCHAR(64)  NOT NULL,   -- 'OrderCreated'
  payload      JSON         NOT NULL,
  created_at   DATETIME(3)  NOT NULL,
  published    BOOLEAN      NOT NULL DEFAULT FALSE,
  KEY idx_unpublished (published, id)
);
```

A separate **relay** then delivers the events. Two styles:

- **Polling publisher** — a scheduled job reads `WHERE published = FALSE ORDER BY id`, publishes each row to the broker, and marks it published. Simple, needs no extra infrastructure, at the cost of a little latency and constant polling.
- **CDC / log tailing** — a tool like Debezium tails the database's binlog and streams outbox inserts to Kafka. Near-zero latency and no app polling, at the cost of running Kafka Connect and Debezium.

The relay is itself at-least-once: if it publishes and then crashes before marking the row, it republishes on restart. That is not a flaw — it is why the outbox and idempotency are **partners**. The outbox guarantees the event is *never lost*; consumer idempotency guarantees a *replayed* event does no second harm. Together they give reliable eventual consistency. On the bench, turn the outbox off to watch an event vanish on a crash, turn idempotency off to watch a redelivery double-charge, then turn both on and confirm the numbers settle correctly.

## Exercises

1. Classify three operations in your system as naturally idempotent or not; for the ones that are not, name the unique id you would dedupe on.
2. Write the single local transaction that inserts both an `orders` row and an `outbox` row; explain what a consumer sees if the process crashes right after commit but before the relay runs.
3. On the bench, disable idempotency and send the same "deduct" event twice; record the balance, then enable the DB unique-key dedup and repeat.
4. Compare polling-publisher and CDC relays for a 2,000-events/second service: estimate the added latency and the operational cost of each, and pick one.
