## 至少一次:重复投递是常态,不是意外

一个消息中间件可以提供三种投递语义,值得把它们说精确:

| 语义 | 保证 | 代价 |
|------|------|------|
| 至多一次 | 绝不重投;可能丢 | 便宜,但对钱不安全 |
| 至少一次 | 绝不丢;可能重投 | 实际中的默认 |
| 恰好一次 | 既不丢也不重 | 昂贵,而且只在单个系统内成立 |

真实的中间件给你的是**至少一次**,原因是结构性的。消费者读一条消息,把活干了,*然后*才提交偏移量(Kafka)或 ack(RabbitMQ)。如果它在干完活、还没提交之前崩了,中间件根本不知道活已经干过,重启后就重投。丢一个 ack 也一样:消费者干完了,网络把确认吃掉了,中间件重投。于是一条「扣 100」的消息真的可能来两次,而一个天真的处理器会扣用户 200。注意 Kafka 的「恰好一次」只在 Kafka *内部*成立(幂等生产者加事务);它没法让你的数据库写入和一个外部支付网关变成原子的。所以你不再跟重投较劲,而是把处理器做成**幂等**的。

## 幂等:唯一 ID 加一次去重检查

幂等就是把处理器跑 N 次和跑一次效果相同。配方是:给每条消息一个**唯一业务 ID**——一个 `orderId`,或一个专门的 `messageId`——在施加效果之前,先检查这个 ID 是否已经处理过。

两种实现,在正确性上有一条尖锐的分界:

- **数据库唯一键(真相来源)。** 把这个 ID 插进一张 `processed_message` 表,*和业务写入在同一个本地事务里*。重投会撞上主键约束,事务回滚,效果绝不重复。原子且持久。
- **Redis SET NX(快速过滤)。** `SET id 1 NX EX 86400` 很快,但 Redis 是和你数据库不同的系统,所以在「Redis 说是新的」和「数据库提交」之间崩一次,就可能放过一个重复。用 Redis 便宜地挡掉明显的重复,用数据库唯一键做真正的保证。

有一个陷阱决定成败:去重标记和业务效果必须在**同一个事务**里。先写效果、再另外标一个「见过了」,中间崩一次,就留下效果已做却没标记的状态——重投会把它再做一遍。能用**天然幂等**的写法就尽量用:`UPDATE order SET status='PAID' WHERE status='PENDING'` 第二次跑影响 0 行,而 `balance = balance - 100` 每跑一次就再扣一次。

## 双写问题

现在是更难的那一半。你的处理器通常必须做**两**件事:写业务行(到数据库)和发事件(到中间件)。这是两个没有共享事务的系统,而且没有任何顺序能救你:

| 顺序 | 崩溃落在… | 结果 |
|------|----------|------|
| 先库,后发 | 提交之后、发送之前 | 事件**丢失**——下游永远不知道 |
| 先发,后库 | 发送之后、提交之前 | **假**事件——下游对着不存在的东西动作 |

先写数据库,进程可能在事件发出去之前就死:订单存在了,库存却没被通知,库存数据开始漂移。先发事件,数据库写入可能回滚:你宣告了一个并不存在的订单,库存白扣了一次。你没法把一个数据库和一个中间件裹进一个 ACID 事务里,除非用跨异构系统的 XA——那正是 sc14 让你避开的长锁、低可用的路。

## 发件箱模式

修法是把两次写变成**一次**写。在保存业务行的同一个本地事务里,把要发出去的事件也插进同一个数据库里的一张**发件箱(outbox)**表。现在要么都提交、要么都不提交——就是普通的单库 ACID,不再有双写:

```sql
CREATE TABLE outbox (
  id           BIGINT       PRIMARY KEY AUTO_INCREMENT,
  aggregate_id VARCHAR(64)  NOT NULL,   -- 比如订单 id
  event_type   VARCHAR(64)  NOT NULL,   -- 'OrderCreated'
  payload      JSON         NOT NULL,
  created_at   DATETIME(3)  NOT NULL,
  published    BOOLEAN      NOT NULL DEFAULT FALSE,
  KEY idx_unpublished (published, id)
);
```

然后由一个单独的**投递器(relay)** 把事件发出去。两种风格:

- **轮询投递** ——一个定时任务读 `WHERE published = FALSE ORDER BY id`,把每行发到中间件,再标记已发。简单,不需要额外基础设施,代价是一点延迟和持续的轮询。
- **CDC / 日志追踪** ——像 Debezium 这样的工具追踪数据库的 binlog,把发件箱的插入流式送到 Kafka。近乎零延迟、应用不用轮询,代价是要运维 Kafka Connect 和 Debezium。

投递器本身也是至少一次:如果它发出去、还没标记那行就崩了,重启后会重发。这不是缺陷——这正是发件箱和幂等是**搭档**的原因。发件箱保证事件*绝不丢失*;消费者幂等保证一个被*重放*的事件不造成第二次伤害。两者合起来,给你可靠的最终一致。在治理台上,把发件箱关掉,看一次崩溃让事件消失;把幂等关掉,看一次重投扣两次钱;再把两者都打开,确认数字最终对上。

## 练习

1. 把你系统里的三个操作分类为天然幂等或非天然幂等;对不是的那些,说出你会拿哪个唯一 ID 去重。
2. 写出那一个既插入 `orders` 行、又插入 `outbox` 行的本地事务;解释如果进程恰好在提交之后、投递器运行之前崩溃,消费者会看到什么。
3. 在治理台上关掉幂等,把同一个「扣款」事件发两次;记录余额,再打开数据库唯一键去重,重复一次。
4. 为一个每秒 2000 事件的服务对比轮询投递器和 CDC 投递器:估算各自增加的延迟和运维成本,选一个。
