## 一个功率异常检测服务,数据从哪来?

上一章把一个 Python 时序服务接进了 Spring Cloud——网关、注册、发现都通了,它能被访问、能被发现。但一个真正要落地的服务,最难的一步还没解决。设想一个具体场景:ERP 里要做功率监控和异常检测,你训练了一个时序模型,包成 Python 服务。现在的问题不是「它怎么被调用」,而是**它的数据从哪来、结果往哪去**——而这一步,是大多数人第一天就会做错的地方。

几乎所有人的第一反应,是把 Python 直接连上 Java 业务服务那个数据库:反正数据都在里面,一个 `create_engine("mysql://...")` 就开干了。在线要判异常?查库。要训练?把三个月的历史 `SELECT` 出来。简单、直接、当天就能跑。

这一章要讲清楚的,就是为什么这条最短的路是错的,以及正确的路怎么按「在线」和「训练」两种负载分开走。核心只有一句:**业务数据归 Java 服务所有,Python 一律不直连它的 OLTP 库。**

## 红线:不共享业务库(OLTP)

「Python 直连业务库」在微服务里有个正式的名字:**共享数据库反模式**。它的代价分三层,一层比一层疼。

**schema 耦合**。你的 Python 代码现在硬编码了 Java 服务的表结构。哪天 Java 团队做一次数据库迁移——改个列名、拆张表、加个非空约束——他们不会通知你,因为在他们眼里那是自己服务的内部实现。于是你的服务在某个凌晨毫无征兆地崩了。微服务本该让两个团队独立演进,直连业务库把这个前提直接废掉了。

**绕过业务逻辑**。那些校验、权限、审计、状态机,都写在 Java 服务的代码层,不在数据库里。你的 Python 直连绕过了这一整层——读到的可能是没经过校验的中间态,写进去的会跳过所有业务规则。而对一个要触发告警、要开工单的异常检测服务来说,「跳过业务规则」几乎等于制造事故。

**抢占交易资源**。这是最致命、也最容易被低估的一层。业务 OLTP 库是给高频、短小的交易事务用的,它怕两样东西:锁,和大扫描。而你的训练拉数恰恰是一次几百万行的大扫描。当这个扫描和正常业务抢同一个库,业务的 P99 会以你意想不到的速度恶化——这不是线性变差,是排队论意义上的**非线性爆炸**:利用率越接近 1,延迟越是往上飙。治理台用一个真实的排队模型让你看这件事:把业务负载拉到 2000 qps、再让直连训练去扫库,利用率冲到 0.83,业务 P99 直接翻了近三倍;再加点负载,系统就过载了——你用一次训练拉数,亲手把交易系统打垮了。

## 在线走事件,训练走 CDC→分析库

「不直连」不等于「只能调接口」。关键洞察是:**在线和训练是两种完全不同的负载,该走两条完全不同的路。**

**在线实时——走事件。** 对每一条新读数打分判异常,这种「随数据到达而触发」的负载,天生就是事件驱动的形状。让 Java 侧在保存读数时,把一条遥测事件发到 Kafka(Spring Cloud Stream);Python 订阅这个 topic,来一条打一条分。它不查库、不轮询,数据被推给它;它还天然解耦(Java 不需要知道有个 Python 在听),还能靠分区数扩并行度。在线这条路,Python 全程不碰业务库。

**批量训练——走 CDC 到分析库。** 拉几百万行历史喂模型,这条路有两个都不能选的诱惑:一是用 REST 接口翻页硬拉——太慢(翻页加序列化),而且请求最终还是压在业务库上;二是直连主库扫——就是上一节那条红线。正确的做法是引入一条数据管道:用 **CDC(Debezium/Canal)**追业务库的 binlog,把 OLTP 的行变更**增量**同步到一个专门的**分析库**(TimescaleDB / ClickHouse)。Python 直连这个分析库跑 SQL。

这里有个很多人会卡住的点:**连分析库,不也是「直连库」吗?为什么这个可以?** 因为红线针对的从来不是「任何数据库」,而是「别人家服务的交易库」。分析库是数据侧自己拥有的、列存、读优化的库,它存在的全部意义就是给你这种批量分析读的;它的 schema 是一个建模过的、稳定的分析层,那张表本身就是契约。你连它,既不耦合 Java 的交易表,也不和业务抢 OLTP 的资源(CDC 只追 binlog,不跑大查询)。**OLTP 管交易,OLAP 管分析,物理分开**——这是数据领域几十年的老规矩,微服务只是让它更该被遵守。

至于 Python 自己算出来的东西——模型文件、特征、每条读数的异常分数、阈值——那是 Python 自己的数据,存 Python 自有库。业务库不是它的家。

## 异常回流:结果写回也要经 Java

数据进来的路走对了,还有一半:**结果出去的路。** Python 判出一个异常,接下来要触发告警、要开工单、要通知运维——它该怎么把这个结果写回系统?

答案和进来时对称:**不要 INSERT 进业务库,发一条异常事件回 Kafka。** 由 Java 的告警/工单服务订阅这条事件,再由它去落库、开工单、走审批流。为什么绕这一圈?因为「开工单」不是一次写库,是一串业务逻辑:要校验这个设备存不存在、要按规则决定工单等级、要写审计、要防重复。这些全在 Java 服务里。Python 直接 INSERT 进工单表,会跳过所有这些——你会得到一张状态不对、没走审批、还可能重复的工单。

而「防重复」在这里尤其关键。异常事件可能被重复投递(Kafka 的 at-least-once),同一个「设备 A 在 12:03 功率异常」可能到两次。所以消费端必须**幂等**:用 `(设备号, 时间戳)` 做去重键,第二次到达时认出「这个工单已经开过」,直接跳过(回顾 TX3 的幂等与发件箱)。异常检测服务尤其容易在这里翻车——模型对同一段异常连续打出多条告警,不做幂等,运维半夜会被同一个故障的几十条工单淹没。

一句话收尾:**数据进来,在线走事件、训练走 CDC→分析库;结果出去,经 Java 回流并幂等。** Python 时序服务因此成了系统里一个干净的、解耦的、既不拖垮业务库也不绕过业务规则的成员——它只做它该做的:把数据变成异常信号。
