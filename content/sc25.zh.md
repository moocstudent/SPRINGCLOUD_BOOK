## 两种内核

Spring Cloud Stream 让你换一个 binder 依赖、改几行 YAML 就能从 Kafka 切到 RabbitMQ。这确实有用——但它也容易让你误以为两者可以互换。它们不能。在同一套编程模型底下,坐着的是两台原理完全不同的机器;上面的治理台之所以要按你的要求现算契合度,正是因为正确答案取决于工作负载,而不是取决于流行度。

**Kafka** 本质是一个分布式的分区提交日志。一个主题被切成若干分区,每个分区是磁盘上一条只能追加的消息序列,按保留期留存(几小时、几天,或永久)。生产者往末尾追加;消费者靠持有一个 **offset**(指向日志的指针)来读,读到哪就把 offset 往前挪。消费者读取时不会删除任何消息,消息一直留到保留期到期。它的吞吐极高,因为往日志追加是顺序磁盘 IO、消息还能批量处理,而且加分区就能水平扩展。

**RabbitMQ** 本质是一个围绕 AMQP 模型的智能 broker。生产者不是把消息发给队列,而是发给**交换机(exchange)**,交换机再按绑定规则和路由键把每条消息路由到零个或多个队列。消费者订阅队列、被**推送**消息,并逐条确认(ack),一旦确认,消息就从队列里删除。路由的活儿由 broker 干——这很强大——但 broker 也因此成了瓶颈。

## 回放、顺序、确认:同一个词,两种含义

体会差别最直接的办法,是三个听起来一样、行为却不同的能力。

**回放。** 在 Kafka 里,因为消息持久保留、消费者自己记录 offset,任何消费组都可以倒回 offset 0 重新处理全部历史——这对事件溯源、重建读模型、或从消费者的 bug 中恢复,都极其宝贵。在 RabbitMQ 里,消息一旦被 ack 就没了,经典队列没有「倒带」。(较新的 Streams 插件补上了类似日志的回放,但那其实是 RabbitMQ 在借用 Kafka 的模型。)

**顺序。** Kafka 保证**分区内**有序。如果一个订单的所有事件必须按序处理,你就用订单 ID 做 key,让它们落到同一个分区。RabbitMQ 在「单队列、单消费者」时保证顺序——但你一旦为了提高吞吐加了竞争消费者,或者某条消息失败后被重新入队,顺序就不再有保证。

**确认与投递。** Kafka 消费者是拉取并提交 offset,慢的消费者只是落后,背压是天然的。RabbitMQ 则在 prefetch 上限内把消息推给消费者、要求逐条 ack,由此换来细粒度的控制——拒绝、重新入队、把单条消息投进死信队列——延迟也更低,代价是每条消息都要多做记账。

## 路由

这正是 RabbitMQ 的强项。它的交换机类型——direct、topic、fanout、headers——让 broker 按灵活规则把一条消息路由到多个队列,而生产者根本不必知道谁在消费。fanout 广播给所有绑定的队列;topic 按 `order.*.eu` 这样的路由键匹配;headers 按属性匹配。Kafka 没有交换机:路由就是主题加分区 key,更细的筛选发生在消费端——它把全部读下来再自己过滤。如果你的系统需要丰富的、服务端的路由拓扑,RabbitMQ 能直接表达;在 Kafka 里你得自己搭。

## 按工作负载选型

没有普适的赢家。像治理台那样,把中间件匹配到需求上:

| 需求 | 更适合 | 为什么 |
|---|---|---|
| 极高吞吐(10 万+/秒) | Kafka | 分区日志、顺序 IO、随分区扩展 |
| 回放 / 事件溯源 | Kafka | 消息保留,消费者按 offset 倒带 |
| 严格的按 key 顺序 | Kafka | 分区内有序 |
| 复杂路由拓扑 | RabbitMQ | 交换机:direct / topic / fanout / headers |
| 任务队列 / 工作分发 | RabbitMQ | 竞争消费者、逐条 ack、重入队 |
| 低延迟、逐条控制 | RabbitMQ | 推送投递、细粒度 ack、死信 |

一条粗略的经验:当数据是一条你可能想留存、回放、并高吞吐处理的**事件流**时,选 Kafka;当数据是要**交给某个 worker 去做的活儿**、需要巧妙路由、并逐条确认时,选 RabbitMQ。

再想想上一章:因为 Stream 抽象了 binder,你可以把决定往后推,先在团队熟悉的那个上做原型,以后靠改配置(而不是改代码)再切:

```yaml
# 同样的 bindings,不同的 binder —— 完整的一对见代码面板
spring.cloud.stream.kafka.binder.brokers: kafka:9092      # 或者……
spring.cloud.stream.rabbit.bindings...:  exchange-type: topic
```

唯一无法便宜地改变的,是一个中间件从根上就不提供的能力——所以让这个硬需求、而不是 binder,来决定你的选型。

## 练习

1. 用 docker compose 起 Kafka 和 RabbitMQ,让同一个 Stream 服务分别通过 `application-kafka.yml` / `application-rabbit.yml` 指向它们,确认 Java 代码一个字节都没改。
2. 在 Kafka 上设 `start-offset: earliest` 并重启一个消费组,看它把整个主题重新处理一遍。在 RabbitMQ 经典队列上试同样的事,体会「没有等价物」。
3. 在 RabbitMQ 上声明一个 topic 交换机,用路由键 `order.*.eu` 和 `order.*.us` 绑两个队列;用不同的 key 发布,看 broker 路由。再在 Kafka 里复刻同样的 fan-out,记下你不得不自己搭了哪些东西。
4. 给一个 RabbitMQ 队列和一个 Kafka 分区各加一个竞争消费者;把一条按 key 有序的流推过去,对比顺序是否还守得住。
