## One instance is not enough: the N× problem

In GW2 you put a token bucket in front of a service and capped it at, say, 1000 requests per second. That works — for one process. But you never run one gateway in production; for availability and throughput you run a fleet of replicas behind a load balancer, ten or twenty of them. And now the limit you so carefully set is quietly broken.

The reason is that each replica has its own bucket, in its own memory. If you configure `replenishRate: 1000` on each of ten gateways — the obvious thing to do, and the most common mistake in the field — then each admits a thousand per second and ten thousand get through. Your "1000 rps limit" is now a 10,000 rps limit. Local buckets do not add up into one global bucket; they multiply.

The obvious fix — give each replica 1/N of the quota, 100 rps each — is also wrong, just more subtly. Load balancers do not spread traffic perfectly evenly. A replica that receives more than its share exhausts its 100 and starts rejecting, while others sit under their limit — so you reject legitimate requests even though the global rate is well under 1000. The bench shows both failures: local buckets overshoot when set to the global value, and under-serve when split and the load is skewed.

## A shared counter and atomicity

The only way to enforce a global limit is to count in one shared place every replica consults. In practice that place is Redis: for each request, a gateway does a check-and-decrement against a single counter (or token bucket) keyed by the client. Because all replicas hit the same key, the quota is exact no matter how many gateways there are or how skewed the load is.

There is a subtlety that will bite you if you miss it: the check and the decrement must be **atomic**. If a gateway reads "1 token left", and a second gateway also reads "1 token left" before the first writes back "0", both admit and you have overshot. You cannot do read-then-write from the application; the whole operation must be a single indivisible step. Redis provides exactly this with server-side **Lua scripts** — the script runs to completion on Redis with nothing interleaved. Spring Cloud Gateway's `RequestRateLimiter` is built precisely this way: a Redis-backed token bucket whose refill-and-decrement is a Lua script, with `replenishRate` and `burstCapacity` as global, fleet-wide values.

## Three algorithms

Once counting is shared, you still choose how to count. The common algorithms trade accuracy against cost:

| Algorithm | Idea | Trade-off |
|---|---|---|
| Fixed window | count per 1-second bucket, reset on the boundary | cheapest; suffers the boundary burst (up to 2× at an edge) |
| Sliding window log | store each request's timestamp, count the last second | exact; memory-heavy (one entry per request) |
| Sliding window counter | weight the current and previous window by overlap | smooths the boundary burst, cheap, slightly approximate |
| Token bucket | refill tokens at a rate, spend one per request | smooth and burst-friendly; the Gateway default |

The boundary-burst problem of the fixed window is worth internalising: with a per-second reset, a client can send 1000 requests at 0.999 s and another 1000 at 1.001 s — 2000 in about two milliseconds, all "within limits". The sliding window counter and the token bucket both avoid this, which is why they, not the naive fixed window, are what you actually want.

## The cost

A shared limiter is correct, but not free, and its costs shape real designs. Every request now makes a **Redis round-trip** before it is even routed — a fraction of a millisecond, but on the hot path of every call. And Redis now takes one operation per request across the whole fleet, which makes it a **hotspot and a single point of failure**: if Redis is slow, every request slows; if Redis is down, you must decide whether to fail open (allow everything) or fail closed (reject everything).

Production systems soften this with a **local-plus-global hybrid**: each gateway keeps a small local allowance and only synchronises with Redis periodically, so most requests are decided locally and Redis sees far less traffic — trading a little accuracy at the edges for a large cut in round-trips. The rule to remember: a global limit needs a shared store, a shared store needs atomicity, and the round-trip it costs is the price of a limit that actually holds.

## Exercises

1. Run two gateway replicas with a local (in-memory) rate limiter set to 1000; drive load and confirm ~2000 get through. Switch to the Redis limiter and confirm it holds at 1000.
2. Read Spring Cloud Gateway's `request_rate_limiter.lua` and trace how refill and decrement happen in one atomic call.
3. Demonstrate the fixed-window boundary burst: send a burst straddling a window edge and observe up to 2× the limit; then switch to a sliding window and watch it disappear.
4. Kill Redis while the limiter is running and observe the fail-open vs fail-closed behaviour; decide which your API should choose and configure it.
