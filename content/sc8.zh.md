## 住在调用方肚子里的负载均衡

在实例前面架一台反向代理——一台 Nginx、一个 ELB——每个请求都要多穿过一个盒子,而这个盒子对你的服务一无所知,只会发个健康检查的 ping。Spring Cloud 的做法不一样:负载均衡器住在**调用方内部**。客户端从注册中心(见 sc4)拿到活着的实例清单,每次调用自己挑一个。这件事最早是 Ribbon 做的,它已经退役;Boot 3 上受支持的实现是 Spring Cloud LoadBalancer。

为什么住在里面更好?因为调用方掌握着代理拿不到的信息。注册中心一更新,它立刻知道完整的实例集合。它知道**自己**此刻对每个实例有多少个在途请求。它还省掉一次网络跳转。代价是每种客户端语言都得有自己的一套负载均衡实现,而它们可能各自漂移——在多语言的公司这是一笔真实的税,在清一色 Spring 的公司则不成问题。

## 轮询为什么会害了你

默认策略是轮询:把每个请求依次发给清单里的下一个实例。当每个实例都一模一样时,它正确又公平。可实例很少一模一样:有的跑在更小的节点上,有的正在 GC,有的是刚起的新 Pod、JIT 还没热,有的正在悄悄地坏。轮询照旧把它那 1/N 的份额发给那个慢实例——这些请求就堵在它的慢后面排队、超时,把你的尾延迟拉高,而平均值几乎纹丝不动。

@fig sc8-lb

上数字。十个实例,九个 25 毫秒响应,一个劣化到 500 毫秒。轮询把 10% 的流量发给那个坏节点。**平均**延迟是 (9 × 25 + 500) / 10 ≈ 73 毫秒——评审时你会签字放行的数。但 10% 的用户等了 500 毫秒,于是你的 **P99 是 500 毫秒**,差了二十倍。平均值告诉你一切正常,而每十个请求就有一个跌下了悬崖。这就是为什么你要用尾部、而绝不是用均值来评价一个负载均衡器。

## 四种策略

| 策略 | 怎么挑 | 需要知道 | 什么时候最合适 | 会在哪里出问题 |
|---|---|---|---|---|
| 轮询 | 依次下一个实例 | 什么都不用 | 实例真正一模一样 | 把整份额发给最慢的节点 |
| 随机 | 均匀随机挑一个 | 什么都不用 | 大集群、不想要协调 | 一样的尾部问题,还没有记忆 |
| 最少连接 | 在途请求最少的那个 | 每个实例的实时在途数 | 速度不均、开销多变 | 可能一窝蜂涌向一个刚恢复的节点 |
| 响应时间加权 | 权重 ∝ 1 / 近期延迟 | 每个实例的延迟滑动平均 | 硬件混杂、对尾部敏感 | 反应慢;没样本的冷节点看起来最快 |

实例不均时,最少连接是务实的默认:慢节点把在途请求越攒越多,它的计数往上爬,负载均衡器自然就不再往它身上发新请求——它不需要谁告诉它哪个节点慢,就自己**绕开**了慢。响应时间加权更锐利,但需要跟踪延迟,而且会被一个「只是还没样本」的冷实例骗到。

Spring Cloud LoadBalancer 开箱只带轮询(默认)和随机,外加健康检查过滤和一个基于 `weight` 的供应器。最少连接和响应时间加权它没有内置——你得实现 `ReactorServiceInstanceLoadBalancer`,再按客户端接上去:

```java
@Configuration
@LoadBalancerClient(name = "inventory", configuration = InventoryLbConfig.class)
public class AppConfig { }

class InventoryLbConfig {
    @Bean
    ReactorLoadBalancer<ServiceInstance> lb(Environment env,
            LoadBalancerClientFactory factory) {
        String name = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        // 这里放的是内置 Random,换成你自己的最少连接实现即可
        return new RandomLoadBalancer(
            factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
    }
}
```

## 看 P99,不看平均

这个教训能推广到负载均衡之外:在任何有扇出的系统里,均值是你能盯着看的、最令人安心也最没用的那个数。一个请求碰了五个服务,每一步都继承这五个里**最慢**的那个,尾延迟因此层层叠加。在治理台上把请求速率调高,直接看:平均值一路平着,P99 却往上爬,因为饱和总是先在尾部露头,很久之后才动得了均值。在池子里留一个劣化实例,把策略从轮询切到最少连接,看 P99 怎么落回健康基线附近,而平均值几乎没眨眼。

3. 打开 Spring Cloud LoadBalancer 的健康检查过滤,说清它和负载均衡**策略**有什么不同——两者各自防的是什么?
